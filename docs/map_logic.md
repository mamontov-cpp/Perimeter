# Загрузка уровней в Perimeter: как это устроено

## 1. Форматы файлов уровня

Уровень (миссия) хранится набором файлов с общим префиксом имени:

| Расширение | Содержимое |
|---|---|
| `.spg` | Основной файл: `MissionDescriptionPrm` + `SavePrm` (архив XPrm) |
| `.sph` | Только заголовок `MissionDescriptionPrm` (без данных сохранения) |
| `.bin` | Сжатые бинарные данные: `SavePrmBinary` + изменения карты + региональные данные (+ команды реплея с 3.0.8) |
| `.gmp` / `.dat` | Устаревший формат: `.gmp` = изменения карты, `.dat` = регионы |

Сам мир (рельеф) лежит отдельно в `RESOURCE/Worlds/<мир>/`: `output.vmp` (заголовок `S2T0` — сырые данные, или `S2T1` — сжатые), `world.ini`, `cache.tga`.

#  Сражение

В режиме «Сражение» (Battle/Skirmish) загрузку карты отвечает в первую очередь **`Source/UserInterface/BattleMenu.cpp`**, а дальше поток сливается с общим пайплайном загрузки миссии. По шагам:

- **`loadBattleList()`** (строки 39–44): лениво, один раз, сканирует каталоги `RESOURCE/BATTLE` и `RESOURCE/BATTLE/SCENARIO` на `.spg` через `loadMapVector(battleMaps, paths, ".spg", false)` — в глобальный вектор `battleMaps`.
- Вызывается из **`MainMenu.cpp:908`** (`SwitchMenuScreenQuant2`) при показе главного меню.

## 2. Выбор карты в UI — `BattleMenu.cpp`

- **`onBattleMenuOpening()`** (строка 274): заполняет списокbox именами карт, сбрасывает цвета/слоты игроков.
- **`setCurrentMission(pos)`** (строка 229): при выборе карты вызывает **`checkMissionDescription(pos, battleMaps, GT_SINGLE_PLAYER)`** и копирует описание в глобальный `missionToExec`.
- **`checkMissionDescription()`** (`MainMenu.cpp:273–283`) — ключевая функция «ленивой» загрузки: при сканировании списка читался только заголовок (имя), а если `worldID() == -1`, здесь происходит полное чтение `.spg`:
  ```cpp
  mVect[index] = MissionDescription(filepath, gameType); // filepath = savePathKey()
  ```

## 3. Запуск — `startBattle()` (`BattleMenu.cpp:316–357`)

Вызывается по двойному клику на карте (**`onMMMapList`**, строка 359) или кнопке Go (**`onMMBattleGoButton`**, строка 377):
- Если **все слоты закрыты** — это режим Survival: ищется отдельный файл `Resource/BATTLE/SURVIVAL/<имя>.spg` (**`getSurvivalFileName()`, строка 304**) и `missionToExec` заменяется на его описание.
- Записывает в `MissionDescription` настройки из UI: фракции, сложность ИИ, хеникапы (`copyToMD()`), цвета и тип игрока/ИИ для каждого слота (строки 342–349).
- **`missionToExec.shufflePlayers()`** — случайная расстановка игроков по сторонам.
- Устанавливает `lastGameType = BATTLE` или `SURVIVAL`, затем переключает экран на `SQSH_MM_LOADING_MISSION_SCR`.

## 4. Общий пайплайн запуска — `MainMenu.cpp:680–712`

В `SwitchMenuScreenQuant2` при переходе на экран загрузки по `lastGameType` выставляется номер миссии:
- **BATTLE → `missionToExec.missionNumber = -1`** (строка 697) — именно это отличает сражение от кампании (`isCampaign()` требует `missionNumber >= 0`);
- SURVIVAL → `-2`.

Затем вызывается **`HTManager::instance()->GameStart(missionToExec)`**.

## 5. Дальше — общий путь (как в любом режиме)

- **`Runtime.cpp:546`** `HTManager::GameStart()` → создаёт `terUniverse`;
- конструктор **`HyperSpace.cpp:165–166`**: `vMap.selectUsedWorld(mission.worldID())` + `vMap.fullLoad(...)` — загрузка мира (рельефа) из `RESOURCE/Worlds/<мир>/output.vmp`;
- **`Universe.cpp:904`** `loadUnitAttributes(campaign=false, ...)` — для сражения загружаются обычные (не campaign) атрибуты юнитов;
- **`GameShell.cpp:1367`** `universalLoad()` → чтение `.spg`/`.bin` карты и восстановление состояния.

Итог: специфика «Сражения» целиком в `BattleMenu.cpp` (сканирование `RESOURCE/BATTLE`, выбор, расстановка игроков, survival-файлы) + установка `missionNumber = -1` в `MainMenu.cpp`; сама загрузка мира и данных карты идёт по общему пути через `GameStart → terUniverse/terHyperSpace → universalLoad`.


# Устройство уровней



Теперь у меня достаточно информации для полного ответа. Вот подробное описание каждого файла.

---

## Файлы мира (`RESOURCE/Worlds/<имя_мира>/`)

### `world.ini`
**Назначение:** Главный конфигурационный файл мира. Содержит все параметры карты и генерации.

**Формат:** INI-файл с секциями. Ключевые секции и параметры:

```ini
[Global Parameters]
Map Power X = 11          ; log2(ширина карты), H_SIZE = 1<<N
Map Power Y = 11          ; log2(высота карты), V_SIZE = 1<<N
GeoNet Power = 5          ; log2(размер ячейки географической сетки)
Section Size Power = 5    ; log2(размер секции рендеринга)
Minimal Square Power = 3  ; log2(минимальный квадрат)
hZeroPlast = 30           ; начальная высота зеропласта

[Storage]
Version = 1.4             ; версия формата (строгая проверка)

[Creation Parameters]
Mesh Value = 200          ; GeonetMESH — размер шага сетки генерации
Noise Amplitude = 255     ; амплитуда шума при генерации
Default Terrain Type = 0  ; тип террейна по умолчанию

[3DF Parameters]
ScalingXYZ = 64 64 32     ; коэффициенты масштабирования kmx/kmy/kmz для f3d
Function = 0              ; номер функции 3D-текстуры (0=Marble, 1=Tree)

[GeoPal Parameters]
NumbersKey = 4            ; количество ключей палитры
Colors = r0 g0 b0 r1 g1 b1 ...  ; (numbers+1) цветов RGB через пробел
Keys = k0 k1 k2 ...       ; numbers высотных ключей
```

**Кто читает/пишет:** `VMAP.cpp::analyzeINI()` читает параметры; `f3d.cpp::saveVariable()/loadVariable()`读写 секцию `[3DF Parameters]`; `f3d.cpp::sKeyGeoPal::loadKeyGeoPal()/saveKeyGeoPal()` — секцию `[GeoPal Parameters]`.

---

### `output.vmp`
**Назначение:** Основной бинарный файл с данными рельефа карты — высоты, дамбы, атрибуты, поверхности.

**Формат:**
```
[Заголовок sVmpHeader — 20 байт]
  char[4] id   : "S2T0" (несжатый) или "S2T1" (zlib-сжатый)
  int32   XS   : ширина карты
  int32   YS   : высота карты
  int32   NX   : (служебный)
  int32   NY   : (служебный)
[Данные — после заголовка]
  VxGBuf[XS*YS] : 1 байт/пиксель — целая часть высоты рельефа (гео-слой)
  VxDBuf[XS*YS] : 1 байт/пиксель — дробная часть высоты (дамба/вода)
  AtrBuf[XS*YS] : 1 байт/пиксель — атрибуты клетки (At_LEVELED, At_ZEROPLAST...)
  SurBuf[XS*YS] : 1 байт/пиксель — индекс поверхности/типа террейна
```
Если `id == "S2T1"`, блок данных сжат zlib и распаковывается при загрузке.

**Как формируется:** Генерируется редактором SurMap3 (`buildWorld()` → `partWrite()`) или сохраняется из игры (`save3BufOnly()`). При отсутствии файла мир генерируется процедурно из `output.vsc` (см. ниже).

**Кто читает:** `VMAP.cpp::fullLoad()`.

---

### `output.vpr`
**Назначение:** Состояние генератора сети географии (`r_net_map`, `m_net_map`) — промежуточные данные процедурной генерации, позволяющие воспроизводить мир детерминированно.

**Формат:**
```
int32   RNDVAL
int32   realRNDVAL
int32   GeonetMESH
int32[8] (зарезервировано)
uint16[net_size]  r_net_map  — вещественная сеть
uint16[net_size]  m_net_map  — мнимая сеть
int32[GEONET_POWER]  r_preRNDVAL
int32[GEONET_POWER]  m_preRNDVAL
int32[PART_MAX*MAX_POWER]  r_cycleRNDVAL
int32[PART_MAX*MAX_POWER]  m_cycleRNDVAL
```
`net_size = H_SIZE * V_SIZE / (1<<GEONET_POWER)^2`

**Как формируется:** `SaveVPR()` при генерации мира в редакторе. Если файла нет — сети инициализируются нулями (`r_net_init()`/`m_net_init()`).

**Кто читает:** `VMAP.cpp::LoadVPR()`.

---

### `output.vsc`
**Назначение:** Сценарий построения мира (build scenario) — параметры генерации для каждой горизонтальной секции карты.

**Формат:** Последовательность записей по 5 int32 на секцию:
```
uint32 partIndex  (обычно 0,1,2,...)
uint32 minAlt     (минимальная высота, в единицах до сдвига VX_FRACTION)
uint32 maxAlt     (максимальная высота)
uint32 noise      (уровень шума)
uint32 minsquare  (минимальный квадрат)
```
Чтение прекращается при записи `0 0 0`.

**Как формируется:** Создаётся в редакторе SurMap3 вручную.

**Кто читает:** `worldGen.cpp::LoadPP()` — заполняет массив `PartPrm[]`, который используется при генерации рельефа.

---

### `geoPal.xml`
**Назначение:** XML-палитра типов поверхности (гео-палитра). Используется вместо `inGeo.act` при сборке с библиотекой `tx3d`.

**Формат:** XML с тегом `<colorTable>`, содержащим ровно 256 тегов `<color>`:
```xml
<colorTable>
  <color value="r0,g0,b0"/>
  <color value="r1,g1,b1"/>
  ...256 записей...
</colorTable>
```
Значения r,g,b — нормализованные float `[0..1]`.

**Как формируется:** Экспортируется из tx3d-редактора или `IndexedTexture3D::colorTableToXML()`.

**Кто читает:** `VMAP.cpp::loadGeoDamPal()` (при `#ifdef _TX3D_LIBRARY_`), через `tx3d::IndexedTexture3D::extractColorTableFromXML()`.

---

### `inGeo.act`
**Назначение:** Бинарная гео-палитра (256 цветов RGB) — тип поверхности для каждого индекса. Используется, когда сборка **без** `tx3d`.

**Формат:** Ровно `SIZE_GEO_PALETTE = 256*3 = 768` байт, порядок **BGR** (аналогично Adobe Photoshop .act без заголовка).

**Как формируется:** Сохраняется из редактора `saveGeoDamPal()`. Может быть сконвертирован из `geoPal.xml`.

**Кто читает:** `VMAP.cpp::loadGeoDamPal()` (ветка `#else`).

---

### `inDam.act`
**Назначение:** Палитра дамбы/воды (Dam layer) — 256 цветов RGB для индексов слоя `VxDBuf`.

**Формат:** Аналогично `inGeo.act` — ровно 768 байт, порядок **BGR**.

**Как формируется:** `saveGeoDamPal()`.

**Кто читает:** `VMAP.cpp::loadGeoDamPal()` — читается **всегда**, независимо от `tx3d`.

---

### `hardness.bin`
**Назначение:** Карта твёрдости грунта — определяет, насколько легко терраформер копает/сыплет в каждой клетке.

**Формат:** Бинарный, packed (4 клетки в 1 байте):
```
Размер: (H_SIZE/2) * (V_SIZE/2) байт
Каждый байт кодирует 4 клетки сетки GABuf (2×2 блока):
  биты [1:0]  → клетка (x+0, y+0)
  биты [3:2]  → клетка (x+1, y+0)
  биты [5:4]  → клетка (x+0, y+1)
  биты [7:6]  → клетка (x+1, y+1)
Значение 0..3 = GRIDAT_MASK_HARDNESS (0=мягкий, 3=твёрдый/некопаемый)
```

**Как формируется:** `saveHardness()` сохраняет из `GABuf`. В редакторе также может быть загружен из `hardness.tga` (монохромный TGA, устаревший путь `loadHardness2Grid()`).

**Кто читает:** `VMAP.cpp::loadHardness()` — вызывается из `fullLoad()` и `loadGameMap()`.

---

### `leveledSurfaceTexture.tga`
**Назначение:** Палитровая текстура (256 цветов) отображения **выровненной** (zeroplastic) поверхности. Определяет, каким цветом рисуется выровненная клетка в режиме 3D.

**Формат:** Стандартный TGA, **палитровый** (ColorMapType=1, CMapDepth=24, ImageType=1 или 9 — RLE). Размер ≤ размера карты, обе стороны — степень двойки. Пиксели содержат индекс в палитру SurPal (BGR).

**Как формируется:** Готовится художником в графическом редакторе. При загрузке палитра конвертируется из BGR в RGB.

**Кто читает:** `VMAP.cpp::loadLeveledTexture()` — вызывается из `fullLoad()`. Если файл отсутствует, используется `SurBuf` по умолчанию.

---

### `cache.tga`
**Назначение:** Кэш RGB-рендеринга карты (24-битный TGA). Предвычисленный вид карты «сверху», используемый для быстрого рендеринга и для мини-карты.

**Формат:** 24-битный uncompressed TGA, размер = `H_SIZE × V_SIZE`.

**Как формируется:** Создаётся в редакторе SurMap3 при рендеринге мира. Игра читает его при загрузке в `fullLoad()` — если файл не найден или формат некорректный, происходит мягкая ошибка.

**Кто читает:** `VMAP.cpp::fullLoad()` — `tgahead.load2RGBL(...)` загружает в `SupBuf`.

---

### `map.tga`
**Назначение:** Стратегическая мини-карта, отображаемая в интерфейсе (радар/карта в углу экрана и в меню загрузки).

**Формат:** TGA произвольного размера, читается как обычная текстура движком.

**Как формируется:** Готовится художником вручную (или генерируется из `cache.tga`).

**Кто читает:** `PerimeterShellUI.cpp:2896` — `terVisGeneric->CreateTexture(GetTargetName("map.tga"))`. Также используется в меню загрузки (`CShowMapWindow::setWorldID()` → `GetTargetName(worldID, "map.tga")`).

---

### `up.tga`
**Назначение:** Текстура «верхней» стороны карты для 3D-рендера (вид сверху в изометрии/перспективе). В отличие от `cache.tga`, может содержать текстурированный вид, а не только палитровый рендер.

**Формат:** TGA (обычно 24 или 32 бита).

**Как формируется:** Готовится в редакторе SurMap3 или вручную.

**Кто читает:** Код прямого обращения к `"up.tga"` через `GetTargetName` в исходниках не найден — вероятно, используется только в редакторе SurMap3 или загружается динамически через конфигурацию модели рендера (`.l3d`/`.m3d`).

#  Атрибуты клеток



В файле `output.vmp` хранится массив `AtrBuf[XS*YS]`, где каждый байт — это атрибуты одной клетки. Байт разбит на два независимых поля, которые хранятся в разных частях карты.

---

## 1. Атрибуты в `AtrBuf` (байт на пиксель)

Определения из `Source/Terra/terra.h`:

```cpp
#define At_LEVELED      (0x80)  // бит 7: поверхность выровнена (zeroplastic)
#define At_ZEROPLAST    (0xC0)  // биты 7–6: маска зеропласта
#define At_SOOT         (0x40)  // бит 6: гарь (повреждённая поверхность)
#define At_SHADOW       (0x20)  // бит 5: тень от объекта
```

### Разбор битов `AtrBuf`:

| Биты | Значение | Описание |
|---|---|---|
| **7–6** | `At_ZPMASK` (0xC0) | **Состояние зеропласта (zero plastic / level state)** |
| 7–6 = `00` | — | Обычная (невыровненная) поверхность |
| 7–6 = `01` | `At_SOOT` (0x40) | **Гарь** (soot) — поверхность повреждена, но ещё не выровнена |
| 7–6 = `10` | — | Выровненная поверхность, но **не** зеропласт |
| 7–6 = `11` | `At_LEVELED` (0x80) | **Выровненная поверхность + зеропласт** (zeroplastic) |

В комментариях к коду это описано так:

> «старшие биты: 10 — выровненная поверхность; 11 — зеропласт; 01 — гарь; 00 — просто поверхность»

| Бит 5 | `At_SHADOW` (0x20) | **Тень** — клетка находится под объектом (зданием, юнитом) |
| Биты 4–0 | — | **Резерв / не используются** (в играх не читаются) |

### Итого `AtrBuf` — 5 бит:

```
бит:  7   6   5   4  3  2  1  0
     [ZP][ZP][SH][.....резерв......]
```

---

## 2. Атрибуты в `GABuf` (графический буфер, сетка)

Кроме `AtrBuf` в `output.vmp` (в секции с изменёнными областями, сохраняемой при загрузке/сохранении игры) есть `GABuf` — сетка `[(V_SIZE>>kmGrid) × (H_SIZE>>kmGrid)]`, где каждый элемент — `unsigned short`.

Определения из `Source/Terra/VMAP.h`:

```cpp
#define GRIDAT_BUILDING         (0x1)      // бит 0: здесь стоит здание
#define GRIDAT_MASK_HARDNESS    (0x3)      // биты 0–1: твёрдость грунта
#define GRIDAT_LEVELED          (0x8)      // бит 3: гео-поверхность выровнена
#define GRIDAT_WATER            (0x10)     // бит 4: здесь вода/дамба
#define GRIDAT_MASK_UNUSED      (0x20)     // бит 5: зарезервировано
```

### Разбор битов `GABuf` (unsigned short, 16 бит):

| Биты | Константа | Описание |
|---|---|---|
| **0–1** | `GRIDAT_MASK_HARDNESS` (0x3) | **Твёрдость грунта** — 0 = мягкий (копаемый), 1 = средний, 2 = твёрдый, 3 = неприкасаемый (некопаемый) |
| 2 | — | Резерв |
| **3** | `GRIDAT_LEVELED` (0x8) | **Гео-слой выровнен** — аналог `At_LEVELED`, но для географической сетки |
| 4 | `GRIDAT_WATER` (0x10) | **Вода** — клетка затоплена / находится под дамбой |
| 5 | `GRIDAT_MASK_UNUSED` (0x20) | Зарезервировано, не используется в игре |
| **0** (альтернативно) | `GRIDAT_BUILDING` (0x1) | **Здание** — на клетке стоит или стояло здание (проверка `!= 0`) |

---

## 3. Сводная таблица всех атрибутов

| Источник | Байт/широкий тип | Биты | Константа | Что означает |
|---|---|---|---|---|
| `AtrBuf` | `unsigned char` | 7–6 | `At_ZPMASK` | Зеропласт: 00=обычная, 01=гарь, 10=выровнена, 11=зеропласт |
| `AtrBuf` | `unsigned char` | 5 | `At_SHADOW` | Клетка затенена объектом |
| `AtrBuf` | `unsigned char` | 4–0 | — | Резерв |
| `GABuf` | `unsigned short` | 0 | `GRIDAT_BUILDING` | Стоит здание |
| `GABuf` | `unsigned short` | 0–1 | `GRIDAT_MASK_HARDNESS` | Твёрдость грунта (0–3) |
| `GABuf` | `unsigned short` | 2 | — | Резерв |
| `GABuf` | `unsigned short` | 3 | `GRIDAT_LEVELED` | Гео-слой выровнен |
| `GABuf` | `unsigned short` | 4 | `GRIDAT_WATER` | Клетка с водой |
| `GABuf` | `unsigned short` | 5 | `GRIDAT_MASK_UNUSED` | Зарезервировано |
| `GABuf` | `unsigned short` | 6–15 | — | Резерв |

---

## 4. Как это используется в игре

- **`At_SOOT` (гарь)** — ставится, когда терраформер копает/сыплет на поверхность (`VMAP.cpp:586`). Определяет, что поверхность «повреждена» и выглядит иначе.
- **`At_SHADOW`** — ставится при рендеринге, когда клетка попадает в тень от здания или юнита.
- **`GRIDAT_MASK_HARDNESS`** — проверяется терраформерами перед копанием (`tools.h:491`), если твёрдость максимальна — копать нельзя.
- **`GRIDAT_BUILDING`** — проверяется при размещении новых зданий, чтобы не ставить поверх существующих.
- **`GRIDAT_WATER`** — определяет затопленные клетки, влияет на проходимость и рендеринг.


# Дамбы



**Дамба** (Dam layer / `VxDBuf`) — это второй слой рельефа поверх основного (geo-слоя `VxGBuf`). Если коротко:

---

## Суть

Карта имеет **два высотных буфера**:

| Буфер | Размер | Содержимое |
|---|---|---|
| **`VxGBuf`** | `XS × YS` байт | **Гео-слой** — основной рельеф (целая высота + 6 бит дроби) |
| **`VxDBuf`** | `XS × YS` байт | **Дамба** — второй слой, накладываемый сверху |

Дамба может **поднимать** или **опускать** высоту клетки поверх основного рельефа. Это позволяет создавать конструкции, которые невозможны одним гео-слоем: мосты, насыпи, подиумы, стены, воронки «в минус».

---

## Как это выглядит в игре

- **Насыпь/мост** — терраформер поднимает дамбу выше земли → создаётся плоская площадка на высоте.
- **Вода/озеро** — дамба заполняет впадину водой (вода видна через `inDam.act` палитру, а не `inGeo.act`).
- **Подиум для здания** — дамба приподнимает клетку, чтобы здание стояло на возвышении.
- **Колодец/воронка** — дамба опускается ниже земли, создавая углубление.

---

## Бинарное представление

В `output.vmp` дамба хранится как отдельный массив `VxDBuf[XS*YS]`, каждый байт — индекс поверхности в дамбовой палитре (`inDam.act`). При загрузке:

```cpp
// fullLoad() -> read VxDBuf -> convertPal2TableSurCol(DamPal, Damming)
```

Палитра `inDam.act` содержит 256 цветов BGR, определяющих визуальный вид воды/дамбы (голубой, синий, тёмно-синий для разных глубин).

---

## Взаимодействие с игрой

- **Твердость грунта** (`GRIDAT_MASK_HARDNESS` в `GABuf`) влияет на то, можно ли копать/сыпать дамбу.
- **`GRIDAT_WATER`** (бит 4 в `GABuf`) — отмечает клетки, где дамба превышает определённый порог (вода).
- Здания **не могут** ставиться на воду (проверка `GRIDAT_WATER`).
- Юниты **не могут** ходить по воде (проверка проходимости).
- Терраформеры могут **копать** (`SDig`) и **сыпать** (`SPutAlt`) дамбу, изменяя высоту.

---

## Визуализация

При рендеринге (функция `RenderStr` и т.д.) движок:
1. Берёт высоту из `VxGBuf` (гео) + `VxDBuf` (дамба).
2. По индексу из `SurBuf` определяет тип поверхности.
3. Если дамба = вода — использует палитру `DamPal` (`inDam.act`), иначе — `GeoPal` (`inGeo.act`).
4. Накладывает освещение и тень (`At_SHADOW` в `AtrBuf`).

---

## В SurMap3

В редакторе SurMap3 переключение между слоями:
- **Geo layer** (`VxGBuf`) — основной рельеф (горы, равнины).
- **Dam layer** (`VxDBuf`) — дамба (воды, насыпи).

Редактор позволяет рисовать их независимо, но при загрузке в игру они суммируются для определения итоговой высоты клетки.


# Рендеринг воды




Вот как устроена текстура воды (дамбы) в Perimeter.

---

## Как определяется цвет клетки

Цвет каждой клетки на экране вычисляется по формуле:

```cpp
// VMAP.cpp:2754, 2768
col32 = Sur2Col32[ SurBuf[offb] ][ RnrBuf[offb] ];
//                 ^^^^^^^^^^^^^   ^^^^^^^^^^^^
//                 тип поверхности  освещение (рельефное затенение)
```

### 1. `SurBuf[offb]` — индекс типа поверхности (0–255)

Это **индекс в палитре** (BGR, 256 цветов), который хранится в файле `output.vmp`. Для воды (дамбы) используется палитра **`DamPal`** из файла **`inDam.act`**. При этом DamPal занимает старшие 128 ячеек таблицы `Sur2Col32` (смещение 128):

```cpp
// VMAP.cpp:1329-1330
case Damming:
    SurBufOffset = 128;  // индексы 128..255 → DamPal (вода)
    break;
```

### 2. `RnrBuf[offb]` — освещение (0–127)

Это карта рельефного затенения, вычисляемая из перепада высот между соседними клетками:

```cpp
// VMAP.cpp:1735 (SurMap3 code, но логика та же)
short rnr = SLightTable[SLT_05SIZE + VxG[x] - VxG[x+1]];
```

Чем больше перепад высот — тем светлее/темнее клетка.

### 3. Палитра `DamPal` (inDam.act)

256 цветов BGR. При рендеринге из палитры строится таблица `Sur2Col32[тип_поверхности][уровень_освещения]` — 256 типов × 128 уровней = 32768 цветов, предвычисленных при загрузке мира.

```cpp
// VMAP.cpp:1346-1372
for (int i = 0; i < MAX_SURFACE_TYPE; i++) {       // 256 типов
    R = palBuf[i*3+0]; G = palBuf[i*3+1]; B = palBuf[i*3+2];
    for (int j = 0; j < MAX_SURFACE_LIGHTING; j++) { // 128 уровней освещения
        // Вычисляется затемнённый/осветлённый цвет
        cb = B * (Lum0 + dLum * j);
        cg = G * (Lum0 + dLum * j);
        cr = R * (Lum0 + dLum * j);
        Sur2Col32[i][j + SurBufOffset] = col32;
    }
}
```

---

## Зависит ли цвет воды от уровня (высоты дамбы)?

**Прямого автоматического пересчёта** типа поверхности из высоты дамбы **в рантайме игры нет**. Индекс `SurBuf` фиксируется при создании карты в редакторе и не меняется при загрузке.

Однако есть два механизма, дающих **косвенную** зависимость:

### 1. Рельефное затенение (`RnrBuf`)

Цвет воды затемняется/осветляется в зависимости от перепада высот соседних клеток. Это создаёт эффект «объёма» воды, но **не меняет её оттенок** (индекс палитры тот же).

### 2. Фильтр по высоте при назначении текстур в редакторе

В редакторе SurMap3 (`putTgaComplete2AllMap`, строки 2627–2713) можно накладывать текстуру `allDamMap.tga` с **фильтром по высоте**:

```cpp
// VMAP.cpp:2685-2687
int h = SGetAlt(off);
if (h < FilterMinHeight || h > FilterMaxHeight) continue;
SurBuf[off] = sur;  // назначаем индекс только если высота в диапазоне
```

Это значит:
- На высоте 0–50 можно назначить **светлую воду** (мелководье, индекс A)
- На высоте 50–100 — **среднюю воду** (индекс B)
- На высоте 100–150 — **тёмную воду** (глубина, индекс C)

Фильтр `FilterMinHeight`/`FilterMaxHeight` позволяет рисовать несколько слоёв текстур дамбы, каждый в своём высотном диапазоне. Результат — в `SurBuf` записывается **разный индекс для разной высоты**, но сам расчёт происходит **в редакторе**, а не в игре.

### 3. `veryLightDam` — автоматический выбор самой светлой воды

При загрузке палитры дамбы движок определяет самый светлый цвет:

```cpp
// VMAP.cpp:1350-1355
if (SurfaceMode == Damming) {
    float lighting = 0.3*R + 0.59*G + 0.11*B;
    if (max_lighting <= lighting) {
        max_lighting = lighting;
        veryLightDam = i;  // индекс самого светлого цвета воды
    }
}
```

`veryLightDam` используется при отображении самых мелких участков воды (границы, блики).

---

## Итоговая схема рендеринга воды

```
output.vmp:  SurBuf[x][y] = индекс типа поверхности (0-255)
             VxDBuf[x][y] = высота дамбы (0-255)
             VxGBuf[x][y] = высота гео-слоя (0-255)

inDam.act:   DamPal[0..255] = палитра 256 цветов BGR

При загрузке:
  Sur2Col32[SurBuf][RnrBuf] ← DamPal[SurBuf] × затемнение(RnrBuf)

RnrBuf = f(перепад высот VxG[x] - VxG[x+1])
```

**Цвет воды = палитра[индекс_в_SurBuf] × освещение[перепад_высот]**

Высота дамбы (`VxDBuf`) влияет на **геометрию** (высота на экране) и **рельефное затенение** (`RnrBuf`), но не на выбор индекса палитры напрямую. Разная глубина воды кодируется **разными индексами в `SurBuf`**, которые назначаются вручную в редакторе (в том числе через высотный фильтр).


# geoLattice.bin



Да, используется. Вот полный путь от определения до применения.

## 1. Компиляция

`geoLattice.bin` читается внутри блока `#ifdef _TX3D_LIBRARY_`:

```cpp
// Source/Terra/f3d.cpp, строки 197–206
#ifdef _TX3D_LIBRARY_
    std::ifstream ifsLattice(GetTargetName("geoLattice.bin"), std::ios::in | std::ios::binary);
    if (ifsLattice) {
        ifsLattice.read((char*)indexLattice, 65536);
    }
    // ...
#endif
```

Макрос `_TX3D_LIBRARY_` **определён в корневом `CMakeLists.txt`** (строка 374):
```cmake
add_definitions(-D_TX3D_LIBRARY_)
```
То есть этот код **компилируется в финальную сборку игры** (не только в редактор SurMap).

## 2. Где вызывается

```
f3d.loadVariable()  // VMAP.cpp:915 — вызывается из fullLoad() при загрузке мира
  └─> ifsLattice.read(indexLattice, 65536)  // загружает geoLattice.bin
      └─> indexedTexture = new tx3d::IndexedTexture3D(..., indexLattice)  // f3d.cpp:181
          └─> indexedTexture->getColorIndex(calcPoint)  // s_f3d::calc()
              └─> indexLattice[index & 65535]  // IndexedTexture3D.hpp:49
```

## 3. Как работает

Каждая клетка карты имеет 3D-координату `(x, y, z)`, где `z` — высота рельефа. `IndexedTexture3D::getColorIndex` вычисляет индекс так:

```cpp
// IndexedTexture3D.hpp:42–50
int index = floor(clr.x * 31.0) * 2048
          + floor(clr.y * 63.0) * 32
          + floor(clr.z * 31.0);
return indexLattice[index & 65535];
```

`geoLattice.bin` — это **LUT (lookup table) ровно 65536 байт** (`64 КБ`). Каждый байт содержит индекс типа поверхности (0–255). Функция `fillIndexLattice` из библиотеки tx3d заполняет эту таблицу методом k-ближайших соседей из `geoPal.xml` — то есть для каждой комбинации RGB-цвета вычисляется ближайший тип террейна и сохраняется его индекс.

В `s_f3d::calc()` эта таблица используется для вычисления `SurBuf` — индекса поверхности клетки:

```cpp
// f3d.cpp:137
vMap.SurBuf[of] = calc(j, i, v);
// где calc() -> indexedTexture->getColorIndex(calcPoint) -> indexLattice[ packed_color ]
```

## 4. Регистрация как ресурс игры

Файл также указан в сканировании контента (`Source/Game/GameContent.cpp`, строка 159):

```cpp
"resource/worlds/*/geolattice.bin",
```

То есть движок ожидает найти его в каждой папке мира.

## 5. Что если файла нет

Если `geoLattice.bin` не найден, `ifsLattice` остаётся открытым, но `read()` не вызывается. Массив `indexLattice[65536]` остаётся нулевым (конструктор `s_f3d` не инициализирует его явно, но C-массив внутри `s_f3d` при создании `f3d` глобально будет обнулён). В этом случае `getColorIndex` вернёт `0` для всех клеток — весь мир получит поверхность с индексом 0.

# Типы повехностей




**Тип поверхности** — это просто число **0–255**, индекс в палитре `SurBuf`. Нет жёстко заданных имён вроде «трава» или «вода» — всё определяется **палитрой** и **цветом**.

---

## 1. Как это работает

```
SurBuf[x][y] = индекс 0–255
               │
               ▼
GeoPal[256] = 256 цветов BGR (inGeo.act)
               │
               ▼
Sur2Col32[256][128] = предвычисленная таблица:
                      Sur2Col32[тип_поверхности][освещение]
```

Каждый индекс — это просто номер строки в палитре. Цвет этой строки = то, что видит игрок.

---

## 2. Что делает этот индекс (кроме цвета)

Индекс поверхности влияет на три вещи:

### А. Фильтрация при рендеринге
```cpp
// VMAP.cpp:2246
if (!FilterGeoTerrain[GetTer(offset)]) return;
```
`FilterGeoTerrain[256]` — массив из 256 булевых значений. Если `FilterGeoTerrain[индекс] == 0`, эта клетка **не рисуется**. Это используется для:
- Скрытия «невидимых» слоёв в редакторе SurMap
- Выделения только определённых типов поверхности (например, только дамбы)

### Б. Материал поверхности (отражение света)
```cpp
// LAND.cpp:1068-1069
for(i=0; i<MAX_GEO_SURFACE_TYPE; i++)
    geoType2Mater[i] = (0<<SHIFT_4TYPE_MATERIALS)|(0&FLAG_SPECULAR_MATERIAL);

// LAND.cpp:1071-1072 (комментарий — пример с водой)
// for(i=0; i<MAX_DAM_SURFACE_TYPE; i++)
//     damType2Mater[i] = (0<<SHIFT_4TYPE_MATERIALS)|(1&FLAG_SPECULAR_MATERIAL);
// damType2Mater[1] = (0<<SHIFT_4TYPE_MATERIALS)|(1&FLAG_SPECULAR_MATERIAL);
```

Каждому типу поверхности назначается **материал**:
- `geoType2Mater[тип] & FLAG_SPECULAR_MATERIAL` — глянцевая (бликует) или матовая
- `SHIFT_4TYPE_MATERIALS` — выбор материала из `MaxAmountMaterials=2`:
  - Материал 0: `kDifSM=0.7`, `kSpecSM=0.5`, `nSpecSM=15`
  - Материал 1: `kDifSM=0.5`, `kSpecSM=0.5`, `nSpecSM=5`

Вода (индексы дамбы) обычно получает **глянцевый материал** — поэтому она бликует.

### В. Выровненная поверхность (зеропласт)
```cpp
// VMAP.cpp:2749-2768
if (at & At_ZEROPLASTEMPTY)
    col = SurZPE2Col[RnrBuf][SurBuf];
else if (at & At_ZEROPLAST)
    col = SurZP2Col[RnrBuf][SurBuf];
else
    col = Sur2Col[SurBuf][RnrBuf];
```

Для выровненных участков используется **другая палитра смешивания** (`SurZP2Col`), где цвет поверхности смешивается с цветом `colZeroPlast`. Это создаёт эффект «выровненной земли» (ровная бетонная/асфальтированная площадка).

---

## 3. Какие типы существуют по умолчанию

### Geo-тип (0–127): `inGeo.act`
Это **земля/суша**. Индексы назначаются художником. Обычно:
- **0** — `DEFAULT_TERRAIN` (по умолчанию 1, пустой/нейтральный)
- **1–10** — основные типы: трава, песок, скала, болото, снег, пустыня и т.д.
- **11–127** — дополнительные вариации, смешанные типы, переходы

### Dam-тип (128–255): `inDam.act`
Это **вода/дамба**. Индексы тоже назначаются художником. Обычно:
- **128–135** — мелководье (светло-голубое)
- **136–145** — средняя глубина (голубое)
- **146–155** — глубокая вода (тёмно-синее)
- Остальные — особые эффекты, грязь под водой, береговые линии

---

## 4. Как определяется тип клетки

```cpp
// f3d.cpp:390-412 (закомментированная функция GetGeoType)
unsigned char vrtMap::GetGeoType(int offset, int h) {
    int j = offset & clip_mask_x;  // x
    int i = offset >> H_SIZE_POWER; // y
    int of = vMap.offsetBuf(j, i);
    
    // tx3d вычисляет цвет на основе (x, y, высота)
    // и возвращает индекс из geoLattice.bin
    // который затем используется как тип поверхности
    return indexLattice[packed_color];
}
```

При генерации мира `tx3d::IndexedTexture3D::fillIndexLattice` сопоставляет **цвет 3D-текстуры** с **типом поверхности**. Результат — для каждой координаты `(x, y, высота)` известен индекс типа.

---

## 5. Пример: как выглядит тип в игре

| Индекс SurBuf | Цвет в палитре | Что видит игрок | Материал |
|---|---|---|---|
| 0 | серый | пусто / земля | матовый |
| 1 | зелёный | трава | матовый |
| 2 | коричневый | песок | матовый |
| 3 | тёмно-серый | скала | матовый |
| 4 | голубой | вода | **глянцевый** |
| 5 | жёлтый | пустыня | матовый |

Но это **абсолютно произвольно** — художник в SurMap3 рисует палитру так, как хочет.

## 6. Итог

**«Тип поверхности» — это индекс 0–255 в палитре `SurBuf`.**

- Цвет этого индекса в `inGeo.act` / `inDam.act` определяет **визуальный вид**
- Значение `FilterGeoTerrain[индекс]` определяет, **видна ли клетка**
- Значение `geoType2Mater[индекс]` определяет, **бликует ли поверхность**
- Значение `at & At_ZEROPLAST` определяет, **выровнена ли поверхность** (зеропласт)

Нет встроенных имён типов — всё определяется палитрой, которую задаёт художник в редакторе.

## Кто читает `geoTx.xml`

Единственное место в коде игры — `s_f3d::loadVariable()` (`Source/Terra/f3d.cpp:177–207`):

```cpp
void s_f3d::loadVariable(void)
{
#ifdef _TX3D_LIBRARY_
    if (!indexedTexture) {
        indexedTexture = new tx3d::IndexedTexture3D(
            tx3d::Texture3DFactory::createTexture3D("<texture type='Primitive'>...</texture>"), // дефолт
            indexLattice);
    }

    std::ifstream ifsTx(GetTargetName("geoTx.xml"));      // <-- вот здесь
    char szBuffer[1024 * 10];
    ifsTx.get(szBuffer, 1024 * 10, '\0');

    tx3d::Texture3D* pTx = tx3d::Texture3DFactory::createTexture3D(string(szBuffer));
    if (!pTx) {
        pTx = tx3d::Texture3DFactory::createTexture3D("<texture type='Clear'/>"); // fallback
    }
    indexedTexture->setTexture(pTx);

    std::ifstream ifsLattice(GetTargetName("geoLattice.bin"), ...);  // тут же читается lattice
    ...
#endif
    // затем читаются ScalingXYZ и Function из world.ini
}
```

Вызов происходит при загрузке мира: `vrtMap::fullLoad()` → `f3d.loadVariable()` (`VMAP.cpp:915`). Максимальный размер файла, который читается — **10 КБ** (буфер `szBuffer[1024*10]`), до первого `\0`.

## Что это такое

`geoTx.xml` — это **описание процедурной 3D-текстуры** для библиотеки tx3d. Это «первоисточник», из которого генерируются цвета, а `geoLattice.bin` — это **квантованная таблица**, построенная по результатам её работы (связка: `geoTx.xml` → текстура → `fillIndexLattice` по цветовой таблице → `geoLattice.bin` → индексы `SurBuf`).

Цепочка использования в рантайме:

```
geoTx.xml ──> Texture3DFactory::createTexture3D() ──> tx3d::Texture3D (процедурная)
                                                        │
geoLattice.bin ──> indexLattice[65536]                  │
                    │                                   │
                    ▼                                   ▼
        IndexedTexture3D::getColorIndex(x, y, z/32) = indexLattice[hash(texture->getColor(...))]
                    │
                    ▼
        f3d.calc() ──> vMap.recalcWorld() ──> SurBuf[x][y] (тип поверхности)
```

Обратите внимание на `recalcWorld()` (`f3d.cpp:126–141`): для каждой клетки **без дамбы** тип поверхности `SurBuf` вычисляется заново через `calc(j, i, высота)` — то есть `geoTx.xml` + `geoLattice.bin` реально влияют на то, как выглядит суша после загрузки карты (`VMAP.cpp:1022`, если не `flag_FastLoad`).

## Формат файла

XML с корневым тегом `<texture type='...'>`. Тип выбирается фабрик `Texture3DFactory::createTexture3D()` (`Source/tx3d/Texture3DFactory.cpp`). Поддерживаемые типы (`TYPE_NAME` по всей библиотеке tx3d):

| type | Класс | Смысл |
|---|---|---|
| `Primitive` | Primitive3D | FBM-шум (Perlin) + цветокорректор + интерполятор |
| `Clear` | Clear3D | Пустая/прозрачная текстура (fallback при ошибке) |
| `Laying` | Laying3D | «Пласты/слои» — стратифицированная текстура |
| `Compound` | Compound3D | Композиция вложенных текстур |
| `Perturbed` | PerTexture3D | Возмущение одной текстуры другой |
| `FlatModelX/Y/Z` | FlatModel*Texture3D | Плоская 2D-модель по оси X/Y/Z |
| `Model` | ModelTexture3D | 3D-модель цвета из набора TGA (`color0.tga`…`color15.tga`, сетка 17³) |

Канонический пример `Primitive` (из встроенного дефолта в коде и шаблонов `Legacy/GeoTool/res/Templates/*.xml`):

```xml
<texture type='Primitive'>
    <persistence value='0.500000'/>       <!-- амплитуда октав шума -->
    <octaveCount value='4'/>              <!-- число октав Perlin-шума -->
    <shift value='0.0,0.0,0.0'/>          <!-- сдвиг координат -->
    <scale value='0.04,0.04,0.04'/>       <!-- масштаб частоты -->
    <colorizer type='Cloud'>              <!-- Cloud, MarbleChaosX, Sand, Wood, Spots... -->
        <bgColor value='0.45,0.75,1.0'/>  <!-- фоновый цвет RGB 0..1 -->
        <fgColor value='0.24,0.0,0.24'/>  <!-- цвет узора -->
    </colorizer>
    <interpolator type='Cubic'/>          <!-- Cubic, Cosine, BackCubic, SphericSimplex... -->
</texture>
```

Типы цветокорректоров (из `tx3d/Clouds.cpp`, `Marbles.cpp`, `Sands.cpp`, `Woods.cpp`, `Spots.cpp`): `Cloud`, `CloudAbs`, `CloudEmboss`, `CloudSin`, `MarbleSolidX/Y`, `MarbleRareX/Y`, `MarbleChaos`, `MarbleChaosX/Y`, `MarbleLeopard`, `Sand`, `SandSmooth`, `Wood`, `WoodSin`, `WoodCos`, `Spots`, и др.

В репозитории есть готовые шаблоны таких XML: **`Legacy/GeoTool/res/Templates/`** (Cloud.xml, MarbleChaos.xml, Sand.xml, Wood.xml, Icefall0/1.xml, AtlasMountains.xml и т.д.) — это заготовки из старого редактора GeoTool, по формату полностью совместимые с тем, что парсит `Texture3DFactory`.

Координата, по которой вычисляется цвет: `calcPoint.x = x; calcPoint.y = y; calcPoint.z = z * 0.03125f` (высота/32) — т.е. текстура «протягивается» по высотам.

## Как формировать

1. Создать XML по шаблону из `Legacy/GeoTool/res/Templates/` (или взять встроенный дефолт из `f3d.cpp:182`), подобрав `scale/persistence/octaveCount/colorizer` под нужный вид суши.
2. В редакторе (GeoTool/SurMap) на основе этой текстуры строится цветовая таблица (`fillColorTable`) и по ней заполняется `geoLattice.bin` (`fillIndexLattice`/`fillIndexLatticeHSB`) — привязка цвета к индексу палитры `geoPal.xml`.
3. Положить `geoTx.xml` в папку мира рядом с `geoLattice.bin` и `geoPal.xml`.

## Что если файла нет

`ifstream` откроется пустым, `createTexture3D("")` вернёт `0` (тип не распознан) → сработает fallback `<texture type='Clear'/>`. Тогда цвет от текстуры будет постоянным, и `getColorIndex` вернёт один и тот же индекс для всех клеток (какой — зависит от `geoLattice.bin`). Ошибки вылета не будет.

Также файл числится в манифесте ресурсов: `Source/Game/GameContent.cpp:157` — `"resource/worlds/*/geotx.xml"`, а рядом (`:111–115`) сканируется `resource/geotx/**` — общие TGA-модели цвета (`color*.tga`) для типа `Model`/`FlatModel*` (см. `ModelTexture3D.cpp:33–58`, который грузит `color0.tga…color15.tga` как 17³-ную LUT).
