# Контекст: нетривиальные находки (редактор карт)

Заметки о неочевидном поведении кода игры/Terra, важные для редактора.
Связанные архитектурные решения — в `docs/architecture.md`.

## Terra

### `vrtMap::prepare()` можно вызвать только один раз за процесс

`vrtMap::prepare()` (`Source/Terra/VMAP.cpp:484`) вызывает `landPrepare()`
(`Source/Terra/LAND.cpp:64`), которая:

- **накапливает** глобальную таблицу `maxRad[MAX_RADIUS_CIRCLEARR+1]` (не
  обнуляется перед подсчётом), и
- **течёт**: аллоцирует `static_xheap`/`static_yheap`, но не освобождает
  предыдущие (освобождает только `landRelease()`, которую `prepare` не зовёт).

Итог: второй вызов `prepare()` в том же процессе считает `max` по удвоенным
`maxRad` и переполняет заново выделенные heap-массивы `xheap/yheap` →
повреждение памяти/краш (0xC0000005). Первый вызов безопасен.

**Что делает редактор.** `EditorSession::refreshWorldTable()` вызывает
`vMap.prepare("RESOURCE/Worlds")` один раз, а дальше сам перестраивает
`vMap.wTable` (та же переборка каталогов `RESOURCE/Worlds`, что и внутри
`prepare`, но без `landPrepare`).

**Почему нельзя полагаться на собственный флаг.** Другие вызовы (игра, тесты)
могут дёрнуть `vMap.prepare()` напрямую, минуя редактор. Поэтому «уже
подготовлено» определяется по состоянию самой Terra: `landPrepare()` оставляет
`xRad[0] != nullptr` (глобальные `xRad/yRad/maxRad` объявлены в
`Source/Terra/tools.h:12-14`). Хелпер `terraLandPrepared()` проверяет `xRad[0]`.

**Побочный эффект.** `vrtMap::~vrtMap` и `EditorSession::unloadWorld()`
намеренно **не** вызывают `landRelease()` — иначе радиусные таблицы пропадут и
понадобится повторный `prepare()`, который крашится (см. выше).

### `worldFree()` — не полная выгрузка мира

`vrtMap::worldFree()` (`Source/Terra/worldGen.cpp:485`) освобождает только
сеточные карты (`r_net_map` и т.п.) и обнуляет `r_net_map`. Буферы
`VxGBuf/VxDBuf/SurBuf/AtrBuf/RnrBuf/SupBuf/GVBuf/GABuf` остаются.

Полная уборка — в `vrtMap::~vrtMap` (`Source/Terra/VMAP.cpp:247`):
`delLeveledTexture()` → `releaseMem4Buf()` → `wTable.clear()` →
`landRelease()` → `worldFree()`. Порядок важен: `delLeveledTexture()` должен
идти раньше, чем `releaseMem4Buf()` (комментарий в коде: «Необходимо вызывать
до удаления VxDBuf!»), иначе `LvdTex` может совпадать с `SurBuf`.

`EditorSession::unloadWorld()` повторяет эту последовательность, кроме
`landRelease()`.

### `save3Buf()` уже включает палитры и `[3DF]`

`vrtMap::save3Buf()` (`Source/Terra/VMAP.cpp:1514`) вызывает `save3BufOnly()`
(пишет `output.vmp` в формате S2T0), затем `saveGeoDamPal()`
(`inGeo.act`/`inDam.act`) и `f3d.saveVariable()` (`[3DF Parameters]` в
`world.ini`). Редактору достаточно `save3Buf()` — отдельные вызовы не нужны.

### Запись Undo в Terra доступна только под `_SURMAP_`

`vrtMap::UndoDispatcher_PutPreChangedArea()` (`Source/Terra/undoDispatcher.cpp:6`)
целиком спрятан под `#ifdef _SURMAP_` — в сборке игры (`_PERIMETER_`) и
редактора это заглушка: в `vrtMap::preCAs` никогда ничего не попадает, а
`UndoDispatcher_Undo/Redo/IsUndoExist/IsRedoExist` всегда «пусты». Валяемый в
плане (§3.6) вариант «Undo/Redo через UndoDispatcher Terra» напрямую работать
не может, а править Terra (включать его под `_PERIMETER_`) нельзя — тело
зависит от toroidal-семантики и тонет в памяти/поведении игры.

Решение: `EditorSession` хранит собственную историю снимков
(`UndoAreaSnapshot`, swap-семантика 1:1 как в Terra: снимок хранит состояние
буферов ДО правки; undo/redo обменивают его с буферами и отмечают область
через `regRender`, т.е. во вьюпорт изменения попадают через обычную
dirty-rect-конвейерку). Инструменты (T3 и позже) обязаны вызывать
`EditorSession::recordUndoArea(x,y,w,h)` ПЕРЕД правкой
`VxGBuf/VxDBuf/AtrBuf/SurBuf`. Позиция последнего сохранения запоминается
в стеке — по ней `undo/redo` пересчитывают флаг modified (правка-отмена
после сохранения снова делает мир «чистым»).

### `cache.tga` обязателен при `fullLoad()`

`fullLoad()` `xassert`-ит на `cache.tga` (`Source/Terra/VMAP.cpp:935-941`).
Файл не поставляется с игрой, поэтому редактор генерирует его на каждом
сохранении (24-бит, `H_SIZE×V_SIZE`). Тест `WorldRoundTripTests` на время
round-trip делает фиктивную чёрную `cache.tga`, если её нет.

### Ссылки на общие ресурсы из XML мира

`geoTx.xml` мира ссылается на общие текстуры вида
`Resource\GeoTx\Stone_2.tga`. Это **не** файлы внутри папки мира, а общий
ресурс `RESOURCE/GeoTx`. Поэтому мир нельзя загрузить из content-root, в
котором есть только папка мира — нужен ещё `RESOURCE/GeoTx` (и `Perimeter.ini`
для `[TD] Color ZeroLayer`, читаемого `analyzeINI`). `SaveWorldTests` строит
такой изолированный content-root, чтобы не трогать папку игры.

### `wTable[].key` — это относительный путь, а не имя папки

В `get_content_entries_directory` поле `key` записи — нижнерегистровый
относительный путь (`resource\worlds\compass`), а имя папки — это
`path_content.filename()` (`compass`). При построении путей к файлам мира
(`GetTargetName` = `wTable[n].dir` + имя файла) нужен именно полный ключ;
при создании каталогов по имени мира — имя папки, не ключ.

### Палитры цвета: `RnrBuf` и общая индексация `SurBuf`

`RnrBuf[off]` (`LAND.cpp:1461-1462`): бит 7 = «здесь дамба» (ставится тогда,
когда `VxDBuf != 0`), биты 0..6 — освещение (`свет >> 1`, всегда ≤127).
`Sur2Col32[Sur][Rnr]` (`VMAP.h:321`) — вторая размерность загоняется дважды:
`convertPal2TableSurCol(GeoPal, Geologic)` заполняет строки 0..127
(`GeoPal`), `convertPal2TableSurCol(DamPal, Damming)` — строки 128..255
(`DamPal`), при этом **первый** индекс (индекс материала в `SurBuf`) общий
для обеих палитр. `PutAltDam()` при установке дамбы **не** переписывает
`SurBuf` (`SetTer` закомментирован, `VMAP.h:864`) — индекс материала
сохраняется. Отсюда: цвет дамбы = `DamPal[Sur] × освещение`, а «гео под
дамбой» восстанавливается точно как `Sur2Col32[Sur][Rnr & 0x7F]` — этим
пользуется Geo-фильтр `ViewportRenderer` (без аппроксимаций через
`GetGeoType`). Ветки `At_LEVELED` ведут себя так же: `Tex2Col32`/`SurZP2Col32`
тоже строятся двумя проходами и берут тот же `Rnr`.

`getColor32` в release-сборке не имеет debug-тинтов: `flag_ShowHardness` /
`flag_ShowDbgInfo` инициализируются нулём в конструкторе (`VMAP.cpp:220-221`).

### Конвейер грязных прямоугольников `regRender → renderQuant`

- `regRender()` (`LAND.cpp:892`) `XCYCL`-ит координаты и, если прямоугольник
  «заворачивается» через границу, дробит его на 2-4 бокса; каждый бокс
  уходит в `renderBox`, который пушит **один и тот же** прямоугольник сразу в
  `vMap.renderAreas` и `vMap.changedAreas`, а для вырожденного запроса
  (`x1==x2` или `y1==y2`) расширяет бокс до **всей строки/колонки**
  (`LAND.cpp:693-696`).
- `sRectS::dx/dy` — **включительные** экстенты (`x1() = x + dx`);
  `renderQuant()` перерисовывает строки `y..y+dx` включительно.
- `renderQuant()` (`LAND.cpp:760`) ранний выход при пустом `renderAreas`,
  в конце делает `renderAreas.clear()` (`LAND.cpp:884`), а `changedAreas`
  **не** трогает — их чистит потребитель: в игре это `terUniverse::quant()`
  (`Universe.cpp:250`), в редакторе — `ViewportRenderer::update()`
  (иначе список растёт бесконечно, а растровый кэш отстаёт).
- `renderBox` дополнительно выставляет `changedT[y]` — ветке `PERIMETER`
  это ни на что не влияет (`changedT` читают другие пути рендера).

### Инкрементальные тени `RenderStr` выходят ЗА пределы грязного прямоугольника

`RenderStr` (`LAND.cpp:1120`) посчитывает «потолок тени» `h_s` со скана
С НАРУЖИ (PREC-скан справа читает уже флажкованные `At_SHADOW`-клетки,
`LAND.cpp:1150-1167`), затем рисует строку идя на запад и **продолжает
рендер западнее запрошенного бокса, пока `prevShadow` не погаснет**
(`j--; while (j >= 0 || prevShadow != 0)`, `LAND.cpp:1467-1469`). Затенённые
дополнительные клетки получают `At_SHADOW` (== `At_SHADOWV`, 0x20) и тёмный
`RnrBuf`, но в `changedAreas` НЕ попадают. Следствия для редактора:

- при ПОДЪЁМЕ рельефа новый след тени западнее штампа рендерится сам, но
  кэш 2D-вьюпорта/мип-пирамида его не перекрашивают (надо бы);
- при ОПУСКАНИИ (кисть «lower», undo, redo) клетки, потемневшие раньше,
  остаются с устаревшим тёмным `RnrBuf` и флагом `At_SHADOW` — «чёрные
  полосы» рядом с отредактированным местом в обоих 3D-видах (оба читают
  `RnrBuf` напрямую; 2D-вид сверху не страдает — он и не заходил в след).

Решение редактора: все тикеты грязного рендера идут через
`EditorSession::regRenderWithShadowTrail()` — перед `regRender` она
проходит по `At_SHADOW`-следу западнее бокса (поклеточно, до первой
нефлажкованной клетки) и включает след в бокс: устаревшие клетки
пересчитываются и флаги снимаются (тест 65 `ShadowTrailTests`).

### `RnrBuf` не вычисляется при загрузке мира

`fullLoad()` распределяет `RnrBuf`, но цикл `RenderStr` внутри него
**закомментирован** (`VMAP.cpp:924-928`) — буфер приходит в мусорном
состоянии. Игра после загрузки вызывает `vMap.WorldRender()`
(`terUniverse::universalLoad`, `Universe.cpp:1052`), который пересчитывает
`RnrBuf` и `At_SHADOW` по всем строкам. Редактор делает то же самое в
`EditorSession::loadWorld()` (п.5) — до этой правки любой `getColor32()`
(вьюпорт, генерация `cache.tga`) читал неинициализированное освещение.

## Наклонный 3D-вид (`viewV2D`, T2.3)

### `cameraAngleLean` — целый член, и у `viewV2D` есть сингулярность в `d0`

- `vrtMap::cameraAngleLean` — **целое** поле (`VMAP.h`);
  `sin(iangle((int)lean))` внутри viewV2D работает только с целыми. Поэтому
  слайдер наклона в UI оперирует градусами и кладёт в Terra округлённое
  целое.
- `viewV2D` перед сканированием дальностной «трубы» делит на
  `d0 = |tan(lean)| * focusC` (`VMAP.cpp:2041-2215`); если сканируемые
  радиусы попадают в `[0, d0)`, получается ноль/отрицательный шаг — мусорный
  кадр. Хелпер `stableLeanDeg(lean, focusC, yside)` отодвигает наклон так,
  чтобы `d0` была больше максимального радиуса скана. Важно: вход в градусах,
  а не радианах — при первой реализации случайно считали, что `atan` вернул
  градусы, и почти во всём диапазоне наклона кадр разваливался.
- Дефолтные значения камеры Terra: rot 0°, lean 140°, `cameraDZ` 100,
  `focusC` 600 (конструктор `vrtMap`, `VMAP.cpp:205-218`); рабочий диапазон
  наклона ≈ [100°, 170°].

### Базис поворота для панорамирования: вперёд = `(sin θ, −cos θ)`

Формулы сдвига внутри `viewV2D` (шаг скана по центру трубы) дают
компоненты `(sin θ, −cos θ)` по `turnAngleAroundZ`. Перпендикуляр
`(cos θ, sin θ)` — «вправо» камеры. Панорамирование правой кнопкой в
`ViewportWidget::panObliqueBy` сдвигает `viewX/viewY` по этому базису — так
компоновка кадра совпадает с интуицией «двигаю землю под камерой».

### Буфер `viewV2D` — RGB565, окно ≤ `MAX_XSIZE_VX_WINDOW`

- Пиксели `example_vx_window` — `ColorsHalfType` (uint16, RGB565) ⇒ обёртка
  в `QImage` нулевой копией возможна только как `Format_RGB16` (маски Qt
  совпадают с 565).
- Массивы примера окна статические и индексируются до
  `MAX_XSIZE_VX_WINDOW` (640) — `View3DRenderer` климпует размер окна
  `≤ 640×640`; компоненте окна передаются coords `vx_wnd` (левый/нижний
  угол, в клетках карты).

## Инфраструктура GUI

### `QPixmap::transformed(QTransform::scale(-1,1))` — падение CRT в Release

Первая версия иконки «поворот» делала зеркалирование через
`pixmap.transformed(QTransform().scale(-1, 1))` — на старте приложения
Release ловила fail-fast (SIGABRT, ErrH `Code: 64 Val: 22`) до входа в
движок. Причина кроется в цепочке pixmap/QTransform на нашем окружении Qt
6.12/MSVC2022 — надёжнее не трансформировать pixmap'ы иконок вовсе. Все
иконки рисуются QPainter'ом явно (дуги/линии), Bundle-иконки приложения
(QStyle painterIcon) не трогаем. Debug-сборка то же самое переживает тихо —
не ориентируемся на Debug при проверке стартовых падений.

## Файлы мира

### `output.vmp`: legacy-поля заголовка не перезаписываются

`sVmpHeader` содержит поля `NX/NY` (байты 12..19), которые runtime не читает.
`save3BufOnly()` их не заполняет, поэтому для байт-идентичного round-trip
редактор/тест копирует эти 8 байт из исходного файла
(`preserveVmpLegacyHeader` в `WorldRoundTripTests`). Игровая сборка сама миры
не пересохраняет, так что это забота редактора.

### Флаг `At_SHADOW` (0x20) — runtime-only

`fullLoad()` → `checkAndRecover()` очищает `At_SHADOW` во всех клетках
`AtrBuf`; тени пересчитывает рендер. Чтобы «загрузить и сохранить» давало
исходный файл байт-в-байт, тест возвращает эти биты из исходного `output.vmp`
(`restoreRuntimeShadowBits`). В `COMPASS`, например, 869 733 клетки имеют
`At_SHADOW`, «зашитый» в файле.

Нюанс: `EditorSession::loadWorld()` теперь вызывает `WorldRender()`
(см. `docs/architecture.md`, §2), поэтому мир, **сохранённый через
`EditorSession`**, пишет вычисленные тени, а не исходные биты файла. Байтовая
стабильность round-trip от этого не страдает: `WorldRoundTripTests` грузит мир
через сырой Terra-API (без `WorldRender`) и восстанавливает тени явно, а
`SaveWorldTests` `output.vmp` не байт-сравнивает.

### Некопаемость: семантика `hardness.bin` и `GABuf`

- Младшие 2 бита ячейки `GABuf` (`GRIDAT_MASK_HARDNESS`): **0 = некопаемо**
  (миссионный редактор пишет 0 именно для «сделать твёрдым»,
  `MissionEdit.cpp:641`; `tVoxSet` масштабирует копание как `h<<h`/24, т.е.
  при 0 копать нельзя), **3 = нормально копаемый грунт** (дефолт
  `initGrid()`). Значения 1/2 формат допускает, но в поставляемых данных
  их нет: декод `hardness.bin` всех миров даёт только 0 и 3 (COMPASS:
  28 692×0 / 233 452×3; HILLKAN: 226 879×0 / 35 265×3; INFORB-1 и VENECIDE —
  только 0).
- Файл: `uint16` ширина сетки (`GH_SIZE`), `uint16` высота, затем байты по
  4 ячейки (по 2 бита, младшие — первые).
- **Миссия vs битва.** Игра после загрузки мира делает
  `vMap.initGrid()` (вся некопаемость → 3) и `loadHardness()` **только** если
  из `.spg` пришло `manualData.loadHardness` (`Universe.cpp:949-952`); у
  многих `RESOURCE/Multiplayer/*`-карт это `false`, у `Missions/*` и
  `Worlds/*.spg` — `true`. Редакторский `fullLoad()` применяет `hardness.bin`
  безусловно, поэтому оверлей «некопаемость» показывает **истину мира-файла**;
  нюанс пропуска `loadHardness` из `.spg` относится к задачам T8/T9.
- `initGrid()` (`grid.cpp:45-90`) для каждого 4×4-блока ставит флаги:
  `GRIDAT_LEVELED` — только если все 16 клеток `At_LEVELED`,
  `GRIDAT_ZEROPLAST` — все 16 зеропласт, `GRIDAT_ZEROPLAST_IS_PRESENT` —
  хотя бы одна. Клетки с дамбой в счётчики не входят, но `At_ZEROPLAST`
  (0xC0) включает бит `At_LEVELED` (0x80), поэтому «полный зеропласт» всегда
  заодно и «выровнен» — отсюда приоритет зеропласт-тинта в оверлее.
- `At_NOTPURESURFACE == 0xC0 == At_ZPMASK` (`terra.h:46`): `SPutAltDam()`
  чистит флаги выровненности/зеропласта вместе с дробной частью высоты —
  при синтезе дамбы в тесте клетка гарантированно уходит из ветки
  `At_LEVELED`.

### В поставляемых мирах нет клеток `At_LEVELED` / `At_ZEROPLAST`

Прямой декод `AtrBuf` из `output.vmp` (COMPASS, HILLKAN, INFORB-1, ALPAIN,
KWILL, MAWN, XELA): верхние 2 бита не выставлены **ни у одной** клетки —
цветовые ветки `Tex2Col32`/`SurZP2Col32` в загруженных мирах не
встречаются, они оживаются только после правок (буши, зеропласт в миссиях).
Поэтому `ViewportRendererTests` выставляет эти флаги сам (форс-ячейки) и
проверяет ветки `getColor32` на реальных палитрах мира.

### Топология COMPASS: слои большими пятнами, гео — низкое

Декод `output.vmp` COMPASS (2048²): ~47% клеток с дамбой, причём области
дамбы/гео идут крупными блоками (опрос тайлами 128²: x 768..1023 /
y 256..511 — 100% гео, (256..384)² — 100% дамба). Целая часть высоты
**гео**-слоя лежит в 0..31 — «поверхность», которую видит игрок на картах со
многими дамбами, хранится в слое дамб. Полезно для выбора опорных клеток в
тестах рендера (боксы сканов захардкожены в `ViewportRendererTests` с
ссылкой на этот раздел).

### Круг кисти = усечённый sqrt, а не геометрический диск (T3.1)

`landPrepare()` (`LAND.cpp:75-84`) определяет «кольцо радиуса r» как все
смещения (i,j) с `(int)sqrt(i²+j²) == r` — **отбрасывание дробной части**,
а не округление и не сравнение с дискриминантом. Отсюда у «круга» Terra
углы заполнены: клетка (2,2) кольца 2, как и (2,0) — `sqrt(8)=2.83 → 2`.
Заполненный круг `influenceDZ` — объединение колец 0..r, т.е. та же
«толстая» фигура. Кисть editor'а (`BrushMasks`) считает край аналитически
той же формулой, чтобы каждая клетка штампа совпадала с таблицами
`maxRad/xRad/yRad` (кросс-чек в тесте 56). Связанный нюанс: при
`XMATH_USE_GAMEMATH` `xm::sqrt` → `gm_sqrt` — это fdlibm-`e_sqrt`, т.е.
правильно-округлённый IEEE-sqrt, тот же результат, что `std::sqrt(double)`;
беспорядочных расхождений в `(int)`-усечении быть не может.

### Почему высотная кисть идёт через `tVoxSet` поклеточно (T3.1)

`individualToolzer::influenceDZ()` умеет только `xRad`-круги и внутри сам
делает `recalcArea2Grid`+`regRender` на каждый вызов. Произвольные формы
(квадраты, кольца, линии, позже картинки T3.5) в его API не влезают, поэтому
`BrushTool` зовёт публичный `tVoxSet(offB, dV)` (`tools.h:488`) для каждой
клетки маски сам, а `recalcArea2Grid`+`regRender` выполняет один раз на весь
bbox штампа — тулза меняет только буферы, и весь маршрут игры (hardness-учёт,
`At_*`, согласованность `VxG/VxD/Sur`, `GetGeoType` для поверхности)
остаётся Terra'овским. Статический экземпляр тулзы внутри
`applyEffectToCell` безопасен: его конструктор читает только
`vMap.hZeroPlast`, а к моменту первого применения мир уже загружен.

### `map.tga` игровых миров: bottom-left origin, произвольный размер (T2.4)

`RESOURCE/Worlds/COMPASS/map.tga` — uncompressed 24-битный TGA, но
descriptor = 0, т.е. строки идут **снизу вверх** (bottom-left origin), и
размер файла 128×128, а не 2048² — шелл читает его в произвольном размере
(`PerimeterShellUI.cpp:2896/4605`, `CreateTexture("map.tga")`). Отсюда:
`WorldImages::loadTga24` (T2.4) обязана поддерживать оба origin (флип при
загрузке) и не привязываться к размеру карты; `MinimapWidget` натягивает
картинку на прямоугольник карты в клетках, а не по пикселям изображения.
Редактор пишет `map.tga` в top-left (descriptor 0x20), комплектные миры —
в bottom-up; TGA-ридер Terra уважает origin-бит (`tgai.cpp:50,89,115,150`),
так что оба варианта корректны для формата `map.tga`.

## Кисти высоты — находки T3.2

### `tVoxSetAll` затирает верхние биты `AtrBuf` дробной частью высоты

Любая запись высоты в `tools.h` (CHANGE_HEIGHT, ALIGN_4ZP, ALIGN_VARIABLE_H)
заканчивается строкой `AtrBuf[offB] = v & VX_FRACTION_MASK;` — присваиваемое
значение всегда < 32, т.е. ВСЕ биты выше 0x1F (`At_SHADOW` 0x20,
`At_SOOT` 0x40, `At_LEVELED` 0x80, `At_ZEROPLAST` 0xC0) снимаются при любом
изменении высоты. Это поведение игры, редактор его не «чинит»; следствие:
клетка, дошедшая до цели, получает `(fraction | At_LEVELED)` (метка ставится
после записи), а недошедшая — чистую долю. Тесты 59/60 сравнивают байт
`AtrBuf` целиком.

### Выравнивание: скип зеропласта и метка выровненности — поведение тулзы

`T2TE_ALIGNMENT_*::tVoxSet`: клетки с `(Atr & At_ZPMASK) == At_ZEROPLAST`
возвращаются нетронутыми; после веток подъёма/опускания (обе каппятся на
`hAppr`, опускание — с hardness-затуханием `dV = dV*(h<<h)/24` в целых
операциях именно в этом порядке) безусловно выполняется
`if (v == hAppr) AtrBuf = (AtrBuf & ~At_ZPMASK) | At_LEVELED` — в том числе
для клеток, которые уже стояли на цели (просто метка, без смены высоты).
`setHAppoximation()` принимает ЦЕЛЫЕ воксели (`h << VX_FRACTION` внутри);
редактор синхронизирует цель перед каждой клеткой, чтобы статическая тулза
не удержала `hZeroPlast` предыдущего загруженного мира.

### Дамба: кто её вообще создаёт и что делать с нулевым гео

Ни одна put/dig-тулза игры не создаёт «настоящую» дамбу (`VxDBuf != 0`) из
пустого гео — они лишь правят активный слой; дамба в поставляемых мирах
(47% COMPASS) — наследие генератора уровней. Единственный сеющий код —
`T2TE_PLOTTING_VERY_LIGHT_DAM`: `VxDBuf = VxGBuf; SurBuf = vMap.veryLightDam`.
Отсюда режим Dam редактора: посев дамба именно этими записями, при
нулевом гео — `VxDBuf = 1` с компенсацией дельты на −32 (1/32 м × 1),
потому что без этого `tVoxSet` считал бы клетку «без дамба» и стал бы править
гео. Снятие дамба — ветка `v <= VG` стандартного CHANGE_HEIGHT: она не только
чистит `VxDBuf`, но и **опускает гео до упавшей поверхности** (`VxGBuf = v >>
VX_FRACTION`) — копание проедает и гео, не только дамбу.

### Geo-кисть на дамбовой клетке: общая дробь AtrBuf и «чужой» SurBuf (bugfix T3.2-ревизии)

Первая ревизия Geo-режима каппила подъём гео на высоту дамба и переписывала
на дамбовых клетках `SurBuf = GetGeoType(off, v)` и `AtrBuf = v & 0x1F`. Обе
записи — ошибки, потому что эти буферы на дамбовой клетке принадлежат ВЕРХНЕМУ
слою:

- `AtrBuf[0x1F]` — одна доля на ОБА слоя: это доля верхней поверхности
  (`SGetAlt`, LAND.cpp:1206-1213, читает её и для дамба). Запись туда доли
  гео (`v`Cap-подъём опускал её выше по остатку) сдвигала ВИДИМУЮ высоту
  дамба без изменения `VxDBuf` — дамба «ныряла»/прыгала при движении кисти
  по гео под ней.
- `SurBuf` — материал верхней поверхности (`GetTer` = `SurBuf`,
  `damType2Mater[SurBuf]`, LAND.cpp:1200-1212; цвет = `Sur2Col32[SurBuf]`
  с дамбовым битом Rnr). `GetGeoType` = 3D-текстура грунта f3d.calc по
  НОВОЙ высоте гео — дамбовая клетка перекрашивалась в материал грунта на
  поднятой высоте, что выглядело как «поднятое гео лежит поверх дамба».

Итоговое поведение Geo-режима: подъём на клетке с дамбом двигает гео и дам
вверх на одну дельту (толщина дамба сохраняется, дробные биты общие и
остаются согласованными — обе верхушки сдвинуты на одно dV, поэтому
`newGeo ≡ newDam (mod 32)`); опускание — точное обращение подъёма, обе
верхушки уходят вниз на одну дельту, и пара «поднять + опустить» с теми
же параметрами возвращает клетку байт-в-байт (симметрию ломают только
клампы на 0..MAX). SurBuf на дамбовых клетках не пишется.
Гео при этом остаётся видимо там, где оно открыто (уступы рядом с дамбом),
а под дамбом — перекрыто им.

### Бюджет тестов кистей: пред-состояние штампа замеряется в момент вызова кисти

`UndoHistoryTests`/`BrushToolTests`-паттерн «снимок → правка → undo» имеет
нюанс: снапшот undo пишется ВНУТРИ `applyStamp` (после любых ручных предправок
теста, например метки `At_ZEROPLAST` или посева тест-дамба). Поэтому
тест-проверка undo обязана замерять «before» непосредственно перед
`applyStamp` (после предправок) — иначе сравнение ложно валится. Тест 60
(режимы) отдельно сверяет undo результата Geo-капа с посеванным (не исходным!)
состоянием.

### Регистрированные тесты T3.2 (порядок 59/60)

Обе цели выравнивания идут в чистом (без дамба и зеропласта) районе COMPASS
возле (24,24)/(22,22); ожидаемые значения реплицируют Terra-математику
(кап на цель, hardness-формула, посев/снятие дамба) — это осознанный
дубликат формул в тесте, выступающий оракулом, а не копипастой продакшена.

### Почему мир в редакторе «блочнее», чем в игре (post-T3.3)

Данные рельефа у игры и редактора идентичны по цвету: заливка текстур тайлов
рельефа в игровом рендере берёт тот же `vMap.getColor32(xx,yy)` по ячейке
(`Source/Game/CopyToGraph.cpp`, `PerimeterTerraInterface::GetTileColor`). Гладкость
даёт не цвет, а способ семплирования: тайл на GPU фильтруется билинейно
(mipmap при отдалении), а поверхность — интерполированный меш: вершины
`TileMapBumpTile` берут высоты через `TerraInterface::GetZf` = `SGetAlt`
(билинейная интерполяция в `VMAP.h`), плюс освещение сцены на вершинах.
Редакторский TopDown показывал «1 ячейка = 1 пиксель» без фильтра, а
`zoomToFit()` для миров с `fitScale_ > 1` (мир меньше окна) вообще рисовал
увеличение nearest-neighbor'ом — мир выглядел крупными квадратами. Также
программный `viewV2D` (3D-вид) сам интерполирует высоту/освещение по углам
ячейки (32.8-фикс, `VMAP.cpp:2105-2173`), т.е. «ступеньки» 3D-вида — это
свойство воксельного рендера, а не отсутствие фильтрации. Решение
(переключаемые стили Chunky/Smooth) — в `docs/architecture.md` §5.6.

### Дальняя «блочность» 3D-вида: минификация с точечной выборкой (post-T3.3)

После внедрения стилей выяснилось продолжение: в наклонном 3D-виде при
крутых камерах (rot 0, tilt 140, lift 100, focus 250, мир FORTOP) дамбы в
углах карты выглядят крупными блоками, а при приближении камеры становятся
гладкими. Причина — **алиасинг уменьшения**: `viewV2D` берёт по одному
семплу клетки на экранный столбец/строку, а у горизонта один пиксель
покрывает десятки клеток (проверено по формулам строки: у горизонта ~30–60
кл/пкс) — цвет скачет между соседними клетками «шахматкой», силуэт
превращается в ступеньки. Высота при этом интерполирована биленейно уже
сейчас — дело в цвете/материале и в выборке вообще. GPU-рендер игры решает
это mip-маппингом текстуры; в редакторе наведена mip-пирамида
`core/ColorMipmap.{h,cpp}` (цвета уровня 0 = `getColor32`, высоты = VxD/VxG,
уровни ≥ 1 — средние 2×2, инкрементальные обновления по dirty-rect), и
`View3DRenderer::renderSmooth` при стиле Smooth рисует ту же проекцию
`viewV2D` (формулы скопированы дословно), но с билинейной обёрточной
выборкой пирамиды на уровне, подбираемом по наземному следу пикселя
(задействованы и |sx| вдоль строки, и |DY(d+1)−DY| вперёд). Чанки-путь
(Terra `viewV2D`) не тронут; Terra не модифицирована. Детали —
`docs/architecture.md` §5.7.1; тесты: «ColorMipmap pyramid» (арифметика
средних/биленейной выборки) и «Smooth 3D view (post-T3.3)» (bit-exact
паритет с `viewV2D` на выровненном мире + следование пирамиды
dirty-rect-конвейеру после правки).

Следом закрыта регрессия ближней половины кадра: при камерах с малым
tilt/коротким фокусом (rot 271, tilt 29 → клампится, lift 100, focus 150,
FORTOP) нижняя часть экрана вместо рельефа становилась одним размытым
пятном. Причина — в следе вперёд |DY(d+1)−DY| для строк с d<0 использовался
немодулированный DY(d+1), у которых основной цикл сам инвертирует знак:
разность вырождалась в ≈ 2·|DY| (до ~950 «клеток на пиксель») и вся нижняя
половина рисовалась верхними уровнями пирамиды. Фикс — DYnext получает ту
же инверсию знака, что и DY; стиль Smooth после него совпадает по
характеру с чанком в ближней зоне (билинейно сглаженная клеточная мозаика)
и сохраняет фильтрацию у горизонта. Тест «Smooth 3D near field»
(order 62) фиксирует вариативность цветов нижней трети кадра относительно
чанк-референса на реальном (невыровненном) мире.

Далее закрыта «слоистость» дальних гор (rot 0, tilt 140, lift 100, focus
300, FORTOP): вершины выглядели стопкой горизонтальных «слоёв», гладких
вдоль камеры, но кусочных в глубину. Причины: 1) каждая полоса строки
красилась одним цветом семпла своей строки — жёсткие ступени между
строками; 2) дискретный выбор уровня (округление следа вверх) — кольца на
каждом удвоении Ядра. Фикс в `View3DRenderer::renderSmooth`: полоса
интерполируется линейно между якорями этой и предыдущей строки (попиксельная
обратная проекция на землю между P(d−1) и P(d) — соседние полосы стыкуются
непрерывно), уровень стал дробным: floor(log2(след)) с трилинейной долей к
более грубому уровню (ядро растёт непрерывно), высоты усреднены по глубине
(силуэты террас тоже фильтруются). Уровень 0-семплы прежние — bit-exact
паритет с `viewV2D` на выровненном мире сохранён тестом; подшаговые по
глубине строки (|ΔDY|<клетки) семплируют только текущую позицию (ближняя
зона не удорожается). Прогон на FORTOP до/после: лоскутные ступенчатые
грани вулканов → гладкие градиенты, силуэты чистые.

### Qt moc и enum-классы в сигнатурах сигналов (T4.2)

Стиль проекта: перечисления-параметры сигналов
(`viewModeChanged(ViewMode)`, `renderStyleChanged(RenderStyle)`) объявлены
**вложенными** в класс-эмиттер (`ViewportWidget::ViewMode`), а в сигнатуре
пишутся полностью квалифицированно. Сборка ломается, если новый
перечисленный тип объявить в namespace-скоупе (`MapEditor::EditorMode`), а
сигнал — с квалификатором вложенности
(`editorModeChanged(MapEditor::ViewportWidget::EditorMode)`): moc
генерирует код, который не находит такой квалификатор («EditorMode не
является членом ViewportWidget»), и падение выливается в шаблонные ошибки
moc-включения. Решение — nested enum в классе (как у `ViewMode`). Урок:
при добавлении сигнала с enum-параметром держать перечисление внутри
класса-эмиттера и писать квалификатор ровно по тому скоупу, где
перечисление реально живёт, по образцу уже работающего соседа.

### Локальная переменная с именем члена-геттера (C++, T4.2)

`const auto *renderer = renderer();` внутри метода-геттера — точка
объявления переменной находится ДО инициализатора, поэтому вызов в нём
резолвится в саму переменную (C2064 «result is not a function taking 0
arguments»). Окружение ловит это не всегда: тот же паттерн в статическом
хелпере собирается, потому что там вызов квалифицирован
(`viewport.renderer()`). Урок: локали не называть именем геттера — или
вызывать через `this->renderer()`.

## Палитры и SurBuf

### `SurBuf` — общий индекс в палитру СЛОЯ клетки, а не «0..127 Geo / 128..255 Dam» (T4.1)

В плане/архитектуре давно жила интерпретация «0..127 — Geo-палитра,
128..255 — Dam» (по ней работали и старые хелперы `paletteRgb`). Код игры
говорит иное:

* `RenderStr`/`WorldRender` ставит в `RnrBuf` `light` для гео и
  `0x80|light` для дамба (LAND.cpp:1462: «если выступает Dam»), т.е.
  принадлежность слою живёт в **бите 7 RnrBuf**, а не в диапазоне `SurBuf`;
* `convertPal2TableSurCol(DamPal, Damming)` заполняет
  `Sur2Col32[i][j+128] = гамма(DamPal[i*3..])` по ВСЕМ 256 строкам
  (VMAP.cpp:1346-1372), `getColor32()` смотрит
  `Sur2Col32[SurBuf[off]][RnrBuf[off]]` — т.е. `SurBuf` индексирует
  палитру активного слоя **напрямую**, без сдвига на 128;
* `PutAltDam` НЕ меняет `SurBuf` (VMAP.h:864, SetTer закомменчен) — рисунок
  дамбы читается по унаследованным гео-индексам «через колонки дамба той же
  строки»; `PutAltGeo` при съёме дамба пересчитывает `SurBuf=GetGeoType(...)`
  с полным диапазоном 0..255;
* `tools.h:235`: игра красит дамбовые клетки `SurBuf=veryLightDam` — индекс
  по argmax по ВСЕЙ DamPal (0..255), без +128;
* гистограмма шиппованного мира (COMPASS, прогон теста): гео-клетки —
  `SurBuf` 0..47 (подавляющее) + 3 выброса ≥128; дамбовые клетки — полностью
  0..255; GeoPal (и из geoPal.xml, и из inGeo.act): нижняя половина занята,
  верхняя (128..255) чёрная — т.е. гео-индексов ≥128 в данных фактически
  нет, а трактовка дамбовых индексов ≥128 как «DamPal[i-128]» была бы
  сплошной ошибкой чтения.

Отсюда конвенция редактора: индекс кисти = сырой байт `SurBuf`; к какой
палитре он относится — определяется слоем (клетки для пипетки/курсора —
через `VxDBuf != 0`; для свотчей кисти — через текущий режим Geo/Dam
кисти). Хелперы сессии принимают слой явно (`paletteRgb(layer, ...)`,
`setPaletteRgb(layer, ...)`), чтобы 128-разрез не «запёкся» в интерфейсе
снова.

### Порядок байт палитр — RGB; комментарии «BGR» были ошибочны (T4.1)

`convertPal2TableSurCol` читает `palBuf[i*3+0]` как красный
(VMAP.cpp:1347-1349), и это же согласуется с данными: первые байты
COMPASS/inGeo.act (172,145,57 | 222,202,106) точь-в-точь равны
`(unsigned char)(x*255)` первых двух компонент шиппованного geoPal.xml
(0.677419, 0.571429, 0.225806), и с толкованием «R,G,B» получается
классический охристый цвет периметровского грунта; в толковании «B,G,R» —
вырожденный сине-зелёный. Комментарии WorldFiles.h «256 x 3 BGR / BGR
order» и пометка в плане исправлены, а прежний `paletteRgb` (T3.3) читал
те же байты как B,G,R — свотчи кисти показывали цвета с перепутанными
R/B каналами; обе ошибки устранены в T4.1.

### geoPal.xml — единственный источник GeoPal при загрузке в TX-сборке (T4.1)

`vrtMap::loadGeoDamPal` (VMAP.cpp:1408-1427): в `_TX3D_LIBRARY_`-сборке
гео-палитра БЕРЁТСЯ ИЗ geoPal.xml (через
`tx3d::IndexedTexture3D::extractColorTableFromXML` → `pal[i].x*255`);
inGeo.act читается только в не-TX сборке. Поэтому «отредактировать GeoPal и
записать inGeo.act» недостаточно — правки живут до первой перезагрузки
мира. Редактор синхронизирует geoPal.xml при `saveWorld()` вместе с
inGeo.act/inDam.act (`saveGeoDamPal`). (Исследовав COMPASS: inGeo.act
совпадает с XML-палитрой поточечно, формат не расходится.)

Дополнительная тонкость: XML хранит float 0..1, а конверсия в байт —
обрывающая (`unsigned char(float*255)` по `Vector3D::x` float). Сериализация
точного `b/255` через `printf/atof/float` может дать `v*255` чуть-чуть ниже
целого: 174/255=0.68235294…, 6 знаков дают 0.682353, (float)0.682353*255
== 173.9999… → байт 173 вместо 174. `PaletteOps::geoPalXml` поэтому пишет
`(b + 0.5)/255` с `%f` (6 знаков): погрешность чтения ≤2e-4 байта против
степени отчёта 0.5 — readback байта гарантирован для всех 256 значений,
включая 0 и 255 (для 255 значения становятся «1.001961» — гранично, но
допустимо: конверсия не клампит). Свойство проверено тестом 64 (round-trip
всех 768 байтов + перезагрузка мира с новой палитрой).

### Буфер чтения XML-палитры ограничен (258*60 байт)

`loadGeoDamPal` читает geoPal.xml в буфер 258*60 = 15480 байт
(VMAP.cpp:1412). Документ 256×`<color value='r,g,b'/>` при `%f`-компонентах
занимает ~11 КБ — влезает, но «расширенный» формат (больше знаков, пробелы,
комментарии) рискует не уместиться и молча усечься. Генератор держит строки
короткими (`%f`, без пробелов).

### Кисть цвета обязана учитывать слой клетки (T4.3)

Бит 7 `RnrBuf` ставится по `VxDBuf` в момент рендера (LAND.cpp:1461-1462),
а не по значению `SurBuf`. Следствие: рендер разрешает цвет клетки через
палитру её слоя всегда — фиксация «чужого» индекса в `SurBuf` дамбовой
клетки покажет цвет `DamPal[индекс]`, а не `GeoPal[индекс]`, и наоборот.
Поэтому `SetColor` гейтится по клетке (BrushTool.cpp, `applyEffectToCell`):
Geo-режим красит только `VxDBuf == 0`, Dam-режим — только `VxDBuf != 0`;
кисть цвета не сеет дамбу (у `PlotZeroplast`/`VeryLightDam`) и не снимает её.
Игровых аналогов не существует (в игре `SurBuf` пишут напрямую только
инструменты дамбы, tools.h:235/540) — решение редакторское, по мотивам §5.13.

Практическое следствие для тестов: анкеры фиксированного центра ненадёжны —
дамбы покрывают ~половину COMPASS. Тест 61 ищет однослойные заплатки
(`findLayerPatch`, шаг 4 по внутренности карты), тест 63 подстраивает
`params.mode` под слой клетки перед краской.
### Цвет «очень лёгкой дамбы» (белый) — это поведение игры (T3.4/T4)

«Очень лёгкая дамба» красит поверхность индексом `vMap.veryLightDam`, а этот
индекс определяется в игре как **самый яркий** (максимальная luminance
0.3R+0.59G+0.11B) цвет дамбовой палитры (`VMAP.cpp:1346-1355`,
`convertPal2TableSurCol(DamPal, Damming)`) — то есть бело-серый оттенок
почти в любых мирах. Это не баг редактора: игра рисует начальную тонкую
дамбу тем же цветом.

Проверено (ревизия по фидбеку): тинт не зависит от ядер/игроков/энергии.
`veryLightDam` присваивается ровно в двух местах кода всего движка —
сброс в 0 в конструкторе (`VMAP.cpp:209`) и расчёт по палитре выше;
`convertPal2TableSurCol` вызывается только при загрузке мира
(`loadGeoDamPal`, VMAP.cpp:1429/1435) и в легаси-SurMap
`putTgaComplete2AllMap` (VMAP.cpp:2713). `SurBuf=veryLightDam` пишут только
тулзы `T2TE_PLOTTING_VERY_LIGHT_DAM` (tools.h:235/540). Цвет клетки на
экране — `Sur2Col32[SurBuf][RnrBuf]`, где `RnrBuf` — рельефное освещение из
`RenderStr` (LAND.cpp), без игроков; hardware-путь красит тайлы тем же
`getColor32` (`PerimeterTerraInterface::GetTileColor`, CopyToGraph.cpp:40).
Единственный per-player хук цвета рельефа в движке — `SetZeroplastColor`
(zeroplast_color, TileMap.h:113-119), применяемый в `TileMapRender.cpp:602`
только к клеткам внутри energy region игрока (`columns[player]->filled()`,
TileMapBumpTile.cpp:157-164) — то есть к зеропласту, никогда к поверхности
дамбы.

(Ревизия по фидбеку: синюю тонировку зеропласта игра показывает только в
поле запитанного ядра через 3D-сцену — в редакторе её быть не должно, см.
ниже «Зеропласт в редакторе рендерится как выровненная земля».)

### Кисти зеропласта доступны только в режиме Dam (решение по фидбеку)

Зеропласт принадлежит домену дамбы, поэтому объединённая кисть «Level to
Zeroplast» (выравнивание до `hZeroPlast` + пометка `At_ZEROPLAST`, слияние
бывших Align4ZP и PlotZeroplast) и «Erase Zeroplast» активны только в
Dam-режиме; при переключении в Geo-режим активный зеропластовый тип кисти
откатывается в Raise (`MainWindow::createBrushActions`, `updateActionStates`).

### Изображение — маска штампа любой кисти (переработка T3.5 по фидбеку)

Раньше «Image Brush» был отдельным типом кисти: переключение на Raise/Lower
теряло загруженную картинку, а в 3D-режиме загрузка из View-режима оставляла
редактор в навигации (клики ничего не красили). Теперь `BrushParams::
useImageMask` делает загруженную картинку геометрией штампа для ЛЮБОГО
эффекта, выбор формы (круг/квадрат/…) явно возвращает форму, а `Load Image`
переключает редактор в режим Brush. Влияние пикселя = его АЛЬФА (0..255),
а не яркость: прозрачные пиксели не действуют совсем, полупрозрачные дают
частичное влияние (это же делает «Paint Color» по маске точным — цвет
ложится только на непрозрачную часть картинки). На панели есть масштаб
маски (10..800%): маска пересчитывается билинейно из сохранённого
оригинала при каждом изменении, поэтому повторные масштабирования не
накапливают размытие.

### Зеропласт в редакторе рендерится как выровненная земля, без синей тонировки

Синий оттенок нулевого слоя в игре приходит из 3D-сцены
(`terMapPoint->SetZeroplastColor`, Game/Player.cpp:850) и виден только в
поле запитанного ядра; ядер в редакторе нет. Поэтому все программные пути
редактора (2D-кэш, mip-пирамида 3D, генерация cache.tga/map.tga) рисуют
`At_ZEROPLAST`-клетки как выровненные: свой цвет + `leveledSurfaceTexture.tga`
сверху; chunky-3D (Terra `viewV2D`) — через временное демотирование
`At_ZEROPLAST` → `At_LEVELED` на время прохода рендера
(`View3DRenderer::render`). `vrtMap::getColor32` (игровой путь) не тронут;
пометка зеропласта видна через оверлей.

### Опции вида по фидбеку: затемнение гео, сетка 3D, заморозка дамбы

Затемнение гео («в игре гео — серые/чёрные оттенки») реализовано как
редакторский LOOK-переключатель (`ViewportRenderer::setGeoDimmed`, по умолчанию
вкл): клетки без дамбы → luminance/2 серым, дамбовые — палитра как есть.
Движкового аналога в программных таблицах нет (единственный per-player тинт —
зеропласт, см. выше), поэтому это воспроизведение игрового ВИДА, а не
движкового кода; на `cache.tga`/`map.tga` и chunky-3D не действует.

Сетка в 3D — «прозрачная плоскость с линиями» (`drawGridOverlay`): каждая
линия на плоскости отсчёта (высота `hZeroPlast`, смещения OXY без рельефа)
проходится в координатах карты адаптивным шагом и ПРОЕЦИРУЕТСЯ наперёд через
ту же камеру кадра (инверсия строчной математики: |near| = |forward|·|cos(lean)|,
строка — из замкнутой формы near(d), колонка — линейно по размаху строки);
сегменты рисуются Брезенхэмом белым 2x2-блоками. Предыдущее перечисление
пересечений со строками развёртки имело вырожденные ориентации: линии,
параллельные строкам (горизонтальные карты при повороте 0°), не пересекали
ни одной строки и пропадали совсем. Важно: наклонная камера видит землю С
ОБЕИХ сторон надира (центр экрана ≈ проекция камеры, нижние строки — земля
ПОЗАДИ неё) — bbox клиена обязан включать отрицательную прямую дистанцию.
Оверлей запечён в кэшированный кадр, поэтому переключение сетки и смена
шага ставят `needs3DRedraw_`.

Затемнение гео в chunky-3D: `viewV2D` сэмплит 16-битные таблицы Terra
(`Sur2Col[sur][свет+128*слой]`, `Tex2Col[свет+128*слой][tex]`), поэтому
`viewV2DChunky` временно сереет гео-половины (строки света 0..127) обеих
таблиц, зовёт `viewV2D` и восстанавливает байты — включая fallback-пути
smooth-рендера без пирамиды. Тест 66 проверяет и отличие кадра, и
байт-точное восстановление обеих половин таблиц.

Заморозка дамбы: `renderSmooth` отслеживает unwrapped-координаты центра
камеры (виджет передаёт НЕ обёрнутый центр — `viewV2D`/`renderSmooth`
оборачивают сами через XCYCL/YCYCL, а разница wrapped/unwrapped даёт смещение
копии карты); сэмплы вне реальной копии читают вторую «гео-только» пирамиду
(гео-палитра + `VxGBuf`), внутри — композитную. Полосы, пересекающие край
карты, смешивают две пирамиды по якорям. Chunky-3D (`viewV2D`) режим не
поддерживает — в этом стиле мир повторяется целиком.

Центр 3D-камеры при открытии мира — `applyViewportSettings()` ставит look-at
в центр карты (раньше оставался (0,0) → вид на левый верхний угол).

### Анти-перспектива viewV2D ниже надира (найдена через сетку)

Сетка 50x50 при rot 60 показала: линии РАСХОДЯТСЯ к низу экрана. Оказалось —
это родовой дефект viewV2D (Terra/VMAP.cpp:2078+,SurMap-наследие, игрой не
используется): для строк d<0 (ниже надира, центр экрана) near = d(F+Z)/(d+tgaF)
положительно с полюсом near=F+Z при d→-inf — дальняя земля сзади занимает
больше строк (dd/dnear растёт) и более узкий боковой размах DX = xside(F+Z-
near)/F — обе оси перевёрнуты. Сетка честно инвертировала рендер (round-trip
бит-в-бит), поэтому дефект был виден на ней, но не на органическом рельефе.
Фикс в редакторе: зеркалирование нижней половины (см. docs/architecture.md
§5.16); Terra не тронута, chunky-стиль переехал на точечную выборку уровня 0
общей прогулки renderSmooth, viewV2D остаётся fallback-ом без источника.

### Одна сетка вместо двух (ревизия по фидбеку)

В 2D и 3D рисовались ДВЕ сетки — настраиваемая (шаг спинбоксами W/H, по
умолчанию 4) и фиксированная грубая 64-клеточная «рамка отсчёта»; каждая
64-я линия покрывалась обеими и читалась как наложение двух сеток. Проверка:
Terra сеток не рисует вовсе — kmGrid/kmGridChA (VMAP.h:89,121) это константы
АНАЛИТИЧЕСКОЙ сетки GABuf (кластеры/изменённые области), viewV2D и getColor32
графических сеток не содержат. Обе сетки были редакторскими; оставлена ОДНА
настраиваемая — грубая удалена (ViewportWidget::drawGrid, draw3DRaster).

### Квиры параметров мира (T5.1)

- **Minimal Square Power фактически игнорируется при загрузке.**
  `analyzeINI` (VMAP.cpp:383) читает его в `MINSQUARE = 1 << power`, но
  следом `setupGeneralVariable()` (VMAP.cpp:570) перезатирает:
  `MINSQUARE = 1 << MINSQUARE_POWER`, а `MINSQUARE_POWER` из ini не читается
  вовсе (только `createWorld` ставит 4 и XPrm-путь `newLoad`). В итоге для
  обычной загрузки `MINSQUARE` зависит от неинициализированного члена
  глобального `vMap` (нуль → MINSQUARE=1). Редактор значение из ini читает,
  показывает и пишет обратно, но семантику «из ini» мир при загрузке не
  получает. Не чинится — Terra не трогаем.
- **Формат output.vmp определяется заголовком, а не ini.** Ключ
  `[Storage] Compressed Format Using` нигде в игре не читается — fullLoad
  смотрит на 4-байтовый id (S2T0/S2T1). Редактор держит ключ в согласии с
  реальным заголовком (`WorldParams::readFromWorld` берёт формат из файла,
  fallback на ключ). `save3Buf()` всегда пишет S2T0 — поэтому сессия
  конвертирует файл после каждого сохранения, повторяя логику
  `vrtMap::compressWorlds` для одного файла (та перебирает все миры и
  умирает через `ErrH.Abort`, для редактора не годится).
- **Периметр.ini `[TD] Color ZeroLayer`** — глобальный цвет зеропласта
  (r g b a), читается `analyzeINI` каждого мира; при отсутствии ключа —
  встроенные 1 11 51 70. В `_TX3D_LIBRARY_`-рендере игры реально
  применяется только внутри энергополя ядра (см. проверенный факт в
  docs/architecture.md §5.14); редактор пишет ключ и обновляет
  `vMap.colZeroPlast`.

### .spg: текстовый DOM вместо зеркальных структур (ревизия плана, T8.1)

План предполагал XPrmArchive + зеркальные структуры Save.h 1:1 + EnumRegistry.
Реализовано иначе — `core/spg/XPrmDocument` (байт-сохраняющий текстовый DOM,
философия IniDocument): .spg хранит ВЕСЬ SavePrm (~52 KB: фреймы, сквады,
frame slots, damage moleculas, 100+ контролов UI, триггеры); зеркалирование
всех структур — тысячи строк, и ЛЮБОЕ пропущенное поле XPrm-райтер молча
теряет при записи. DOM хранит исходные слайсы каждого узла + промежутки
(gaps) и терминаторы — незатронутый файл воспроизводится байт-в-байт,
редактируется только изменённое значение (`name = value;` с исходным
';'/','). Enum-идентификаторы сохраняются как текст — EnumRegistry не нужен.
Схемный слой `core/spg/SpgFile`: worldName, playersData, players[i].frame
(позиция + squad + stablePosition + frameSlots + камера — двигаются группой,
dz по дельте высот рельефа), manualData.zeroLayerHeight, setPlayerCount
(клонирование/удаление элементов массивов + перенумерация playerID).
Уроки: u8string()-итераторы временного объекта в MSVC дали SIGABRT — читать
файл через readFileBytes; массив, пересобранный программно, нужно помечать
edited у КАЖДОГО поля, иначе отрисуются старые raw-слайсы.
