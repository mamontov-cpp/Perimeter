# Архитектура редактора карт

Документ фиксирует принятые архитектурные решения по редактору карт (см.
`docs/map_editor_plan.md`). Обновляется по мере выполнения задач.

## 1. Границы и слои

Редактор — отдельное приложение `map_editor` (Qt6 Widgets), собирается только
при `OPTION_MAP_EDITOR=ON`. Игровая сборка не зависит от Qt. Исходники —
`Source/MapEditor/`, три слоя:

| Слой | Зависит от Qt | Ответственность |
|---|---|---|
| `MapEditorCore` | нет | сессия/мир, файлы (`WorldFiles`), INI (`IniDocument`), preflight-проверки, изображения, кисти, `.spg`, валидация |
| `MapEditorSupport` | нет | шимы для живущих в игре символов: `init_content_root`, `ErrH`, `logicRND`, `IniManager`, `terEnergyBorderCheck`, `currentShortVersion` |
| `MapEditorApp` (`ui/`) | да | окна/панели/вьюпорт; вся работа с `vMap` — в UI-потоке |

`MapEditorCore` линкуется с `Terra`, `tx3d`, `XTool`, `Util`, `SDL2::SDL2`
(заголовки), `ZLIB::ZLIB`. Terra переиспользуется как есть, без `_SURMAP_`.

## 2. `EditorSession` — жизненный цикл мира

`EditorSession` (в `core/`, без Qt) инкапсулирует глобальный `vMap` Terra.

**Установка папки игры.** `setGameDir()` проверяет, что путь существует и
содержит `RESOURCE/Worlds/`. `init_content_root()` (в `MapEditorSupport`)
выставляет content-root = текущий рабочий каталог и сканирует ресурсы
(`set_content_root_path` + `scan_resource_paths("./")`).

**Скан миров.** `scanWorlds()` перечисляет каталоги `RESOURCE/Worlds` через
`get_content_entries_directory` — та же логика, что в `vrtMap::prepare`, —
ПЛЮС миры модов: `Mods/<ModName>/RESOURCE/Worlds/<World>` (папка `Mods` может
отсутствовать; `Mods/Publish` — служебная, пропускается). Мод-миру
`WorldInfo.modName` непуст, `displayName()` = `Mod / World`. Перечисление
модов идёт через тот же content-map: скан `"./"` уже положил `mods/<mod>/
resource/worlds/...` под ключи (XTool принимает ключи с `mods`), поэтому
`dirKey` мода — точный ключ, через который Terra резолвит файлы мира.

**Загрузка.** `loadWorld(index)`:
1. `fs::current_path(gameDir_)` + `init_content_root()`;
2. `refreshWorldTable()` — наполняет `vMap.wTable` (базовые миры + моды);
3. резолв мира ПО КОНТЕНТ-КЛЮЧУ (`wTable[i].dir == dirKey`; `getWorldID` по
   имени — фолбэк: у мода и базы может быть одноимённый мир);
4. `vMap.selectUsedWorld(terraIdx)` (analyzeINI + worldPrepare + данные) +
   `vMap.fullLoad()`;
5. `vMap.WorldRender()` — инициализация освещения `RnrBuf`/`At_SHADOW`, ровно
   то, что после загрузки делает `terUniverse::universalLoad`
   (`Source/Game/Universe.cpp`). Без этого `fullLoad()` оставляет `RnrBuf`
   неинициализированным (его цикл `RenderStr` закомментирован в
   `VMAP.cpp:924`), и любой `getColor32()` — вьюпорт, `cache.tga` — читал бы
   мусор (см. `docs/context.md`).

`loadWorldByName` при совпадении имён отдаёт предпочтение базовому миру.
Сохранение мода идёт в его папку: `worldFilesFor` строит путь как
`gameDir / dirKey`. Боевые карты из модов не сканируются (миры только).

**Выгрузка.** `unloadWorld()` освобождает именно буферы мира:

```cpp
vMap.delLeveledTexture();  // обязательно до освобождения VxDBuf
vMap.releaseMem4Buf();     // VxG/VxD/Sur/Atr/Rnr/Sup/GV/GA
vMap.worldFree();          // сеточные карты
```

`vMap.worldFree()` сам по себе освобождает только сеточные карты, поэтому
`isWorldLoaded()` (проверяющий `VxGBuf`) остался бы `true`. Полная
последовательность скопирована из `vrtMap::~vrtMap` (`Source/Terra/VMAP.cpp`),
но **без** `landRelease()` — радиусные таблицы `prepare()` одноразовые на
процесс (см. `docs/context.md`).

**Флаг изменений.** `isModified()` = `vMap.worldChanged || modified_`;
`setModified()` синхронизирует оба.

## 3. `WorldFiles` — доступ к папке мира

`WorldFiles(worldDir)` — типизированный доступ к файлам одного мира по именам
из `Source/Terra/VMAP.cpp:21-38`: `world.ini` (все секции через `IniDocument`),
`inGeo.act`/`inDam.act`, `hardness.bin`, `geoPal.xml`/`geoTx.xml`,
`leveledSurfaceTexture.tga`, `cache.tga`/`map.tga`. Неизвестные ключи INI при
записи сохраняются; чужие файлы не трогаются (см. `docs/context.md`).

## 4. Сохранение мира (T1.3)

`saveWorld()` (в `EditorSession`) выполняет конвейер:

1. **Буферы/палитры/[3DF].** `vMap.save3Buf()` — внутри вызывает
   `save3BufOnly()` (S2T0, `output.vmp`), `saveGeoDamPal()`
   (`inGeo.act`/`inDam.act`) и `f3d.saveVariable()` (`[3DF Parameters]`).
2. **`hardness.bin`.** `vMap.saveHardness()` — только если файл уже есть
   («Сохранить» не добавляет файлы, которых автор не просил).
3. **`world.ini`.** `writeMapPower(H_SIZE_POWER, V_SIZE_POWER)`,
   `writeHZeroPlast(hZeroPlast)`, `writeStorageVersion` (сохраняет текущую
   версию, иначе `1.4`).
4. **Изображения** (генерация T6):
   - `cache.tga` — 24-бит несжатый TGA `H_SIZE×V_SIZE`, пиксели из
     `ViewportRenderer` (Composite-фильтр, без оверлеев, т.е. ровно
     `vMap.getColor32()`, BGR). Игра `xassert`-ит на этом файле при
     `fullLoad`, поэтому он перегенерируется на каждом сохранении;
   - `map.tga` — миникарта: та же картинка, масштабированная не более чем до
     256×256 (ближайший сосед).

После успеха сбрасываются `modified_` и `vMap.worldChanged`; в стеке undo
запоминается позиция «последнего сохранения» — после undo/redo флаг modified
пересчитывается относительно неё (правка → сейв → undo снова «чист»).

## 4.1 Undo/Redo (T1.4)

Terra записывает undo только под `_SURMAP_` (`UndoDispatcher_PutPreChangedArea`
— заглушка в сборке игры/редактора), поэтому история хранится в сессии:
`EditorSession::recordUndoArea(x,y,w,h)` снимает «до»-состояние
`VxGBuf/VxDBuf/AtrBuf/SurBuf` над прямоугольником (клип к карте, лимит памяти
как в Terra — 4096² клеток), `undo()/redo()` обменивают снимок с буферами и
отмечают область через `regRender` (вьюпорт обновляется по обычной
dirty-конвейерке). Обязательный контракт для инструментов (T3): вызывать
`recordUndoArea()` ДО первой правки буферов. Подробности — в
`docs/context.md`.

**Coalescing-транзакции (окно 500 мс).** Последовательные undoable-действия
(штампы кисти по штриху, операции scripted brush, импорт картинки и т.п.),
приходящие с интервалом меньше **500 мс**, не пушатся в стек по одному, а
копятся в «pending»-транзакции и сливаются в **одну запись** по объединённому
прямоугольнику (per-cell выигрывает самый ранний снимок — восстанавливается
ровное «до»-состояние всей серии); один `Ctrl+Z` откатывает всю серию.
Транзакция закрывается (финализируется в стек): по истечении окна, при
`undo()/redo()`, `clearUndoHistory()`, `breakUndoCoalescing()`, при
переполнении бюджета клеток (`kMaxPendingUndoCells` — иначе непрерывный
штрих копил бы снимки бесконечно) и при `setUndoCoalescingWindowMs(0)`.
Явная группа `beginUndoGroup()/endUndoGroup()` участвует в окне: после
`endUndoGroup()` транзакция остаётся pending и следующие <500 мс действия
доклеиваются к ней. Окно задаётся `setUndoCoalescingWindowMs()` (по
умолчанию 500; 0 — по записи на действие, так работают тесты кистей).
Всё состояние истории (стек, pending-группа, позиции) защищено
`undoMutex_`: запись/откат может идти в середине редактирования мира, и
история обязана оставаться консистентной при вызовах не только из UI-потока.
Контракт «читать/писать буферы `vMap` только в UI-потоке» при этом
не меняется.

**GUI (MainWindow).** File: Save (Ctrl+S) / Save As (Ctrl+Shift+S, имя —
диалог, папка `RESOURCE/Worlds/<имя>`, перезапись запрещена, после —
перебиндинг вьюпорта); Edit: Undo (Ctrl+Z) / Redo (Ctrl+Y) / Clear Undo
History. Доступность кнопок/действий пересчитывается во всех изменениях
состояния сессии. Диалог «несохранённые изменения» (Save/Discard/Cancel)
показывается перед загрузкой/выгрузкой мира и закрытием окна
(`closeEvent`).

Общий рендер-хелпер `renderMapToBgr()` используется обоими генераторами и
растеризует через `ViewportRenderer` (свежий экземпляр с дефолтными
настройками), чтобы `cache.tga`, `map.tga` и экранное окно не могли разойтись
ни в одном пикселе.

## 5. `ViewportRenderer` — растр 1:1-вьюпорта (T2.1)

`core/ViewportRenderer.{h,cpp}` (без Qt) — программный растеризатор вида
сверху 1:1 с кэшем и грязными прямоугольниками.

**Кэш.** `std::vector<uint32_t>`, попиксельно `0xFFRRGGBB`, `H_SIZE×V_SIZE`
построчно. Раскладка совпадает с `QImage::Format_ARGB32`, поэтому виджет (T2.2)
обернёт буфер zero-copy, а сам `MapEditorCore` остаётся без Qt и
тестируется headless — это осознанное уточнение плана §3.4 («кэш в `QImage`»).

**Конвейер `update()`** (безопасно звать каждый кадр):

1. `vMap.renderQuant()` — пересчёт освещения (`RnrBuf`/`At_SHADOW`) для областей,
   помеченных `regRender()`; очищает `vMap.renderAreas`;
2. сборка прямоугольников: полная карта после `bindWorld()`/смены
   фильтра/оверлеев, иначе боксы из `vMap.changedAreas`; список
   `changedAreas` очищается (тот же consume-и-clear-контракт, что у
   `terUniverse::quant()` в игре);
3. перерисовка боксов в кэш; возврат перерисованных `DirtyRect`
   (координаты — ячейки, `x/y/w/h`, в отличие от включительных `dx/dy` у
   `sRectS`). Пустой вектор = «ничего не изменилось».

Цвет базового слоя — редакторская обёртка `color32WithLighting()` над
`vrtMap::getColor32()`: ветка `At_LEVELED` (включая `At_ZEROPLAST`) через
смесь `Tex2Col32[LvdTex]` + `Sur2Col32`, обычный рельеф — `Sur2Col32`.
Намеренное отличие от `getColor32()`: клетки `At_ZEROPLAST` НЕ идут через
`SurZP2Col32` (синий тинт нулевого слоя) — в игре он приходит из 3D-сцены
(`SetZeroplastColor`) и виден только в поле запитанного ядра, которого в
редакторе нет (docs/context.md). Chunky-3D (`viewV2D`, Terra не трогаем)
решается демотированием зеропластовых клеток в простой `At_LEVELED` на время
прохода рендера (`View3DRenderer::render`, восстановление байт в байт).
`bindWorld()` предполагает
загруженный и освещённый мир (п.5 `loadWorld()`); вызов без него откажется.

**Фильтры слоя** (`LayerFilter`):

| Фильтр | Поведение |
|---|---|
| `Composite` | точь-в-точь `getColor32()` |
| `Geo` | цвет считается с освещением `RnrBuf & 0x7F` (гео-половина таблиц): бит 7 `RnrBuf` — признак дамбы, он переключает строки 128..255 палитры на `DamPal`, а `SurBuf` хранит общий индекс материала для обеих палитр (`PutAltDam` вообще не трогает `SurBuf`) — поэтому под дамбой гео-цвет восстанавливается точно, без аппроксимации |
| `Dam` | дамбовые ячейки — как есть, без дамбы — затемнены до 25% (`dimColor`) |

**Оверлеи** (`OverlayFlags`, поверх любого фильтра, по флагам 4×4-блока
`GABuf`): зеропласт — сильный (`GRIDAT_ZEROPLAST`, α 96) / слабый
(`GRIDAT_ZEROPLAST_IS_PRESENT`, α 40, приоритетнее «выровнено»), «выровнено»
(`GRIDAT_LEVELED`, зелёный α 72), некопаемость — красный, сила по
`GRIDAT_MASK_HARDNESS` (0 — максимум, 3 — без тинта; см. семантику в
`docs/context.md`). Палитры тинтов/альфы — публичные константы класса:
контракт, который переиспользуют тесты; `blendTint()`/`dimColor()` —
`constexpr`-стatische, тот же канал-в-канал расчёт.

Смена фильтра/оверлеев помечает всю карту; `renderMapToBgr()` (T1.3) растеризует
через этот же класс, см. §4.

## 5.5. `ViewportWidget` — Qt-виджет вьюпорта (T2.2)

`ui/ViewportWidget.{h,cpp}` — наследник `QWidget`, отображает растр
`ViewportRenderer` и добавляет навигацию/оверлеи.

**Zero-copy QImage.** `drawBaseRaster()` оборачивает `uint32_t*` кэш
`ViewportRenderer` в `QImage` с тем же layout (`Format_ARGB32`, row-major) и
рисует одним вызовом `painter.drawImage(targetRect, image, sourceRect)`. Ни одной
дополнительной копии памяти — это критично для карт 2048². Включение
`SmoothPixmapTransform` зависит от выбранного стиля рендера — см. §5.6.

**Диапазон зума «1:1…fit».** В стиле Chunky `zoom_` климпуется в
`[fitScale_, 1.0]`; в стиле Smooth верхняя граница поднимается до 4:1
(см. §5.6).
`fitScale_` вычисляется в `resizeEvent` как `min(viewW/mapW, viewH/mapH)`
с отступом 12 px. `zoomToFit()` центрирует карту и ставит zoom на `fitScale_`;
двойной клик — тоже. Колесо мыши меняет zoom с шагом 1.25, центрируя на
координатах курсора.

**Панорамирование.** Средняя и правая кнопки мыши — перетаскивание.

**Сетка.** Два уровня: тонкая (шаг `kFineGridCell = 4`, соответствует `kmGrid` из
`terra.h`/`VMAP.h`) рисуется только когда расстояние между линиями ≥ 4 px;
грубая (шаг `kCoarseGridCell = 64`, соответствует `kmGridChA`) — всегда.
Линии выравниваются по началу сетки (divisible by step), а не по видимому
диапазону, чтобы избежать смещения.

**Превью кисти.** Жёлтый пунктирный контур (круг/квадрат) размером `brushRadius_ * zoom_`,
центрированный на ячейке под курсором. Видимость управляется из панели инструментов (T3).

**Координаты курсора.** `mouseMoveEvent` конвертирует экранные координаты в
карту (`screenToMap`), эмитит `cursorMapPosition(mapX, mapY)` — `MainWindow`
показывает их в статус-баре. В правом нижнем углу вьюпорта — HUD с
координатами и текущим зумом.

**Спавны.** `drawSpawnPoints()` / `drawSpawnPoints3D()` рисуют цветные
кольца (2D) и диски на рельефе (3D). Данные подаются из T8 — виджет только
рендерит.

**Порядок отрисовки в `paintEvent()`:** (1) `renderer_->update()` — слить
грязные прямоугольники и пересчитать освещение; (2) фон; (3) растр;
(4) сетка; (5) превью кисти; (6) спавны; (7) HUD.

## 5.6. Стили рендера: Chunky / Smooth (фикс «блочного» вида, post-T3.3)

**Проблема.** Растр мира — один цвет на ячейку (`getColor32`). После загрузки
мира `zoomToFit()` для небольших карт даёт `fitScale_ > 1.0` (карта меньше
окна), а `clampZoom()` ограничивал зум диапазоном «1:1…fit» сверху единицей,
поэтому карта рисовалась nearest-neighbor'ом на увеличении — крупные
квадратные блоки. В игре те же данные выглядят гладко: движок заливает
текстуру тайлов тем же `getColor32` по ячейке (`Source/Game/CopyToGraph.cpp`,
`GetTileColor`), но GPU семплирует её билинейно, и рельеф — интерполированный
меш (`TileMapBumpTile` берёт высоты `TerraInterface::GetZf` = `SGetAlt`).
Редактор же показывал дискретные ячейки без фильтрации.

**Решение — переключатель стиля, а не замена вида.** В `ViewportWidget`
появился `RenderStyle { Chunky, Smooth }` (по умолчанию — Smooth):

- **Chunky** — прежнее поведение: solid-блоки ячеек, верхняя граница зума
  1:1 (даже если для мелкой карты `fitScale_` больше 1 — картинка остаётся
  блочной), 3D-кадр `View3DRenderer` растягивается без фильтра.
- **Smooth** — (`SmoothPixmapTransform`) билинейная фильтрация растра
  (эквивалент GPU-фильтрации текстуры рельефа в игре); зум в 2D допускается
  выше 1:1 — до `kMaxSmoothZoom = 4.0`, но не меньше масштаба «вписать
  карту» (`max(fitScale_, kMaxSmoothZoom)`, иначе для мелких миров кап
  отменял бы `zoomToFit()`); 3D-кадр растягивается билинейно, как и
  раньше (T2.3).

**Реализация.** Интерполяция делается в момент отрисовки самим Qt — ядро
(`ViewportRenderer`) не менялось: кэш 1 цвет/ячейку остаётся источником
правды для кистей/пипетки/оверлеев, а стиль — чисто свойство Qt-виджета.
`clampZoom()` учитывает стиль (верхняя граница 1.0 или `kMaxSmoothZoom`);
`setRenderStyle()` при переходе в Chunky возвращает zoom в диапазон, сохраняя
ячейку под центром виджета как точку опоры (тот же приём, что в `zoomStep`).

**GUI (MainWindow).** Пара взаимоисключающих кнопок `actChunkyRender_` /
`actSmoothRender_` в меню View (после «3D View», с разделителем) и в тулбаре
рядом с переключателем 2D/3D; иконки рисуются программно
(`makeChunkyIcon` — 2×2 solid-блока, `makeSmoothIcon` — та же сетка с
размытыми/градиентными краями). Обратная синхронизация кнопок — через
`ViewportWidget::renderStyleChanged` (коннект в `buildViewport()`, т.к. меню
строятся раньше вьюпорта).

## 5.7. `View3DRenderer` — наклонный 3D-вид (T2.3)

`core/View3DRenderer.{h,cpp}` (без Qt) — тонкая обёртка над `vrtMap::viewV2D`
(`Source/Terra/VMAP.cpp`): живой код Terra рисует объёмную карту сам, класс
только подготавливает параметры камеры и отдаёт готовый RGB565-буфер.

**Параметры камеры** (`View3DCamera`, всё в удобных единицах — градусы и
клетки):

| Поле | Смысл | Диапазон |
|---|---|---|
| `rotationDeg` | поворот вокруг Z (`turnAngleAroundZ`) | [0°, 360°) |
| `tiltDeg` | наклон камеры (`cameraAngleLean`) | инвертируется в `lean` |
| `liftCells` | высота камеры (`cameraDZ`) | `MIN/MAX_CAMERADZ_VX_WINDOW` |
| `focusCells` | «зум» (`focusC`) | [150, 8000] |

`lean` в `vrtMap` — целочисленный член; для его защиты от сингулярности в
`viewV2D` (деление на `d0 = |tan(lean)|*focusC`, когда сканируемые
дальностные радиусы попадают внутрь `[0, d0)`) служит
`stableLeanDeg(lean, focusC, yside)`: он отодвигает угол от вертикали так,
чтобы `d0` вышла за пределы сканируемого диапазона. `focusC` климпуется в
[150, 8000] — интервал, с которым `viewV2D` работает стабильно.

**Буфер.** Рендер `viewV2D` пишет RGB565 (`ColorsHalfType`), поэтому буфер
`View3DRenderer` объявлен как `ColorsHalfType` (uint16_t): раскладка
совпадает с `QImage::Format_RGB16`, виджет оборачивает его zero-copy —
зеркальное решение аргументации T2.1 (ARGB32 ↔ `Format_ARGB32`). Ширина
окна ограничена `MAX_XSIZE_VX_WINDOW` (640), массивы примера
`example_vx_window` уже статические, поэтому размер окна климпуется
`≤ 640×640`.

**Базис поворота.** `viewV2D` сканирует «трубу» перед камерой по клеткам;
направление «вперёд» при повороте `θ: (sin θ, −cos θ)` — это следует из
формул внутри `viewV2D`; панорамирование в виджете использует этот же базис
(вправо/влево от камеры = перпендикуляр).

### 5.7.1. Smooth 3D-вид: mip-пирамида вместо точечной выборки (post-T3.3)

Дальняя часть чанки-рендера «блочит» не из-за отсутствия биленейной
высоты (высота в `viewV2D` и так интерполируется), а из-за **минификации с
точечной выборкой**: на каждый экранный столбец берётся одна клетка, а у
горизонта один пиксель покрывает десятки клеток (у углов карты до
~30–60 кл/пкс) — классический алиасинг уменьшения.GPU-рендер игры решает
это mip-маппингом; в редакторе проблему закрыла mip-пирамида
`core/ColorMipmap.{h,cpp}`:

* **Данные.** Пирамида лежит в `ViewportRenderer` (ленивая, строится
  `ensureMips()` при первом Smooth 3D-рендере) и хранит те каналы, которые
  читает `viewV2D`: цвет уровня 0 = чистый composite (`vrtMap::getColor32`,
  без оверлеев и без фильтров слоёв — он же `Sur2Col32[sur][rnr]`, но
  клетки с At_LEVELED/At_ZEROPLAST получают свои ветки таблиц, т.е. на
  Smooth-пути такие поверхности чуть плавнее, чем прямой `Sur2Col`
  чанки-пути), и эффективная высота (VxD, иначе VxG). Уровни ≥ 1 —
  округлённые средние 2×2 вниз по цепочке; обновление инкрементальное по
  dirty-прямоугольникам вместе с обычным repaint (`renderRect` →
  `refreshMipRegion`), полная перестройка — при bind/invalidate/подмене
  мира.
* **Выборка.** `View3DRenderer::renderSmooth` проходит ту же проекцию, что
  `viewV2D` (формулыdy/dx/поворота скопированы дословно — геометрия обоих
  стилей совпадает), но метод выборки — GPU-подобный:
  - **Уровень дробный.** На строку берётся `floor(log2(наземного следа))`
    (максимум из |sx| вдоль строки и |DY(d+1)−DY| вперёд) с долей как
    трилинейным весом к следующему более грубому уровню — соседние строки
    меняют ядро непрерывно; дискретные уровни на строку рисовали «кольца»
    вокруг дальних гор.
  - **Глубина попиксельно.** Полоса строки красится не одним цветом
    семпла P(d), а линейным переходом между якорями: P(d) внизу полосы
    (экранная строка y(d)) и P(d−1) наверху (y(d−1)) — обратная проекция
    (un-projection) каждого экранного пикселя на землю между якорями.
    Соседние полосы стыкуются непрерывно (верх соседней = низ текущей
    ≈ P(d)), и глубинный профиль дальних склонов перестаёт выглядеть
    «слоями кусков». Подшаговые по глубине строки (|ΔDY| < клетки)
    семплируют только текущую позицию.
  - **Высоты усредняются по глубине** (h(P(d)) с h(P(d−1))) — силуэты
    дальних строений/террас тоже фильтруются. Высоты/цвета на грубых
    уровнях ядерно усреднены; уровень 0 с нулевыми дробями даёт ровно те
    же значения таблиц и той же точности биленейную высоту, что и
    `viewV2D` (проверяется тестом bit-exact паритета на выровненном мире).
  Нюанс следа вперёд: для строк с отрицательным d основной цикл инвертирует
  знак DY (земля «позади/под» камерой, рисующая нижнюю половину кадра), и
  DY(d+1) обязан получить ту же инверсию — иначе |DY(d+1)−DY| вырождается в
  ≈ 2·|DY|, нижняя половина кадра уходит на самые грубые уровни пирамиды и
  превращается в одноцветное пятно (регрессия поймана и закрыта; тест
  «Smooth 3D near field» держит её на реальном рельефе).
* **Модификация Terra не требуется** — чанки-путь остаётся «как был»
  (Terra `viewV2D` не тронут), smooth — полностью сторона редактора.

## 5.8. 3D-режим в `ViewportWidget` + панель View (T2.3, GUI)

**ViewMode.** `ViewportWidget` имеет `ViewMode { TopDown, Oblique }`;
переключение (`setViewMode`) эмитит `viewModeChanged`. В Oblique виджет:

- оборачивает буфер `View3DRenderer` в `QImage::Format_RGB16` и рисует его
  целиком (базовая растеризация без зум-трансформаций — масштаб задаёт
  камера через `focusC`);
- правая/средняя кнопка — панорамирование по плоскости земли
  (`panObliqueBy`): сдвиг считается в клетках через базис камеры, затем
  переносится в `vMap.viewX/viewY`;
- левая кнопка — орбита (drag меняет поворот/наклон);
- колесо — зум `focusC` (шаг 10%);
- навигационные клавиши 2D-режима в 3D отключаются — камера в 3D
  самодостаточный навигатор.

**Панель View + меню.** `MainWindow::buildViewToolbar()` создаёт действия:
F9 — переключение 2D/3D, Ctrl+←/→ — поворот ±15°, Ctrl+↑/↓ — наклон ±5°,
PageUp/PageDown — подъём камеры ±100, Ctrl+= / Ctrl+- — зум, Ctrl+Home —
сброс камеры. Иконки нарисованы программно (`makeRotateIcon` и т.п.,
QPainter-дуги) — намеренно без `QPixmap::transformed`, который в связке с
QTransform вызывал падение CRT (см. `docs/context.md`). Живой QLabel в
панели показывает текущие значения (rot/tilt/lift/focus) и обновляется при
каждом изменении камеры.

## 5.9. Миникарта + прямоугольник вида (T2.4)

**Источники изображения.** `MinimapWidget` (dock-панель `MainWindow`, справа,
по умолчанию видима; переключается из меню View, клавиша M) показывает
`map.tga` текущего мира — тот же файл, что читает шелл игры; перечитывается
после `saveWorld()` (файл регенерируется при сохранении) и при загрузке мира.
Если `map.tga` отсутствует или не читается (свежий/сохранённый без него
мир) — панель рендерит живой растр через `WorldImages::renderMinimapToBgr()`
в тот же размер, что `generateMapTga()` пишет в файл (не более
`kMinimapMaxSize`), т.е. тот же пиксельный источник, что и кэш вьюпорта
(`getColor32`, Composite, без оверлеев). Сам метод никогда не трогает Terra:
пакеты `WorldImages` (core, без Qt — TGA чтение/запись, даунскейл, генераторы
`cache.tga`/`map.tga`) переехали туда из `EditorSession` и переиспользуются
конвейером сохранения, поэтому сохраняемые файлы и миникарта не могут
разойтись.

**Живое обновление правками.** `map.tga` описывает последнее сохранение, поэтому
штамп кисти, undo/redo, импорт картинки и правка палитры в файле не видны, а
панель раньше молча оставалась старой. `ViewportWidget::paintGL()` эмитит
`terrainRepainted()`, когда `renderer_->update()` вернул непустой список
прямоугольников, — т.е. после того как `vMap.renderQuant()` пересчитал свет
затронутых клеток; `MainWindow::buildMinimapDock()` соединяет сигнал с
`MinimapWidget::refreshFromLiveTerrain()`, который досэмплирует весь обзор из
живых буферов тем же `renderMinimapToBgr()` и помечает GL-текстуру устаревшей.
Панель перебирается только при `session_->hasUnsavedChanges()`: репейн кэша
после загрузки мира или смены фильтра слоёв правкой не считается и не должен
затирать ручную картинку радара. Сэмпл одной клетки — статический
`ViewportRenderer::compositeColorAt()`: он отдаёт ровно тот же пиксель, что
Composite-ветка `colorAt()`, и не заводит второй полноразмерный кэш, потому что
`bindWorld()` опустошил бы `vMap.changedAreas` и оставил вьюпорт без его
грязных прямоугольников.

**Прямоугольник вида.** `ViewportWidget::currentViewRect()` — видимая область
карты в клетках: в TopDown это точный `visibleCellRange()`; в Oblique —
аппроксимация следа 3D-окна на земле (основание `viewV2D`: ширина ≈
окно × `(focusC+cameraDZ)/focusC`, глубина — через наклонный kv-коэффициент
`panObliqueBy`, после клипа по карте). Виджет эмитит `viewRectChanged`
после каждой отрисовки, где прямоугольник изменился (пан/зум/орбита/
переключение режима/resize/загрузка мира), — миникарта подписана на сигнал
и рисует жёлтую рамку. Клик по миникарте → `ViewportWidget::centerOnCell()`
(центрирует 2D-вид либо переносит 3D-`obliqueCenter_`).

## 5.10. Кисти — каркас (T3.1)

`core/BrushTool.{h,cpp}` (без Qt) — каркас для всех T3.x-инструментов:
`BrushParams{shape, radius, strength, mode(Geo/Dam), colorIndex, effect,
direction, thickness}` + генераторы масок `BrushMasks` + одна точка применения
`BrushTool::apply()`.

**Формы масок** (`BrushMask` — bbox-офсет относительно центра штампа +
`uint8 influence[0..255]` на клетку; частичные влияния появятся в T3.5):

| Форма | Геометрия |
|---|---|
| `FilledCircle` | все клетки с `ring(dx,dy) ≤ r` — то же множество, что штампует `influenceDZ` |
| `CircleOutline` | кольцо-полоса `ring ∈ [r-t+1, r]` — при `t=1` ровно смещения собственных радиусных таблиц Terra `maxRad[xRad[r]/yRad[r]]` |
| `FilledSquare`/`SquareOutline` | `|dx|,|dy| ≤ r` / полоса `max(|dx|,|dy|) ∈ [r-t+1, r]` |
| `Line` | Брезенхэм от (x0,y0) до (x1,y1) со штампом-кругом радиуса `lineStrokeRadius(r, t)`; каждая клетка входит в маску ровно один раз (перекрытия штампов не суммируются) |

**Толщина штриха (`BrushParams::thickness`).** Для НЕзаполненных форм
(`CircleOutline`, `SquareOutline`, `Line`) задаёт ширину полосы в клетках.
Полоса строится **внутрь** от внешнего края: внешний радиус остаётся `r`,
поэтому штамп физически не может выйти за пределы прежнего отпечатка формы.
`thickness = 0` — «авто», прежнее поведение (одно-клеточное кольцо/граница,
Line — штамп полного радиуса); положительные значения дают `t`-клеточную
полосу. Для `Line` эффективный радиус штампа равен `(t-1)/2` с ограничением
сверху величиной `r`, т.е. `t=1` — ровно путь Брезенхэма. Заполненные формы,
маска-картинка и Decal параметр игнорируют. UI: спинбокс в панели Brush,
активен только для незаполненных форм; предпросмотр курсора рисует
внутреннее кольцо/прямоугольник полосы.

`ring(dx,dy) = (int)sqrt(dx²+dy²)` — отбрасывающий `sqrt`, ровно тот же
округляющий расчёт, которым `vrtMap::landPrepare()` строит радиусные таблицы
(`LAND.cpp:77`), поэтому аналитические маски совпадают с таблицами Terra
клетка-в-клетку (проверено тестом 56). `sqrt` в игре — fdlibm-эквивалент
(`gamemath.h`/`std.cpp`), т.е. правильно-округлённый, как и `std::sqrt`.

**Применение** (`applyStamp`/`applyLine`/`applyMask`, один вызов = одна
undo-запись):

1. клип bbox по карте (торус не используется — как `recordUndoArea`);
2. `session.recordUndoArea(bbox)` ДО правок (план называет
   `UndoDispatcher_PutPreChangedArea`, но он пуст под `_SURMAP_` — контракт
   undo редактора описан в §4.1);
3. маршрутизация эффекта: высотные инструменты T3.2 (`ChangeHeight`,
   `Align4ZP`, `AlignVariableH`, §5.11) — каждая клетка маски проходит
   через Terra-тулзу (`individualToolzer<T2TE_*>::tVoxSet()` /
   `tVoxSetAll()`): hardness-затухание (только `ChangeHeight`), биты
   `At_*`, согласованность `VxGBuf/VxDBuf/SurBuf`
   и разделение слоёв Geo/Dam — всё это поведение самой Terra, не
   переизобретается. Дельта клетки ChangeHeight = `direction × strength` (в
   1/32 м, `<<VX_FRACTION`) × влияние маски (255 → полный дельта),
   округление по модулю; для выравнивающих инструментов знак дельты берётся
   по геометрии (к цели). Остальные эффекты (`SetColor`, `PlotZeroplast`,
   …) объявлены в `BrushEffect`, `apply()` их отвергает до
   соответствующих задач T3.3–T3.5;
4. `vMap.recalcArea2Grid(bbox±1)` + `EditorSession::regRenderWithShadowTrail(bbox±1)` — сетка и
   вьюпорт обновляются по обычной dirty-конвейерке (запас в 1 клетку, как
   у тулз игры, `tools.h:252-254`). Обёртка расширяет бокс на инкрементальный тени-след RenderStr
    западнее бокса (см. docs/context.md: тени выходят за пределы грязного
    прямоугольника; без расширения после undo/redo и кисти «lower»
    остаются чёрные полосы устаревшего освещения).

`strength` климпуется в `[1,100]`, `radius` — в `[0, MAX_RADIUS_CIRCLEARR]`,
`heightLevel` (цель `AlignVariableH`) — в `[0, MAX_VX_HEIGHT_WHOLE]`.

**GUI-интеграция.** `MainWindow` владеет одним `BrushTool` (параметры —
пока дефолт: круг r=8, поднять, strength 30%); `ViewportWidget` при
`setBrushTool()` красит по левому драгу в обоих режимах вида (штамп на каждую
новую клетку курсора), курсор — крест, `viewRectChanged`/превью работают как
раньше. Сигнал `worldEdited()` обновляет статус-бар/undo-actions. Выбор типа
кисти и режима Geo/Dam — тулбар «Brush» и подменю «Brush Type / Mode» (T3.2,
§5.11); переключение того, что делает клик (View/Brush/Eyedropper), — режимы
взаимодействия редактора (T4.2, §5.12); полноценная панель параметров
(`ToolPanel`) — задача T3.5+.

## 5.11. Кисти высоты — сглаживание/выравнивание, режимы Geo/Dam (T3.2)

Высотные эффекты перечислены в `BrushEffect`; все маршрутизируются через
Terra-тулзы без правок Terra:

| Эффект | Terra-тулза | Цель |
|---|---|---|
| `ChangeHeight` | `T2TE_CHANGING_TERRAIN_HEIGHT` | raise/lower на `direction × strength` |
| `Align4ZP` | `T2TE_ALIGNMENT_TERRAIN_4ZP` | уровень к `vMap.hZeroPlast` («выровнять относительно зеропласта»), игровой шаг `strength` за штамп, hardness игнорируется |
| `AlignVariableH` | `T2TE_ALIGNMENT_TERRAIN_VARIABLE_H` | абсолютная установка высоты `BrushParams::heightLevel` за один штамп |

**Выравнивание.** Цель (`hAppr`) синхронизируется перед КАЖДОЙ клеткой
(`setHAppoximation(целое)`): статическая тулза иначе удерживала бы
`hZeroPlast` предыдущего мира. `direction` кисти игнорируется: знак дельты
берётся по геометрии (к цели), тулза каппит результат на `hAppr` с обеих
сторон.

- **`Align4ZP`** сохраняет игровую инкрементальную семантику: модуль дельты
  — `strength-×-влияние` (`heightDeltaMagnitude`), клетки, дошедшие до цели,
  помечаются `At_LEVELED` (клетки с `At_ZEROPLAST` скипаются — поведение
  игры). Кисть НЕ учитывает `GRIDAT_MASK_HARDNESS`: используется
  `tVoxSetAll`, а не `tVoxSet`. У `tVoxSet` затухание понижения
  `dV = dV*(hardness<<hardness)/24` даёт множители 0/24, 2/24, 8/24, 24/24
  для hardness 0..3: на твёрдом грунте дамба либо не двигалась вовсе, либо
  проходила лишь часть шага, поэтому штамп по клеткам разной высоты
  оставлял их неровными и выше `hZeroPlast` (bugfix: «Set zeroplast brush
  ignores hardness»).
- **`AlignVariableH`** («Level to Height») — абсолютная установка: дельта
  клетки равна всему оставшемуся расстоянию `target − SGetAlt`, умноженному
  на влияние маски (255 → точная цель). Один штамп ставит даже сильно
  заниженный дамб/гео ровно на выбранную высоту; перекрывающиеся штампы не
  могут подняться выше цели. Используется `tVoxSetAll` (не `tVoxSet`),
  чтобы GRIDAT-затухание при понижении не оставляло клетку ниже цели.
  Тулза `T2TE_ALIGNMENT_TERRAIN_VARIABLE_H` пишет только дробные биты
  `AtrBuf` — `At_LEVELED` она не ставит.

**Режимы Geo/Dam.** Terra-тулза ChangeHeight всегда правит активный (верхний)
слой; выборка слоя редактором сделана ВОКРУГ тулзы, в `BrushTool.cpp`:

- **Geo** — на клетке без дамба правится только `VxGBuf` (порядок записи
  повторяет geo-ветку `tVoxSetAll`: `SurBuf = GetGeoType(off, v)`,
  `AtrBuf = доля`); `VxDBuf` не пишется и не создаётся.
  На клетке С дамбом колонна поднимается как единое целое: при подъёме
  гео и дамб сдвигаются вверх на одну и ту же дельту («гео остаётся
  ниже, дамбовая часть поднимается», толщина дамба сохраняется; если
  дельта не кратна вокселю, дробные биты общие и остаётся согласованной).
  Опускание — точное обращение подъёма: обе верхушки сдвигаются вниз на
  ту же дельту, поэтому пара «поднять + опустить» с теми же параметрами
  возвращает клетку байт-в-байт (клампы на границах 0..MAX ломают
  симметрию неизбежно). Поверхностное состояние верхнего слоя
  (SurBuf и дробные биты AtrBuf) на дамбовых клетках содержательно не
  переписывается: `GetGeoType` по новой
  высоте гео перекрашивал бы дамб в текстуру грунта (выглядело как
  «поднятое гео поверх дамба»), а запись дроби гео в общие биты AtrBuf
  сдвигала бы видимую высоту дамба (bugfix T3.2-ревизии);
- **Dam** — при подъёме клетки без дамба слой сеется копией текущей
  поверхности (`VxDBuf = VxGBuf`, `SurBuf = vMap.veryLightDam`) — в точности
  запись `T2TE_PLOTTING_VERY_LIGHT_DAM`; у 0-высотного гео слой сеется на
  1 воксель выше с компенсацией дельты, потому что `VxDBuf == 0` означает
  «дамба отсутствует», и сеять нулевой дамб не имеет смысла; дальше
  изменения ведёт стандартная тулза `T2TE_CHANGING_TERRAIN_HEIGHT`,
  включая снятие дамба при опускании до гео-уровня (и зачистку в него же).
  Опущение клетки без дамба в режиме Dam игнорируется (гео не трогается).

Для выравнивающих инструментов режим трактуется так же: в Geo клетки с
`VxDBuf != 0` двигают гео под дамбом через `geoAlignUnderDam` (с
ограничением «гео ≤ дамба», §5.14), в Dam дамба сначала сеется
(`seedDamLayer`), дальше работает стандартный переход слоёв самой тулзы.

`BrushTool::heightDeltaMagnitude(params, influence)` — модуль дельты
ChangeHeight и инкрементального `Align4ZP`, вынесен для тестов. Абсолютный
`AlignVariableH` его не использует: его дельта — всё оставшееся расстояние
до цели, умноженное на влияние маски. Оба выравнивающих инструмента идут
через `tVoxSetAll` (без hardness-затухания); `tVoxSet` остался только у
`ChangeHeight`.

**GUI (T3.2).** Тулбар «Brush»: 4 типа кисти (Raise/Lower/Level-4ZP/Level-H,
взаимоисключающие), спинбокс цели высоты `Level to Height` (0..255 вокселей,
активен только для `AlignVariableH`), пара режима Geo/Dam. Те же действия
дублируются в подменю Edit → «Brush Type / Mode». Все кнопки активны только
при загруженном мире, синхронизация — `syncBrushControls()`.

## 5.12. Режимы взаимодействия редактора + пипетка как тип кисти (T4.2)

Клик по миру — отдельная сущность в редакторе, ортогональная режиму вида
(2D TopDown / 3D Oblique). Описана вложенным перечислением
`ViewportWidget::EditorMode { View, Brush, Eyedropper }`
(`setEditorMode`/`editorMode()`/сигнал `editorModeChanged`):

| Режим | что делает клик/драг | камера |
|---|---|---|
| `View` (V) | левый драг — пан в TopDown / орбита в Oblique | полный контроль |
| `Brush` (T) | левый пресс/драг — штампы кисти в обоих видах (линия — двухточечный штамп) | средняя/правая — пан, колесо — зум, Alt+левый — орбита в Oblique |
| `Eyedropper` (E) | левый пресс/драг — выборка цвета из пикселя Geo/Dam | те же «ограниченные» изменения камеры, что у Brush |

Навигация доступна во всех режимах (средняя/правая пан, колесо); смена
режима сбрасывает продолжающийся жест (недокрашенный штамп — не штамп,
недовзор — не выборка). Превью штампа рисуется только в `Brush`; HUD
показывает активный режим (`View`/`Brush`/`Pipette`). Форма курсора —
крест в `Brush`/`Eyedropper`, стрелка в `View`.

**Пипетка — тип кисти в общем интерфейсе.** Сэмплирование цвета реализовано
как `BrushEffect::PickColor` в `BrushTool` (core, без Qt), а не отдельной
веткой вьюпорта: `applyStamp(..., effect = PickColor)` — точечная операция
(маска/форма/радиус не строятся, штамп = клетка курсора), читает
`vMap.SurBuf[клетка]` и кладёт индекс в `lastPickedColorIndex()` **и в
`params().colorIndex`** — выборка и кисть цвета живут в одних и тех же
параметрах, поэтому «пипетка → Paint Color» даёт тот же цвет без перезаписи.
`SurBuf` несёт индекс безотносительно выбираемой палитры, а выбор палитры
делает слой клетки-носителя (подробнее — §5.13; историческая формулировка
«0..127 — Geo, 128..255 — Dam» оказалась неверной, T4.1 перепроверил и
поведение рендера, и настоящие миры). Мир не меняется, undo-запись не
создаётся (тест 63). Вне карты/«небо» (3D-raypick промахнулся)
→ отказ (`false`). Форма `Line` отвергает `PickColor` (линия семплов не
имеет смысла).

**Стыковка режима и типа.** Eyedropper-режим вьюпорта форсирует эффект
`PickColor` при клике (`pickColorAtCell`), поэтому MainWindow держит их
в согласии при переключении в обе стороны:

- кнопка типа «Pick Color» → `params.effect = PickColor` + режим `Eyedropper`;
  любая красящая кнопка типа → режим `Brush`;
- включение режима `Eyedropper` → тип становится `PickColor`; включение
  режима `Brush` при типе `PickColor` → тип возвращается к `SetColor`
  (в `Brush`-режиме клик обязан красить).

Пипетка работает как в 2D (линейный маппинг курсора), так и в 3D
(луч-пик `View3DRenderer::pickGroundCell`) — через тот же
`cellAtWidgetPos()`, что и штампы кистей; сэмлелятся и Geo-, и Dam-пиксели
(тот, что реально отображается by SurBuf). После выборки
`onEyedropperPicked` в `MainWindow` ставит эффект `SetColor` с выбранным
индексом (кисть сразу готова красить), синхронизирует спинбокс/свотч.

**GUI.** Пара «Brush Editing»/«Eyedropper»-переключателей заменена
взаимоисключающей группой Edit → «Editor Mode» (V/T/E) и тремя кнопками в
начале тулбара «Brush»; в тулбар доплен тип «Pick Color» (иконка пипетки).
Программные смены эффекта зеркалятся в кнопки типов в `syncBrushControls()`
(эксклюзивная группа автопроверяет только триггнутые действия), состояние
кнопок режимов поддерживает слот `onEditorModeChanged` по сигналу
вьюпорта.

## 5.13. Панель палитр + редактирование RGB (T4.1)

**Модель слоёв и индексов (перепроверено по коду игры и настоящим мирам,
см. docs/context.md).** Байты `SurBuf` — общий индекс 0..255 в палитру слоя
клетки: клетки без дамбы (`VxDBuf == 0`) отображаются как
`GeoPal[SurBuf]`, дамбовые (`VxDBuf != 0`) — как `DamPal[SurBuf]`;
принадлежность слою несёт бит 7 `RnrBuf` (`RenderStr`: `0x80|light`,
LAND.cpp:1462), поэтому `convertPal2TableSurCol(DamPal, Damming)` строит
`Sur2Col32[i][j+128] = гамма(DamPal[i])` по всем 256 строкам
(VMAP.cpp:1364-1372), и `PutAltDam` не трогает `SurBuf` (рисунок дамбы
читается по тем же `SurBuf`-индексам). В шиппованных мирах дамбовые
значения `SurBuf` целиком покрывают 0..255, нижняя половина GeoPal занята,
верхняя — чёрная. Порядок байт палитр — RGB (`palBuf[i*3+0]` — красный), а
не BGR (устаревший комментарий WorldFiles.h про BGR исправлен).

**Ядро.**
- `PaletteOps::geoPalXml(GeoPal)` — сериализация гео-палитры в
  `<colorTable>` 256× `<color value='r,g,b'/>` (формат шиппованных миров);
  компоненты пишутся как `(b + 0.5)/255` — игра грузит XML
  (`loadGeoDamPal`, `_TX3D_LIBRARY_`) с обрывающей конверсией
  `unsigned char(float*255)`, и точное `b/255` может попасть ровно на
  границу обрыва (printf/atof/float); сдвиг полбайта держит каждое значение
  в середине ячейки обрыва, поэтому readback байта точный всегда.
- `EditorSession`: `paletteRgb(layer, index)` / `cellIsDam(x,y)` /
  `setPaletteRgb(layer, index, rgb)` / `applyPalettes()`
  (`convertPal2TableSurCol` обеих палитр — тот же вызов, что делает
  `loadGeoDamPal` после загрузки; пересчитывается и `veryLightDam`) +
  флаг `isPaletteModified()` вне undo-истории (входит в
  `hasUnsavedChanges()`).
- `saveWorld()`: при отредактированной палитре — Terra-пайплайн
  `saveGeoDamPal()` (inGeo.act/inDam.act) и перезапись sync-файла geoPal.xml
  (в TX-сборке игра при загрузке берёт гео-палитру ИЗ XML, так что
  .act-файлы одни не выживают до перезагрузки). Неизменённая палитра файлов
  не трогает (как с hardness.bin). `saveWorldAs` переносит правки в
  копию-приёмник до перезагрузки мира (иначе правки погибают при
  `unloadWorld()`).

**`ui/PalettePanel`** — док-панель (View → «Palette», P) из двух сеток по
256 свотчей (Geo/Dam), с скроллом; клик по свотчу → `colorSelected(index,
dam)`, двойной клик → диалог цвета → `setPaletteRgb` + `applyPalettes` →
`paletteEdited(...)`. Панель не касается Terra — только Qt-free хелперы
сессии.

**MainWindow**: док после миникарты; выбор свотча ставит кисть
(mode=слой свотча, colorIndex) и синхронизирует спинбокс/свотч кисти;
`paletteEdited` инвалидирует визуализацию целиком
(`refreshPaletteRenderers()`: `invalidateAll()` 2D-кэша +
`setNeeds3DRedraw()`, мир перекрашивается). Пипетка зеркалит выборку в
панель: мода кисти ставится по слою семплированной клетки (`cellIsDam`),
свотч подсвечивается в соответствующей сетке. Статус-бар при движении
курсора показывает `Sur: <индекс> (Geo|Dam) <rgb>` — чтение ровно как у
рендера.

**Кисть цвета и слои (T4.3).** `SetColor` красит `SurBuf` без касания
высотных буферов (VxGBuf/VxDBuf/AtrBuf), но краска учитывает слой клетки:
бит 7 `RnrBuf` несётся за `VxDBuf` на этапе рендера (LAND.cpp:1461-1462),
поэтому рендер всегда разрешает цвет клетки через палитру **её слоя** —
написание «не в том» индексе дало бы произвольный цвет чужой палитры.
Гейтинг — по клетке внутри `applyEffectToCell`: Geo-режим красит только
клетки без дамбы (`VxDBuf == 0`), Dam-режим — только уже существующие
дамбовые (`VxDBuf != 0`); кисть цвета никогда не сеет и не снимает дамбу
(создание дамбы — у `PlotZeroplast`/`VeryLightDam`). Правило работает в
обоих путях приложения (штамп и линия — общий цикл по маске). Анкоры
теста 61 ищут совпадающие однослойные заплатки возле центра карты вместо
фиксированного центра (заполнение дамбы на реальных мирах ~ половина
карты); 61.4 проверяет оба гейта (Geo на дамбе — нет, Dam на дамбе — да,
Dam на гео — нет).

## 5.14. Слияние зеропластовых кистей, Geo-режим выравнивания, маска-картинка (переработка по фидбеку)

Три изменения кистей после практической проверки T3/T4:

1. **«Level to Zeroplast» = бывший Align4ZP + PlotZeroplast.** Один тип
   кисти: выравнивание до `hZeroPlast` (T2TE_ALIGNMENT_TERRAIN_4ZP) и
   пометка достигших целевой высоты клеток `At_ZEROPLAST`
   (T2TE_PLOTTING_ZEROPLAST) в том же проходе. В Dam-режиме дамба сначала
   сеется (`seedDamLayer`, аналог T2TE_PLOTTING_VERY_LIGHT_DAM — поведение
   бывшего PlotZeroplast); клетки с уже стоящим `At_ZEROPLAST` пропускаются
   целиком, чтобы сеанс дамбы не задевал их. Отдельный тип «Plot
   Zeroplast» и `BrushEffect::PlotZeroplast` удалены.

2. **Выравнивание в Geo-режиме над дамбой.** Раньше клетки с дамбой в
   Geo-режиме пропускались («Level to Height» ничего не делал). Теперь
   `geoAlignUnderDam` двигает гео-слой к цели под дамбой с ограничением
   «гео <= дамба»; дамба (целый воксель и SurBuf) не трогается, дробные биты
   общие — как в собственной ветке понижения дамбы Terra (tVoxSetAll).
   Выравнивание в Dam-режиме поверх дамбы работает через штатный тулзер
   Terra (дамба — активный слой).

2a. **Выравнивание в Dam-режиме на гео-клетках (исправление).** Раньше
   `AlignVariableH` в Dam-режиме на клетке без дамбы (`VxDBuf == 0`) не
   сеял дамбу — тулзер Terra брал ветку `VD==0` и двигал гео, а не строил
   дамбу на выбранной высоте. Теперь перед вызовом `T2TE_ALIGNMENT_TERRAIN_VARIABLE_H`
   вызывается `seedDamLayer` (аналогично `Align4ZP` в Dam-режиме), что
   создаёт дамбу на высоте гео, после чего тулзер ведёт её к цели.
   Нюанс: при `VxGBuf == 0` (`seedDamLayer` поднимает дамбу на 1 воксель,
   `bump = 1 << VX_FRACTION`), потому что `VxDBuf == 0` семантически
   означает «дамбы нет» и нулевая клетка не может нести дамбу.

2b. **Снятие зеропласта при выравнивании дамбы (исправление).** Оба
   Terra-тулзера (`T2TE_ALIGNMENT_TERRAIN_4ZP`, `T2TE_ALIGNMENT_TERRAIN_VARIABLE_H`)
   имеют early-return gate: `if ((AtrBuf & At_ZPMASK) == At_ZEROPLAST)
   return 0` (tools.h:546, 590). Клетки с `At_ZEROPLAST` молча пропускались —
   «Level to Height» в Dam-режиме ничего не делал на зеропластовой дамбе.
   Пользовательское правило: если целевая высота кисти `heightLevel` отличается
   от `hZeroPlast`, дамба должна выровняться на эту высоту, а метка зеропласта
   сняться (клетка больше не представляет зеропласт). Теперь перед вызовом
   тулзера `AlignVariableH` в Dam-режиме, при `heightLevel != hZeroPlast`
   и `(AtrBuf & At_ZPMASK) == At_ZEROPLAST`, бит `At_ZPMASK` очищается —
   gate тулзера не срабатывает, дамба движется к цели. При `heightLevel ==
   hZeroPlast` цель совпадает с зеропластом, метка сохраняется (тулзер
   пропускает клетку, как и раньше — поведение `Align4ZP`).

3. **Картинка как маска штампа.** `BrushParams::useImageMask`: загруженная
   картинка (`BrushTool::setImageMask`) заменяет форму/радиус как геометрию
   штампа для любого эффекта; выбор формы сбрасывает флаг. Тип «Image
   Brush» и `BrushEffect::ImageBrush` удалены.

Высотный спинбокс панели — один на инструменты высоты: для Raise/Lower это
шаг за штамп (`params.strength`, 1..100 вокселей), для «Level to Height» —
целевая высота (`params.heightLevel`, 0..255); значение на экране зависит от
активного типа. Зеропластовая кисть «Level to Zeroplast» доступна только
в Dam-режиме; переключение в Geo откатывает активный зеропластовый тип
в Raise («Erase Zeroplast» удалена по фидбеку — см. контекст). Undo/Redo —
Ctrl+Z / Ctrl+R (и Ctrl+Y).

## 5.15. Опции вида по фидбеку: затемнение гео, сетка в 3D, заморозка дамбы, центр камеры

Четыре расширения вьюпорта (всё только в редакторе, Terra не тронута):

1. **Затемнение гео (игровой вид).** `ViewportRenderer::setGeoDimmed` — в
   композитном растри (2D-кэш и mip-пирамида smooth-3D) клетки без дамбы
   рисуются затемнёнными оттенками серого (luminance/2), дамбовые сохраняют
   палитру — контраст «терраформено/дикая земля» как в игре. View-menu +
   тулбар (у кнопки сетки), включено по умолчанию. Chunky-3D тоже затемняется:
   `View3DRenderer::viewV2DChunky` временно сереет гео-половины (строки
   света 0..127) 16-битных таблиц `Sur2Col`/`Tex2Col`, которые сэмплит
   `viewV2D`, и восстанавливает их байт-в-байт после кадра (Terra не
   меняется). Не влияет на генерацию `cache.tga`/`map.tga` (свой
   `ViewportRenderer` без флага).

2. **Сетка в 3D.** `View3DRenderer::drawGridOverlay(stepX, stepY, color)` —
   «прозрачная плоскость с линиями» поверх кадра: каждая линия сетки живёт на
   плоской плоскости отсчёта на высоте `hZeroPlast` (смещения OXY, без
   привязки к рельефу) и рисуется ПРЯМОЙ проекцией через ту же камеру, что
   рендерит кадр: линия проходится в координатах карты адаптивным шагом
   (цель ~несколько экранных px на сегмент), каждая точка проецируется
   инверсией строчной математики рендера (`|near| = |forward|*|cos(lean)|`,
   строка `d` — из замкнутой формы `near(d)`, колонка — линейно по
   боковому размаху строки), сегменты рисуются Брезенхэмом белым (0xFFFF)
   блоками 2x2 px. У метода нет вырожденных ориентаций: перечисление
   пересечений со строками развёртки (предыдущая попытка) не рисовало линии,
   параллельные строкам (горизонтальные карты при повороте 0, вертикальные
   при 90), и теряло их у горизонта. Область прохода — bbox видимого клина
   камеры (строки развёртки видят землю С ОБЕИХ сторон надира — нижний край
   клина имеет отрицательную прямую дистанцию); дальний край обрезается у
   горизонта (~3% от него), чтобы проход оставался ограниченным. Работает
   для обоих стилей; сетка рисывается, когда её линии разрешаются на экране
   (буферных px/клетку >= ~3). ОДНА сетка на вид (шаг — пользовательский
   W/H; фиксированная грубая 64-клеточная убрана по фидбеку — читалась как
   две наложенные сетки); переключение/смена шага ставят `needs3DRedraw_`.

3. **Редактируемый шаг сетки.** `ViewportWidget::setGridStep(w, h)` — размер
   клетки ЕДИНСТВЕННОЙ сетки в клетках карты (1..1024, по умолчанию 4 =
   `kmGrid`). Спинбоксы на View-тулбаре рядом с кнопками сетки; действуют на
   2D-линии и 3D-оверлей одновременно.

4. **Заморозка дамбы при скролле 3D.** Мир бесконечно повторяется (тор).
   `View3DRenderer::setDamFrozen` + вторая, «гео-только» mip-пирамида
   (`ViewportRenderer::ensureGeoMips`: цвета через гео-половину таблиц,
   высоты `VxGBuf`): ground-сэмплы вне реальной копии карты (unwrapped-коор-
   динаты центра камеры отслеживаются в `renderSmooth`) семплируют её —
   повторяются только гео-слой и рельеф гео, дамба остаётся в единственном
   оригинальном месте, реальный край карты виден сразу. Только smooth-стиль
   (chunky `viewV2D` не видит wrap); включение строит вторую пирамиду
   (~память первой) по требованию.

5. **Центр камеры.** `ViewportWidget::applyViewportSettings()` (setSession/
   reloadWorld после `bindWorld`) ставит look-at 3D-камеры в центр карты —
   раньше центр оставался (0,0) и 3D-вид открывался на левом верхнем углу.

## 5.16. Симметричная проекция надира (фикс анти-перспективы viewV2D)

Обнаружено на сетке 50x50 (rot 60/tilt 135/lift 100/focus 1150): линии сетки
расходятся к низу экрана и картинка несимметрична. Причина — не в сетке:
оригинальный viewV2D (Terra, SurMap-наследие; игра его не использует) ниже
точки надира (центр экрана, d=0) картырует землю через полюс near = F+Z:
дальняя земля занимает БОЛЬШЕ строк и более УЗКИЙ боковой размах —
перспектива перевёрнута на всей нижней половине кадра (и террейн, и сетка
честно это повторяли). Верхняя половина (d>0) корректна.

Фикс (только код редактора): нижняя половина — ЗЕРКАЛО верхней.
|near| = |d|(F+Z)/(d0-|d|) на обеих сторонах (d0 = |tga|F — строка
горизонта), near подписан отрицательно на обеих сторонах, поэтому боковой
размах xside(F+Z+|near|)/F растёт с дистанцией симметрично; надир в центре,
земля убегает к переднему горизонту (+d0, верх) и заднему (-d0, низ), обе
половины сжимаются с дистанцией. Строки за |d| >= d0 земли не несут (небо).
Применено в renderSmooth (ОБА стиля: chunky теперь — точечная выборка
уровня 0 той же прогулки, k0=k1=0/fW=0), pickGroundCell (обратный проход) и
drawGridOverlay (проекция сетки). Terra viewV2D остаётся только fallback-ом
без color source (легаси-геометрия; тест 66 проверяет его затемнение
таблиц). Проверка сим: перпендикулярные расстояния сетки зеркально равны на
равных дистанциях, сжимаются с дистанцией в обе стороны, отношение семейств
1.00 при rot 45; остаточные 0.85 при rot 60 — корректное ракурсное сжатие
оси глубины против боковой (как у реальной камеры).

### 5.16.1. Горизонтная дымка + кламп расстояния (фикс «коричневого низа», XELA rot 210/tilt 185/focus 150)

При малом фокусе горизонт входит в кадр: у краёв кадра расстояние до
грунта взлетает до тысяч клеток, пиксель покрывает сотни клеток, и кадр
стягивался в плоскую кашу среднего цвета (у XELA — грязно-коричневый),
плюс у самого горизонта DY = near·sqrt(1+tga²)·65536 переполнял int32
(наследие viewV2D) — мусорные якоря и сорванный mip-уровень. Фикс в
`renderSmooth`: near клампится в `32000/sqrt(1+tga²)` (int-безопасность,
тот же кламп в `pickGroundCell`), строки с истинным расстоянием больше
клампа гасятся в цвет неба полностью, а строки с footprint > 24 клеток/
пиксель плавно гасятся (smoothstep, full при 144) — симметрично с обеих
сторон кадра. Обычный зум (focus ≥ 600) footprint-порога не достигает и
не меняется вовсе (тесты 76–77: регрессия на камере отчёта + защита
дефолтного вида). Terra не тронута; viewV2D-fallback (без источника
цвета) ведёт себя как раньше.

## 5.17. Параметры мира — `WorldParams` + `WorldSettingsDialog` (T5.1)

`core/WorldParams.{h,cpp}` (без Qt) — снапшот параметров мира, разбросанных
по трём местам:

- `world.ini [Global Parameters]` — `hZeroPlast` и степени генерации
  (GeoNet/Section/MinimalSquare). Для загруженного мира степени пишутся
  **только в ini**: буферы выделены под размеры, действующие на момент
  загрузки; новые значения вступают в силу при перезагрузке мира или при
  генерации рельефа. `hZeroPlast`, наоборот, применяется в живую
  (`vMap.hZeroPlast`, пометка modified) — от него зависят зеропластовые
  кисти и опорная плоскость 3D-сетки. Найденный квирк Terra (не чиним,
  см. docs/context.md): `analyzeINI` читает `Minimal Square Power` в
  `MINSQUARE`, но `setupGeneralVariable()` затирает его из
  `MINSQUARE_POWER`, который из ini никогда не читается.
- `[Storage]` / заголовок `output.vmp` — сжатие S2T0/S2T1. Игра определяет
  формат по 4-байтовому id в заголовке файла, ключ в ini — документация.
  `save3Buf()` всегда пишет S2T0, поэтому сессия хранит целевой формат
  (`vmpCompressionTarget_`, инициализируется с заголовка файла при
  загрузке) и после каждого `save3Buf()` конвертирует файл заново
  (`EditorSession::saveWorld`). Конвертация — `convertVmpCompression()`,
  однозаголовочная копия `vrtMap::compressWorlds` на тех же
  `XBuffer::compress/uncompress` (та делает это для всех миров сразу и
  завершается через `ErrH.Abort`). `currentWorldParams()` берёт формат
  из реального заголовка файла.
- `[3DF Parameters]` — масштаб гео-шума kmx/kmy/kmz и легаси-индекс
  функции. Применяются в живую (`f3d.setKM`/`setFunction`) и пишутся
  Terra'овским же `f3d.saveVariable()` (текущий мир, content root).
- `Perimeter.ini [TD] Color ZeroLayer` — общая для всей установки игры
  окраска зеропласта; отсутствующий ключ = встроенные значения игры
  (1 11 51 70). Пишется в файл игры сразу при применении
  (`writeZeroLayerColor`, IniDocument — с сохранением байтов остального
  файла) плюс в `vMap.colZeroPlast`; вне конвейера сохранения мира.

Размер карты в диалоге для загруженного мира read-only (буферы уже
выделены); режим `Mode::NewWorld` с редактируемыми степенями и высотой
гео-слоя (< hZeroPlast, заливается вокселями при создании) переиспользует
мастер нового мира (T5.2). Диалог включён в File-меню
(«World Parameters...»), активен при загруженном мире.

## 5.18. Мастер нового мира — `WorldCreation` + `NewWorldWizard` (T5.2)

`core/WorldCreation.{h,cpp}` — `createNewWorld(session, params, template)`:
- **Шаблон** — существующий мир той же установки: из него копируются
  обязательные `inGeo.act`/`inDam.act`/`geoPal.xml`/`geoTx.xml`/
  `leveledSurfaceTexture.tga` и опциональные `geoLattice.bin`/`map.tga`/
  `up.tga`; `world.ini` копируется целиком и переписывается значениями
  мастера (Global Parameters, Storage, 3DF) — секции рендера шаблона
  (`[Rendering Parameters]`, `[Dynamic Palette]`, …) выживают нетронутыми.
- **Плоский режим** — редактор сам пишет S2T0 `output.vmp` (VxG = высота
  гео-слоя везде, VxD/Atr/Sur = 0, заголовок с нулями в NX/NY), после
  загрузки поверхность перекрашивается `f3d.recalcWorld()` (SurBuf из
  гео-шума; indexedTexture уже загружен fullLoad) и мир перерендеривается
  `WorldRender()`. **Генерация** — папка остаётся без `output.vmp`, и
  загрузчик сам вызывает `vrtMap::buildWorld()` (путь `selectUsedWorld`;
  `LoadVPR` отсутствие `output.vpr` обрабатывает, `output.vsc` не нужен —
  в COMPASS его тоже нет).
- После создания мир загружается сессией и один раз сохраняется —
  `cache.tga`/`map.tga` существуют с рождения; целевое сжатие применяется
  через `applyWorldSettings`. Ошибки (имя, существование, нехватка файлов
  шаблона) возвращают `WorldCreateResult.error` и подчищают папку.
- UI — `ui/NewWorldWizard.{h,cpp}` (QWizard: имя+шаблон → рельеф →
  параметры); страница параметров переиспользует `WorldSettingsPanel`
  (вынесен из диалога T5.1) в режиме `NewWorld`; дефолт значений берётся
  из шаблонного мира.

## 5.19. Изображения — импорт/экспорт (T6)

`cache.tga`/`map.tga` генерируются при каждом сохранении с T1.3
(`WorldImages::generateCacheTga/generateMapTga` через общий `renderToBgr`,
так что файлы и вьюпорт пиксельно совпадают). Новое в T6:

- **up.tga** (T6.1) — эталонный формат shipped-миров: 24-бит несжатый
  TGA 512×512, top-left (`WorldImages::kUpTgaSize`). Игровым кодом не
  читается. UI (`MainWindow::onActionImportUpTga`) грузит любой
  QImage-формат, скейлит Qt-smooth до 512², переводит RGB888→BGR и пишет
  `WorldImages::writeUpTga`; при сохранении не трогается.
- **Экспорт** (T6.2) — `exportHeightmapTga` (8-бит серый TGA, тип 3,
  `SGetAlt >> VX_FRACTION` — дамба приоритетна, как на видимой
  поверхности) и `exportTopViewTga` (растр вьюпорта в 24-бит TGA).
- **Импорт на карту** (T6.3) — `EditorSession::importSurfaceImageRgb`/
  `importSurfaceImageIndexed`: картинка сэмплится nearest в клетки карты
  (UI скейлит QImage заранее — smooth), каждая клетка получает индекс
  палитры СВОЕГО слоя (GeoPal/DamPal, гейт T4.3); чекбоксы «красить
  гео/дамбу» в диалоге опций. Indexed TGA (тип 1, несжатый — читатель
  `WorldImages::readIndexedTga`, палитра ре-базится на CMapStart) пишет
  индексы в SurBuf как есть. Вся карта — один undo-шаг
  (`recordUndoArea(0,0,H,V)`), затем `regRenderWithShadowTrail` по всей
  карте. Фильтры SurMap по высоте/цвету не переносились (гео/дамба-гейт
  покрывает редакторские сценарии).
- **leveledSurfaceTexture.tga** (T6.4) — UI читает TGA в байты, валидирует
  `WorldFiles::validateLeveledTexture` (правила `loadLeveledTexture`),
  пишет `writeLeveledTexture` и живо перегружает текстуру в загруженный
  мир (`EditorSession::reloadLeveledTextureLive` = del+load), после чего
  3D-перерисовка показывает её без перезагрузки мира.

## 5.21. Боевые карты `.spg` — XPrmDocument/SpgFile + панель (T8)

- **`core/spg/XPrmDocument`** — байт-сохраняющий DOM XPrm-текста
  (решение против зеркальных структур — см. docs/context.md): каждый узел
  хранит исходный слайс + терминаторы + промежутки; незатронутый файл
  воспроизводится байт-в-байт (тест 70 это доказывает на COMPASS.spg),
  редактируется только изменённое значение. Поля-потомки при редактировании
  пересчитывают цепочку `hasEdits()` до корня блока.
- **`core/spg/SpgFile`** — схемный слой: worldName/playersData/
  playersShufflingIndices/zeroLayerHeight; группы спавна игрока (frame +
  squad + stablePosition + frameSlots + камеры) двигаются вместе
  (`setPlayerAnchor`), dz передаёт вызывающий (дельта высот рельефа —
  `EditorSession::terrainHeightAt`); `setPlayerCount` клонирует/удаляет
  элементы массивов с перенумерацией playerID (T8.4). Переезды спавнов
  бывают undoable: `setPlayerAnchorUndoable` пишет дельту в per-document
  историю (`undoPlayerMove`/`redoPlayerMove` применяют ∓дельту — round-trip
  точен, без перезаписи абсолютов; redo-хвост отбрасывается новым ходом,
  `load()` историю чистит).
- **UI** — `ui/BattleMapPanel` (док, клавиша B): список игроков, Go To,
  Move to View Centre (z-коррекция), Edit Properties (playersData +
  Location X/Y), New Battle Map (шаблон из RESOURCE/Battle + число игроков +
  спавны по эллипсу, zeroLayerHeight из мира). Файл-меню: Open Battle Map
  (автосмена мира по worldName), Save/Save As (Battle/Worlds, предупреждение
  о перезаписи; `.gmp`/`.dat` не читаются и не пишутся). Оверлей спавнов —
  `ViewportWidget::setSpawnPoints` (T2.2-хук).
- **Place Spawn** — четвёртый editor-mode виджета (`ViewportWidget::
  EditorMode::PlaceSpawn`, кнопка на тулбаре Brush рядом с View/Brush/
  Eyedropper, клавиша `S`): клик эмитит `spawnPlacementRequested(x, y)`,
  вьюпорт мир/`.spg сам не трогает; `MainWindow::onSpawnPlacementRequested`
  двигает спавн ВЫБРАННОГО в панели игрока через
  `SpgFile::setPlayerAnchorUndoable` (та же z-коррекция по рельефу, клик по
  текущей клетке — no-op), после чего `BattleMapPanel::refresh()` +
  `syncSpawnOverlay()`. Режим включён только при загруженной боевой карте
  (`updateActionStates` его гасит и сбрасывает на Brush при закрытии карты).
  Undo/redo общие с террейном: `onActionUndo/Redo` сначала спрашивают
  террейн-историю, при пустой — историю переездов спавнов (две независимые
  стеки, порядок LIFO внутри каждой; см. docs/context.md).

## 5.23. GPU-режим Oblique-вида: TerrainGpuView + sokol (post-plan)

Пост-плановая миграция Oblique-вида с софтверного `View3DRenderer` (voxel-окно,
CPU-пиксели) на игровой sokol-рендер. TopDown-вид и `MinimapWidget` остаются на
точных CPU-пикселях (`QOpenGLTextureBlitter`), оверлеи — по-прежнему QPainter.
Если GL 4.1/sokol недоступны (ANGLE, старый драйвер, сборка без
`OPTION_SOKOL`) — автоматический фолбэк на прежний CPU-рендер.

### Таргет `MapEditorRender` и линковка (CMakeLists.txt)

* Источники: неизменённые не-D3D9-исходники `Source/Render` (src/client/
  tracker/tilemap/gemsiii/saver + sokol/*.cpp), fetched imgui core +
  `imgui_impl_opengl3.cpp`, и редакторские `render/EditorSokolDevice.cpp`,
  `render/EditorTerraInterface.cpp`, `render/TerrainGpuView.cpp`.
* Define `SOKOL_GLCORE`. MSVC: `/UPERIMETER_D3D9` через AdditionalOptions —
  `/U` попадает в командную строку после корневых `/D`, поэтому унаследованный
  `PERIMETER_D3D9` надёжно вычитывается (в логе видно предупреждение D9025 —
  это подтверждение работы трюка). Остальные определения (`PERIMETER_SOKOL`,
  `_PERIMETER_`, `_TX3D_LIBRARY_`...) наследуются от корня как в игре.
* `map_editor` линкует `MapEditorRender` и получает `MAP_EDITOR_GPU_VIEW=1`;
  без таргета виджет собирается с инертным стабом `TerrainGpuView` (тот же
  интерфейс, `init()` возвращает false).
* Игровые библиотеки `Render`/`RenderSokol`/`PluginMAX`/`HT` НЕ линкуются —
  на Windows они собраны с D3D9/D3D11 и клэшат с шимами (`logicRND`,
  `ZIPStream`, ...). Недостающие символы стека закрыты стабами в
  `shim/game_stubs.cpp`: `MTConfig::multithreading/setMultithreading`
  (HT не линкуется; редактор однопоточен, `MT_IS_GRAPH()` > true),
  `hWndVisGeneric`, и ПлагMAX-символы, на которые ссылается `ObjLibrary::LoadM3D`
  (`ZIPIsOpen`, `cMeshFile::*`, `cMeshScene::Read`, `sSubTexmap::Release` —
  редактор 3D-модели не грузит). Плюс линк `SDL2_image` (игровой `FileImage`
  зовёт `IMG_*`).

### MSVC: доступ члена в mangled-имени (shim/render_msvc_access.h)

MSVC кодирует доступ (private 'A', protected 'P', public 'Q') в mangled-имени
метода. Хак `#define private public` в `EditorSokolDevice.cpp` делает
обращения к приватным членам `cSokolRender` публичными (Q...), а определения в
sokol-*.cpp остаются приватными (A...) — LNK2019. Решение: каждый TU таргета
компилируется с forced include `/FI shim/render_msvc_access.h`
(push_macro + `#define private/protected public`), плюс
`_ALLOW_KEYWORD_MACROS` — иначе xkeycheck.h MSVC STL даёт #error на
макроизацию ключевого слова. Это меняет только манглирование внутри таргета:
он заменяет (не линкуется с) игровые Render-библиотеки. На GCC манглирование
доступа отсутствует — там достаточно локального хака в `EditorSokolDevice.cpp`.

### `EditorSokolRender` (render/EditorSokolDevice.{h,cpp})

Подкласс игрового `cSokolRender`, создаваемый только фабрикой
`CreateEditorSokolDevice()`; доступ к приватным членам — через ограниченный
хак. Переопределения:

* `Init` — базовый `Init` с нулевым SDL-окном, затем пулы/sg_setup (размер и
  sample_count=1 от виджета), simgui_setup, `debugUIEnabled=false`, сэмплеры,
  `emptyTexture`, `UpdateRenderMode()`.
* `EndScene` — перед родителем подменяет `swapchain` (ширина/высота и
  `gl.framebuffer` = FBO виджета, ? 0).
* `Flush(false)` — без SDL-свапа: `sg_commit()`, `ClearPooledResources`,
  `ClearAllCommands` (Qt сам композитит виджет).
* `Done` — родитель (пропускает sg_shutdown при нулевом окне) + свой
  `sg_shutdown()`.
* Хелперы: `setDeviceTarget(device, fbo, w, h)` — кадр в FBO виджета;
  `resetDeviceStateCache(device)` — `sg_reset_state_cache()`.

sokol здесь НЕ владеет контекстом: между кадрами QPainter и texture blitter
портят GL-состояние, поэтому `TerrainGpuView::renderFrame` каждый кадр зовёт
`resetDeviceStateCache` до `BeginScene`, чтобы sokol заново применил всё своё
состояние, а не только дельты.

### `TerrainGpuView` (render/TerrainGpuView.{h,cpp})

Сборка сцены (в init, контекст актуален): `CreateIVisGeneric` >
`SetData(device)` > `SetShadowType(SHADOW_NONE,0)` (отключает per-frame
CreateLightmap) > `CreateScene` > `DisableTileMapVisibleTest()` (до CreateMap)
> `CreateCamera()` + `SetAttr(ATTRCAMERA_PERSPECTIVE)` >
`CreateMap(terra_, 0)` (SetBuffer сам создаёт tilemap и ставит полный
UpdateMap). Разрушение — в обратном порядке при живом девайсе: tilemap >
camera > scene > visGeneric > device (dtor cSokolRender зовёт Done).

* Камера — дословная копия `terCameraType::update()` + `SetCameraPosition`
  (Source/Game/CameraManager.cpp) с параметрами psi = PI/2 + turn,
  theta = lean ? 90°, r = H/cos(theta), H = focusC + cameraDZ (высота над
  zeroplast-плоскостью в клетках), фокус в клип-координатах =
  focalDevPx / ширина_экрана. Виджет передаёт focalDevPx = focusC ? DPR,
  поэтому масштаб "клеток на виджет-пиксель" = (F+Z)/F — не зависит от DPR и
  совпадает с формулами CPU-вида.
* Пикинг — `cCamera::GetWorldRay` (вход pe в [?0.5,0.5], y вверх; домен тот
  же, что у ConvertorCameraToWorld) + собственный ray-march по высотам
  (`SGetAlt`, вход обязан быть clamped — офсет не циклический) с бисекцией.
* `projectToScreen` — `cCamera::ConvertorWorldToViewPort` (девайс-пиксели,
  y вниз).
* Цвета — `EditorTerraInterface` (наследник `StandartTerraInterface`):
  `GetTileColor` берёт пиксели из кэша `ViewportRenderer::colorAt`
  (фильтры слоёв + приглушение geo — ровно то, что показывает TopDown);
  альфа всегда 0xFF — сценa создаётся с zeroplastnumber=0 (зелёные
  zeroplast-квадраты игры — рантайм-эффект, CPU-вид их тоже не рисует, а
  маркер 0xFE проделал бы дыры в террейне).

### Интеграция в `ViewportWidget`

* Конструктор запрашивает `QSurfaceFormat` (desktop GL ? 4.1) только для себя.
* `setSession`/`reloadWorld`/`setGeoDimmed` зовут `scheduleGpuRebuild()` —
  пересборка сцены выполняется в `paintGL`/`initializeGL` (контекст актуален;
  без него sokol/тайлмапу делать нечего).
* Dirty-прямоугольники `renderer_->update()` (штампы кисти, undo/redo)
  раздаются и в тайлмап: `gpuView_->updateCells(...)` — та же каноника,
  что и у 2D-кэша.
* Пиксельная математика GPU-режима (currentViewRect / pan / pxPerCell /
  сетка) — без клампа окна 640: cellsPerWidgetPx = (F+Z)/F прямо, kv-эвристика
  по сырому lean; 640-кламп остаётся только в CPU-ветке.
* Сетка в GPU-режиме — плоскость zeroplast, линии проецируются через
  `projectToScreen` и рисуются QPainter'ом (прямая на земле остаётся прямой
  в перспективе).
* После sokol-кадра: вернуть FBO виджета и выключить depth/blend/scissor
  перед QPainter.
* Формулы MinimapWidget (вид-прямоугольник по currentViewRect) сохранены —
  по построению они остаются согласованными.

### `MinimapWidget`: дисциплина native-first

Раньше `ensureMinimapTexture()` делал raw-GL между конструированием QPainter
и `beginNativePainting()` — UB для GL paint engine. Теперь загрузка текстуры,
clear и blit выполняются до конструирования QPainter (как в ViewportWidget),
QPainter рисует только оверлеи. Контекст-хук `aboutToBeDestroyed` освобождает
GL-объекты при пересоздании контекста.

### Известные ограничения GPU-режима

* Dam-фичи CPU-рендера (`damFrozen` — торцевые повторы, террасность) в
  GPU-виде игнорируются: рендерится одна карта, как в игре.
* Рендер каждый кадр без кэша кадра (стоимость как в игре, ~единичный
  tilemap-проход; рисование только по update()).
* Вид "как в игре": пулы текстур дают лёгкое сглаживание, которого нет в
  Chunky-режиме TopDown; это ожидаемое отличие от CPU Oblique.

## 5.24. Кисть ImageDecal — палитро-ограниченный штамп картинки

Кисть ставит на карту картинку, но не как маску влияния (T3.5), а как набор
индексов палитры Dam: каждый пиксель — цвет поверхности дамбы. Поэтому штамп
стоит ровно столько же, сколько `SetColor`, и никакой RGB на карте не хранится.

**Конвертация (`core/ImageDecal.{h,cpp}`, Qt-free).** `ImageDecal::prepare()`
получает RGBA-байты, 768 байт `vrtMap::DamPal` и 256 флагов «этот индекс уже
использует дамба мира» (`EditorSession::damPaletteUsage()` — проход по
`VxDBuf`/`SurBuf`):

1. **Размер.** Больше `kMaxImageSize = 512` по любой стороне — отказ с текстом
   «The maximum size of an image is 512 px on each side». Штамп 512x512 уже
   покрывает четверть карты 1024, больше для кисти не нужно.
2. **Прозрачность.** Участвуют только полностью непрозрачные пиксели
   (`alpha == 255`); «почти непрозрачный» (254) — это прозрачный пиксель и он
   никогда не красит.
3. **Проверка ёмкости палитры.** Считаются `unusedDamColors = 256 − занятых` и
   `imageForeignColors` — число различных цветов картинки, которых нет в
   палитре. Если свободных меньше двух **и** «чужих» цветов больше двух —
   возвращается ошибка (в палитре не хватит места на новые цвета). Это ровно
   правило из фидбека: 0/1 свободный слот при пёстрой картинке = отказ, 2 и
   больше — работаем.
4. **Список цветов (шаг 3).** Кандидаты = индексы палитры, чей цвет есть в
   картинке ∪ индексы, уже используемые дамбой мира; список добивается
   свободными индексами до `kMinPaletteColors = 64`. Эти цвета — начальные
   центры k-means.
5. **k-means (шаг 4).** Кластеризация по непрозрачным пикселям, взвешенная по
   частоте; точки — 5-битные RGB-корзины (суммы точные, поэтому центр кластера
   — истинный средний цвет, а фотография не раздувает число точек). Пустые
   кластеры отбрасываются: подложенные «для 64» цвета не занимают палитру.
6. **Размещение (шаг 5).** Центр, совпавший с цветом палитры, переиспользует её
   индекс (и помечается занятым, чтобы новый цвет его не перезаписал). Новый
   цвет занимает первый свободный (не используемый дамбой) индекс и попадает в
   `paletteWrites`; если свободных не осталось — привязывается к ближайшему
   существующему цвету. Существующие цвета дамбы никогда не перезаписываются.

**Кисть (`BrushEffect::ImageDecal`).** Хранит `DecalImage` (индексы, −1 =
прозрачно) в `BrushTool::setDecalImage()`. `applyStamp()` центрирует деку на
клетке клика, строит маску по её bbox (влияние 255 там, где индекс ≥ 0) и
красит `SurBuf` индексом пикселя — по правилам `SetColor`: только клетки дамбы
(`VxDBuf != 0`), буферы высоты не трогаются. Кисть работает только в режиме
Dam: в Geo-режиме `applyStamp()` отказывает, кнопка Geo в UI блокируется, а
переключение в Geo переводит тип кисти в обычный Raise. `applyLine()` деку
отказывает — у неё своя прямоугольная геометрия (ViewportWidget не начинает
линию для этого эффекта).

**UI.** Кнопка `Image Decal` — одновременно тип кисти и выбор файла
(PNG/TGA/BMP): клик включает эффект, принудительно ставит Dam и открывает
диалог; отмена сохраняет ранее загруженную деку. После `prepare()` новые цвета
пишутся в палитру через `EditorSession::setPaletteRgb(Dam, …)` +
`applyPalettes()`, панель палитр (`PalettePanel::refresh()`) и рендереры
(`refreshPaletteRenderers()`) обновляются. Спинбокс масштаба общий с
маской-картинкой T3.5: для деки он вызывает `ImageDecal::scaleNearest()` от
несжатого оригинала, поэтому повторное масштабирование не накапливает
искажений.

## 5.25. Камера «как в игре» — модель terCameraType в TerrainGpuView

**Что.** Пара пунктов меню View — `Camera Like in Game` / `Camera Like in
Editor` (эксклюзивная группа). Первый переводит GPU-oblique вид на камеру
главной игры: та же параметризация `CameraCoordinate` (psi/theta/distance
вокруг точки взгляда) и тот же фрустум — фокус = скриптовая опция
`HardwareCameraFocus` (0.8, `Scripts/Config.prm`) в clip-space, zplane
(30, 1e5) — т.е. игровой FOV. Второй возвращает редакторскую камеру
(`View3DCamera`: turn/lean/lift/focus), её состояние при переключениях не
теряется.

**TerrainGpuView.** `CameraState` получил ветку `gameMode` (psiDeg/thetaDeg/
distance/focusClip); `applyGameCamera()` дословно воспроизводит
`terCameraType::update()` + `SetFrustumGame()` (CameraManager.cpp):
радиус = distance × aspectScale, aspectScale = (sizeX/sizeY)/(4/3),
matrix = Mat3f(theta, X_AXIS)·Mat3f(PI/2−psi, Z_AXIS) с теми же flip-ами
`SetCameraPosition`, камера z клампится в [200, 10000] (CAMERA_MIN/MAX_HEIGHT,
restricted-игра — в поставляемом Perimeter.ini `CameraRestriction = 1`).
Тета клампится в [0, PI/2.85] (CAMERA_THETA_MAX restricted-игры), дистанция —
в [300, 5000] (CAMERA_ZOOM_MIN/MAX).

**Пресет (`core/GameCameraPreset`).** Состояние «камеры первого игрока мира»
редактор берёт там же, где его берёт игра: триггер `ActionSetCamera`
(`Units/Triggers.cpp:1149`) ищет сплайн `Camera<idx>`/`UserCamera<idx>` в
`manualData.cameras` и при `useAsSpline=false` ставит координату из первой
точки `path`. Резолвер пробует `RESOURCE/Multiplayer/<мир>.spg`, затем
`Battle/`, `Worlds/`; берёт `SpgFile::playerCamera(0, …)` (первая точка
сплайна: position{x,y} + psi/theta в радианах + distance), при отсутствии
сплайна — якорь фрейма игрока 0, иначе фолбэк-центр с игровыми дефолтами
терCameraType (psi=0, theta=0 — надир, distance=300). Нюанс данных: у
`Worlds/FORTOP.spg` миссионная заглушка — `cameras = { 0; }` (первый скаляр
XPrm-коллекции — число элементов) и `frame = 0` без позиций; настоящие
камеры игроков лежат в `Multiplayer/FORTOP.spg` (FORTOP, игрок 0:
psi=1.56223, theta=0.314159 = PI/10, distance=1000 — наклонный вид на спавн).

**Взаимодействие в игровом режиме.** Жесты маппятся на игровые величины:
колесо → distance (×kZoomStep, клампы игры), орбита (Alt+левая / View-режим)
→ psi/theta, пан (средняя/правая) — «тащить рельеф»: `panObliqueGame()`
берёт клетку под курсором через `pickCell()` (реальный луч камеры) и
удерживает её под курсором, дельта укорачивается через шов тора. Тулбарные
Rotate/Tilt/Zoom/Reset работают через те же ветки. `centerOnCell` (клик по
миникарте) двигает центр игрового фрустума.

**Кисть в игровом режиме.** Штамп не зависит от камеры: клик/драг берут
клетку через `pickCell()` реального фрустума, применение кисти — прежний
пайплайн буферов + dirty-rects + `updateCells`. Нюансы: (1) в игровом режиме
НЕВЕРНЫЙ фолбэк пикера на CPU `view3d_` отключён — там проекция редакторской
камеры, не совпадающая с отображаемой (штамп ушёл бы в чужую клетку);
(2) превью кисти — `projectedBrushContour()`: контур ВЫБРАННОЙ пользователем
формы (круг — выборка диска, квадрат — подразбитые рёбра) проецируется
через игровой фрустум по высотам рельефа; эвристическое кольцо редакторской
камеры в этом режиме не рисуется вовсе.

**Миникарта.** Жёлтая рамка в GPU-режиме строится из `groundFootprint()`
(луч в каждый угол экрана через `cCamera::GetWorldRay`) — она учитывает
любой фрустум автоматически, включая игровой FOV/aspect; в игровом режиме
`currentViewRect()` (потребители прямоугольника) считается как bbox этого
же полигона.

**Проверка.** Тест 72 (`GameCameraPresetTests`) — чтение сплайна
`Multiplayer/FORTOP.spg`, конверсия радиан→градусы, фолбэки; GUI-прогон
`MAP_EDITOR_AUTOTEST=1 MAP_EDITOR_WORLD=FORTOP`: переключение действием
меню, кадр `18_game_camera`, рамка миникарты `19_minimap_game` (полигон
центрирован на (354.8, 306.4) — точка взгляда Camera0), реальный штамп
кистью `20_game_brush_stamp` (152 тыс. изменённых пикселей) и undo
`21_game_brush_undo` (терраин восстановлен бит-в-бит, остаточная разница с
до-штампным кадром — только кольцо превьи под курсором).



## 5.26. 3D-кисти — твердые тела поверх Raise / Lower / Set-to-Height

Шесть фигур на тулбаре Sculpting (Dam-режим только, как скульптинг):
**Cone / Pyramid / TruncatedCone / TruncatedPyramid / Torus (верхняя
половина) / HalfEllipsoid**. Это не отдельные эффекты, а геометрия
(`BrushParams::shape3d`), наложенная на ОБЫЧНЫЕ типы кисти: с Raise/Lower
Terrain и Set-to-Height фигура штампуется соответствующей модой.

- **`core/Shape3D.h`** — чистая анлитика профиля (Qt-free, vMap-free):
  `shape3DProfile(kind, settings, dx, dy) → [0;1]` — нормированная высота
  поверхности тела в колонке (dx, dy) от центра основания. Конус/пирамида —
  линейное падение от вершины (у пирамиды знаменатель — радиус грани
  правильного многоугольника в направлении колонки: а(θ)=апофема/cos δ);
  усечённые тела — пересечение колонки с боковой поверхностью усечённого
  конуса (квадратное уравнение |p−off·z| = r0+(r1−r0)·z, первый корень в
  [0;1], под верхней крышкой → 1); тора — полусечение кольца (пик на
  среднем радиусе); полуэллипсоида — полукруглое куполообразное сечение.
  `clampShape3DSettings` клампит верхнюю часть строго внутрь основания
  (норма смещения / верхний радиус / выведенный из длины стороны верхний
  описанный радиус ≤ R−0.5 клетки). У тора «upper part radius» —
  внутренний радиус кольца, усечённой пирамиды «upper part side» —
  длина стороны верха (верх подобен базе).
- **Штамп** (`BrushTool::applyShape3D`, два прохода как у скульптинга):
  основание фигуры — маска штампа (`BrushMasks::filledCircle` /
  `filledPolygon` с общими polygonSides/polygonAngle); цель клетки —
  абсолютная `Height + round(профиль·ShapeHeight)` **в целых вокселях**
  (таргет квантуется: `setHAppoximation` клампит тулзер на границе целых
  вокселей, дробная цель была бы недостижима и штамп не сходился бы в
  no-op). Raise (ChangeHeight
  direction>0) двигает клетки к цели снизу только, Lower — сверху только,
  Set-to-Height (AlignVariableH) — в обе стороны. Запись через тот же
  variable-H toolzer (tVoxSetAll, без hardness-затухания), ZP-гейт
  снимается, дамба посевается; Shape Height = 0 в Lower/Set стирает форму
  до базы (дamba снимается там, где рельеф до неё дошёл). Height gate —
  по высоте до штампа. **No-op precheck до recordUndoArea**: повторный
  штамп готовой формы / raise над более высоким рельефом — отказ без
  записи в историю («достигнутая высота не трогается»).
- **UI** (`MainWindow`): шесть кнопок в тулбаре Sculpting + спинбоксы
  Shape Height (амплитуда 0..255), Upper part X/Y (смещение вершины),
  Upper part radius, Upper part side — каждый включён только у фигур,
  которые его потребляют (`shape3DHasTop*`); число сторон и угол —
  общие спинбоксы 2D-полигона (доступны и у пирамид). Выбор 3D-фигуры
  форсирует Dam и сбрасывает не-height тип кисти на Raise; выбор любого
  другого типа/формы кисти или Geo-режима сбрасывает shape3d (правило
  как у image mask). Превью в обоих видах — основание фигуры (круг/
  многоугольник; у тора — с внутренним кольцом).

**Проверка.** Тесты 93/94 (`Shape3DTests`): профили всех шести фигур +
клампы; на мире — flatten Set'ом с Shape Height 0, Raise строит конус
(центр = база+амплитуда, стена линейна, повторный штамп — refused no-op),
undo/redo байт-в-байт, Lower с 0 стирает форму до базы, основание пирамиды
= полигональной маске (клетка вне треугольника не тронута), Geo отказан.


## 5.27. Кисть «модель как хайтмап» — ModelBrush + тулбар Model

Импорт PLY-модели и штамп её как прямоугольного хайтмапа (Dam только).
Собственный тулбар **Model** (`addToolBarBreak()` перед ним): кнопки
**Import Model...** (диалог .ply), **Use Model Brush** (включает кисть;
доступна после успешного импорта и при загруженном мире), режимные кнопки
**Place / Add / Subtract** (эксклюзивная группа) и спинбоксы **Height**
(0..255 вокселей — z-диапазон модели масштабируется пропорционально на
0..Height) и **X/Y scale** (0..1, размер размещения). Превью во всех
путях отрисовки (2D/3D, GPU-проекция + фолбэки) — прямоугольник размещения
(`ViewportWidget::setBrushPreviewRect`, асимметричные полу-экстенты;
прямоугольник рисуется веткой Square).

- **`core/ModelBrush.{h,cpp}`** — импорт PLY (ascii и binary_little_endian;
  big-endian и прочее — ошибка с описанием). Модель трактуется как ТВЁРДОЕ
  ТЕЛО: XY-прямоугольник вершин растризуется в сетку (длинная сторона до
  512, аспект сохранён), и высота ячейки — ВЕРХ МОДЕЛИ НАД ЭТОЙ КОЛОНКОЙ:
  каждая грань (fan-триангуляция полигонов) сэмплируется в центре ячейки
  (барицентрика), побеждает МАКСИМАЛЬНАЯ поверхность — внутренность
  замкнутого меша покрывается верхними гранями, а не остаётся дырками
  (иначе куб давал бы «четыре угловых столба»). Цвет — барицентрическая
  интерполяция цветов победившей грани; при точном совпадении высот первой
  грани wins. Модели без граней (облако точек) — по максимуму вершин в
  ячейке. Пустые колонки (настоящие дырки/вне тела) — высота 0 и средний цвет
  модели. Цвет вершины: red/green/blue, либо текстура из `comment`-строки
  заголовка со словом «texture» (24-бит TGA рядом с .ply,
  `WorldImages::loadTga24`), сэмплируемая по UV (v = 0 — низ текстуры, кламп в
  [0;1] — edge repeat); без текстуры и вершинных цветов модель красится
  БЕЛЫМ. Квантование цветов — `ImageDecal::prepare` (тот же
  k-means с учётом неиспользуемых цветов палитры); `paletteWrites` пишутся в
  Dam-палитру как в декале. Ошибки: «Unable to import from PLY the model
  <имя>\n<описание>».
- **Штамп** (`BrushTool::applyModelBrush`, два прохода + no-op precheck до
  recordUndoArea — как у 3D-кистей): размер штампа =
  round(размер_растра × scale), ресемплинг ближайшим соседом (высоты и
  индексы). Цели в целых вокселях (кламп тулзера — целые воксели): **place**
  target = round(norm·Height), обе стороны + покраска SurBuf квантованным
  индексом там, где дamba осталась; **add** target = round(средняя_по_крышке
  + norm·Height), только вверх; **subtract** target = round(средняя −
  norm·Height), только вниз, кламп ≥ 0 — уход ниже рельефа снимает дамбу
  (тулзер сам). Height gate по высоте до штампа; Geo отказан; Line нет.
- **Эксклюзивность**: modelBrush сбрасывается выбором любого типа кисти,
  2D-формы, image mask, декали, 3D-фигуры и Geo-режимом; активация модели
  сбрасывает shape3d/useImageMask. Квантование цветов ленивое: при импорте,
  если мир загружен, иначе — при первом включении кисти.

**Проверка.** Тесты 95/96 (`ModelBrushTests`): ascii/binary PLY дают один
растр (макс-высоты, цвета вершин, дырки), текстура по комментарию сэмплится
через UV, все ошибки импорта с описаниями; на мире — place ставит высоты
рампы 0/⅓/⅔/1 и красит индекс там, где дamba есть (западная колонка на
уровне гео без дамбы), undo/redo байт-в-байт, add/subtract от средней
плоского прямоугольника (глубокий subtract снимает дамбу), scale 0.5
сужает штамп до двух колонок, Geo отказан.

## 5.28. Режим различий (.gmp) — различия террейна боевой карты

Боевые карты могут нести бинарные различия террейна рядом с `.spg` — формат
игры `vrtMap::loadGameMap/saveGameMap` (VMAP.cpp:952-1090): `int` индекс мира
(не проверяется загрузчиком), таблица флагов грубых областей `(V>>6)*(H>>6)`
(`kmGridChA=6`), на каждую отмеченную область четыре АБСОЛЮТНЫХ блока
64×64 — `VxG, VxD, Atr, Sur`. Хвост (`saveGrid`) необязателен — игра читает
его только если байты остались.

- **Модель** (`EditorSession`): `diffAreas_` — map «индекс грубой области →
  4 блока абсолютных байт»; вся логика Qt-free в ядре. Пока режим ВЫКЛЮЧЕН,
  буферы vMap — БАЗОВЫЙ террейн, правки идут в мир. При ВКЛЮЧЕНИИ сессия
  снимает снапшот базы (`baseGeo_/…`, 16 МБ на 2048²) и кладет в буферы
  БАЗУ+РАЗЛИЧИЯ (то, что показала бы игра с .gmp).
- **Захват правок**: единая точка — `regRenderWithShadowTrail()` (её зовут
  все кисти, импорт, undo/redo после правки буферов): в режиме ON
  `resyncDiffRect()` за заново отрендеренный прямоугольник сравнивает буферы
  с базой и обновляет/удаляет записи областей. Побочный эффект: undo в
  режиме различий сам схлопывает модель до пустой.
- **Чистота мира**: правки в режиме ON НЕ помечают мир изменённым —
  `recordUndoArea`/`markModifiedAgainstSavedState` в diff-режиме ставят
  флаг `diffModified_` (данные различий изменены с последнего
  `saveDiffToGmp`/загрузки), а флаг мира не трогают. Флоу выхода
  (`confirmDiscardUnsavedChanges`) сначала предлагает сохранить МИР (если он
  правился в OFF-режиме/палитрой), затем — СОХРАНИТЬ РАЗЛИЧИЯ В .GMP
  (Save/Discard/Cancel); мерж различий в мир из этого промпта невозможен.
- **Переключение** (`setDiffMode`) меняет СОДЕРЖИМОЕ буферов целиком и
  ЧИСТИТ историю undo (снапшоты другого состояния испортили бы картину);
  полная перерисовка через `regRender(0,0,H,V)` + `invalidateAll()` вьюпорта.
  Модель различий переживает выключение (OFF фиксирует её полным resync).
- **.gmp I/O**: `saveDiffToGmp`/`loadDiffFromGmp` — ровно игровой корневой
  формат (загрузка заменяет модель; при включённом режиме экран обновляется
  сразу). Блоки различий geo/dam хранятся в 16 битах на высоту
  (`uint16_t`), в файл уходит прежняя 8-битная секция (кламп 255) плюс
  трейлер "XH16" с полными 16-битными блоками при высотах >255 (тот же
  приём, что у `vrtMap::saveGameMap`; см. docs/map_logic.md). UI: тоггл
  «Difference Mode» на View-тулбаре/меню (F2), File →
  Save/Load Difference (.gmp) (путь по умолчанию — сосед .gmp загруженной
  боевой карты, иначе диалог; работает в любом состоянии тоггла). **Save мира
  пишет ВСЕГДА базовый террейн** — весь файловый конвейер (`writeWorldFiles`)
  гоняется внутри `runWithBaseTerrain()`, различия в output.vmp не попадают
  ни при каких обстоятельствах. При выгрузке мира состояние режима
  сбрасывается.
- **16-битные высоты** (лифт лимита 256→8191 вокселей, docs/map_logic.md):
  снапшоты undo держат geo/dam в `uint16_t` (`UndoAreaSnapshot`), спинбоксы
  высот кистей/скульптов/gate/`hZeroPlast` — домен `0..MAX_VX_HEIGHT_WHOLE`
  (8191); sidecar мира `heights16.bin` пишется/читается самой Terra
  (`save3BufOnly`/`fullLoad`), мастер нового мира кладёт его для плоского
  рельефа выше 255 вокселей (`WorldCreation::writeFlatVmp`).
- **Превью — всегда от базы**: `map.tga`/`cache.tga` (сейв мира, автoфикс
  регенерации) и Export Top View генерируются через
  `runWithBaseTerrain()` — временный своп буферов на базу (эффективное
  содержимое возвращается после). Экран выбора карты в игре показывает
  `map.tga` мира и НЕ применяет .gmp, поэтому превью не должно нести
  различий.

**Проверка.** Тест 98 (`GmpDiffTests`): тоггл база/база+различия и захват
штампа; байтовая сверка сохранённого .gmp с игровым форматом; загрузка
рукотворного .gmp с абсолютными значениями (в обоих порядках тоггла);
undo стирает модель (пустой .gmp = заголовок + флаги); round-trip.

## 5.30. M3D-пайплайн зданий — BuildingModels + UnitModelCatalog

Реальный рендер M3D-моделей игры во вьюпорте редактора и панельные иконки
кнопок зданий. Ключевой момент: весь стек моделей уже скомпилирован в
MapEditorRender (§5.23 компилит `ObjLibrary/MeshBank/ObjNode/TexLibrary/
FileImage` как в игре), а сцена вьюпорта — настоящая `cVisGeneric`+`cScene`,
поэтому `cScene::CreateObject(name, texturePath)` (тот же вызов, что в игре
через `createObject` → `terScene->CreateObject`, UnitAttribute.cpp:392)
загружает M3D и аттачит его — существующий `scene_->Draw(camera_)` рендерит
модель с текстурами и светом без единой правки игрового кода.

- **PluginMAX** — реальный парсер M3D (cMeshFile/cMeshScene + объектная
  модель) скомпилирован в MapEditorRender тем же списком, что и либа
  PluginMAX, минус ZIPStream.cpp/zip_resource.cpp (ни один Src-файл ZIP не
  трогает; `ResourceFileRead` ObjLibrary читает через файловый стаб ZIPStream
  из shim/game_stubs.cpp, `ZIPIsOpen` всегда false). Исторические стабы
  cMeshFile/cMeshScene/sSubTexmap в game_stubs.cpp удалены — без них LoadM3D
  падал в VisError («Cannot read file» → abort) при первой попытке создания
  модели.
- **UnitModelCatalog** (`core/UnitModelCatalog.h`) — сгенерированная из
  `Source/Scripts/UnitAttribute.prm` таблица «атрибут → ModelNameArray[0]
  (построенная модель), BoundRadius, BoundScale». Игра компилирует атрибуты
  в exe (`scripts_export::unitAttributeDataTable`) и не читает .prm ниоткуда,
  поэтому редактор тоже берёт их статической таблицей (для всех модов
  одинаково). Масштаб повторяет `GeometryAttribute::initGeometryAttribute`:
  `BoundRadius > 0 ? BoundRadius / nativeBoundRadius : BoundScale`
  (debuScales — чит-дебаг, по умолчанию 1).
- **BuildingModels** (`render/BuildingModels.{h,cpp}`) — слой на сцене
  вьюпорта: directional light по рецепту игры (`Runtime.cpp`: направление
  (-234,0,-180), ambient приподнят до 0.3 — иначе теневые грани чёрные),
  пул инстансов `cObjectNodeRoot` (index-aligned со списком оверлея; рост —
  CreateObject, уменьшение — `Release()`, как в игре), превью-инстанс Place
  (скрытие через `ATTRUNKOBJ_IGNORE`). Поза: `z = hZeroPlast − boxMin.z·scale`
  (`terBuilding::setPose`; `boxMin` из `GlobalBound`, считается при загрузке
  в `cObjLibrary::LoadM3D` → `CalcBorder`, масштаб применяется через
  `SetScale`+`SetPosition`+`Update`), x/y — как есть (1 клетка == 1 мировая
  единица). Текстуры — фракционный путь по умолчанию
  `Resource\Models\Main\EXODUS\` (`GetBelligerentTexturePath`, дефолтная
  фракция), здания ничьи.
- **TerrainGpuView**: `syncBuildingModels()`/`setBuildingModelPreview()`
  (zeroplast из vMap.hZeroPlast),
  `renderModelIcon(fbo, w, h, attrId)` — с теми же путями effect-библиотек, что в игре
  (`SetEffectLibraryPath("RESOURCE\FX", "RESOURCE\FX\TEXTURES")` при init —
  без них ParseNodeEffect падает в VisError на моделях с "effect:"-узлами,
  например filth_spot.m3d -> steam.effect); запекание иконки в чужой FBO: ленивая отдельная icon-сцена (свой light +
  камера по рецепту BGScene: сферическая позиция, фрустум с focus =
  dist/2.6r), рендер через тот же device (`setDeviceTarget` на FBO,
  прозрачный фон). Qt-сторона (`ViewportWidget::bakeBuildingIcon`) даёт
  `QOpenGLFramebufferObject`, делает контекст current и заворачивает readback
  в `QIcon` (флаг латчится по первому успеху, до GPU-вьюпорта кнопки
  текстовые и запекаются позже).
- **ViewportWidget**: синхронизация поз перед `renderFrame` (оба списка —
  overlay и модели — index-aligned); ghost-диски в `drawBuildingPoints3D`
  рисуются только для слотов без модели (CPU-фолбэк/незагрузившийся M3D),
  превью-круг валидности остаётся всегда. 2D и миникарта без изменений
  (белые точки — как радар игры).

## 5.33. Встроенный MCP-сервер (QHttpServer + JSON-RPC 2.0)

Каталог инструментов — `mcp/McpTools.h` (имя + агентское описание +
JSON Schema), общий для приложения и тестов, 28 инструментов:
set_game_path / list_worlds / get_world_properties / create_world /
open_world / save_world / list_battle_maps / open_battle_map /
save_battle_map / new_battle_map / list_battle_map_objects /
place|update|delete_{building,scum_spot,nature_object} / apply_brush /
run_script / set_scripted_brush_script / get_terrain_at / get_palette /
set_palette_color / undo / redo. Описания мутирующих инструментов и undo
упоминают группировку правок внутри 500 мс в одну undo-транзакцию.

- **Мост** (`ui/MainWindowMcp.cpp`): сервер живёт на UI-потоке (QHttpServer
  обрабатывает соединения в событийном цикле своего потока — обращения к
  vMap/editor-state строго однопоточны, как у виджетов). Каждый инструмент
  зовёт те же core-пути, что UI-экшены/панели (диалоги заменены строковыми
  аргументами: run_script -> runEditorScript, set_scripted_brush_script ->
  BrushParams.script, open_battle_map -> battleMap_.load + мир из spg и т.д.).
  Результат — JSON; ошибка -> {"error": ...} -> MCP isError.
- **Порт**: map_editor.ini рядом с exe, [mcp] port=N, default 10102
  (McpServer::configuredPort). Занятый порт — предупреждение в trace,
  редактор работает дальше. start()/stop() пересоздают QHttpServer +
  QTcpServer целиком — рестарт на том же порту без "address already in use".
- **Компиляционный нюанс**: Qt6 навязывает потребителям /permissive-, под
  которым ломается legacy-тернарий PrmString в Util/EditArchive.h (цепочка
  terra.h -> tools.h -> UnitAttribute.h). Мост не включает terra.h вообще
  (terrain-сэмпл — Qt-free EditorSession::terrainSample); тестовые TUs,
  включающие terra.h, собираются с /permissive (per-file override).
- Тестирование: тесты гоняют НАСТОЯЩИЙ сервер по loopback через
  QNetworkAccessManager (main() обзавёлся QCoreApplication).

**Проверка.** Тест 110 (`McpServerTests`): каталог (все обязательные
инструменты, описания >40 символов, схемы-object, заметка 500 мс у undo и
apply_brush), ini-конфигурация порта, протокол (initialize/list/call/
isError/unknown-tool/notification 202/unknown-method -32601/GET), рестарт
на том же порту, занятый порт -> чистый отказ.

## 5.35. Разбиение MainWindow — вынос BattleMapController (2026-11)
